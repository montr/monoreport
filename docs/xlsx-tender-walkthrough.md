# Authoring the XLSX tender sample

1. Start with [xlsx-tender.template.xlsx](../Samples/xlsx-tender.template.xlsx) and [xlsx-tender.json](../Samples/xlsx-tender.json). Generate with the existing CLI using --template Samples/xlsx-tender.template.xlsx --json-file Samples/xlsx-tender.json --output tender.xlsx, or submit the same files through Core MergeEngine.Merge or POST /api/documents/generate. The sample has two bidders, two criteria and a lot containing two items. It requires no Excel runtime. Automated Core, CLI and HTTP transport checks use a small generated, test-owned repeating workbook through XlsxTransportFixture; they do not read or verify this user-facing sample. Separate Core subsystem tests verify supported values, formulas, merges and Cartesian structures with test-owned inputs. This sample's acceptance requires manual generation and Excel checks for appearance, calculation and printing; those checks are not established by the automated transport or Core subsystem results.
2. In Excel, set the Tender worksheet's PrintArea to B3:F10. This is the complete retained report. Column A and rows 1–2 contain controls outside it; output physically removes those margins and moves the retained report to A1. Keep every required formula input inside PrintArea. Worksheets using repetition controls require one finite rectangular area; uncontrolled worksheets may omit PrintArea and retain their coordinates and sparse content. Explicit disjoint areas and references to discarded content reject.
3. Place $h(1) in D1:E1 and $h(2) in E2. These top control rows describe geometry: D:E is the parent block and E is its child. In A5 put $header(1).Bids and in A6 put $header(2).Criteria to associate header rows with collections. Their short forms are $h(1).Bids and $h(2).Criteria. Both parent columns repeat once per bidder; the child repeats once per criterion. D is a parent-only column with authored width zero and hidden state. It still occupies a column and adds no data records. The authored merge D5:E5 expands with its children; the engine does not invent headings, merges or formatting.
4. In column A, rows 7–9 use $level(10).Items, $l(20).Items and $l(10).Items. Numeric levels establish presentation: the first lot block is a header, item blocks repeat beneath it, and the final lot block is a footer. Consecutive equivalent markers form one multirow block; an unmarked control row ends a vertical region. JSON numeric levels determine actual data ancestry; $path is an opaque grouping key, never an ancestry path or sort key.
5. Supply each logical row as four adjacent Items records, in this exact positional order: Alpha/Unit price, Alpha/Lead days, Beta/Unit price, Beta/Lead days. That is the Cartesian product of Bids then Criteria in input order. The lot also needs four records even though its header has no intersection field. Each group has one $path and a consistent integer $level. Preserve input order and keep groups contiguous; a path must not reappear later. There are no bidder/criterion IDs for remapping, sparse records or per-bid criteria lists. A permutation of complete records cannot be detected. If either horizontal collection is empty, supply exactly one descriptor record per logical row instead.
6. Header {Company} in D5 resolves from the current bidder, while {Name} in E6 resolves from the current criterion. In a horizontal header, ../ accesses the preceding header level. The title uses explicit document-root {$.Title}. Ordinary vertical fields {Name} and {Quantity} use the first record of each logical group. B8 combines the item name with {../Name}, which follows the actual data parent to the lot. E8's {Value} resolves from its own positional intersection record. Parent-only D8 uses the first logical-row record. A missing ordinary property follows the existing missing-value policy; an unavailable vertical ancestor emits an empty value and a warning by default. Strict Core MissingValues.Error rejects it.
7. E9's SUM(E8:E8) is an authored lot subtotal, relocated separately for each generated bidder/criterion column and expanded over both item rows. Output is A1:I9; headings merge at C3:E3 and F3:H3, item values occupy D6:E7 and G6:H7, and formulas occupy D8, E8, G8 and H8. Complete unformatted scalar numbers remain Excel numbers; authored number formats stay intact. Surrounding text or explicit formatters produce text. Formulas request recalculation on opening; MonoReport does not calculate them or cache new totals.
8. Keep one horizontal region per worksheet. Recursive headers and branching siblings are supported, but controls must describe contained blocks and a complete shared Cartesian product. Use supported finite A1 formulas and safe retained merges. Tables, charts/drawings, conditional formatting, validation, hyperlinks and unsupported metadata reject; see [XLSX compatibility](xlsx-template-compatibility.md) for the full boundary. ISO date strings remain text, and unsafe numeric precision rejects rather than truncates.
9. CLI successful warnings go to stderr in Core order with available source/data context and exit code 0. HTTP defaults to binary. Explicit Accept: multipart/mixed requests the document and diagnostics.json attachments from the same merge; diagnostics always contains format, fileName and warnings, including an empty array for this sample. See the [HTTP documentation](../README.md#http-api-and-playground) for quality negotiation and failure behavior.
