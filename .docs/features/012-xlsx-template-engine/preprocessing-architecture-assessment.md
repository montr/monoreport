# Feature 012 — Preprocessing alternatives for the XLSX engine

## 1. Conclusion and authority

1. **Updated: 2026-10-22. Recommendation, not an adopted architecture decision:** retain the accepted source trees, bound data hierarchy, scalar resolver, final geometry and renderer. Prefer a **bounded form of alternative B**, an explicit vertical logical block schedule between binding and placement, subject to Owner approval and evidence that it simplifies the next checkpoints. Alternative A remains technically sufficient and is the lower-change fallback. Generalized data/template preprocessing into a widened or flattened representation, alternative C, offers insufficient benefit for this contract. The [concrete bounded-B proposal](bounded-logical-block-schedule-proposal.md) defines the smallest proposed model, its costs and a draft plan amendment.
2. Preprocessing is feasible and already substantially present. The current renderer consumes prepared placements, values, formulas and settings; it does not interpret data hierarchies. B would mainly simplify and expose the decisions currently made between binding and geometry. It would not remove the hard work of merge ownership, safe formula images, cropping or metadata preservation.
3. The strongest reason for B is an inspectable, shared account of which logical item owns each header/body/footer and field context before coordinates exist. Stable ancestors already exist in M3.2. Neither an additional representation nor wide records automatically prevents duplicated hierarchy interpretation: consumers must actually use the authoritative source tree and bound parent links.
4. **Current boundary:** M1/M2 and M3.1/M3.2 are accepted. The bounded F1/F2 corrections are complete and verified; static scopes and structural planning now share the parsed source tree, and the nested guard accurately names pending emission/placement. Nested generation remains guarded. M3.3/M3.4, full M3.14 integration and an architecture change are not authorized. Review R1 remains M3.5; R2 requires consideration during M3.4. Favoring investigation of B is not approval to implement it.
5. This document supplements [the existing architecture assessment](architecture-assessment.md), [the approved specification](feature-spec.md) and [the Developer-owned plan](implementation-plan.md). It does not amend them, replace milestone criteria, add backlog work or record approval. No implementation, tests, controlling Skills, existing reviews, Git index or publishing operations are changed.

## 5. Alternatives

### 5.1. A — Continue the approved architecture

1. Extend the current geometry traversal to visit compatible bound logical items through the parsed source tree. For each item, emit its authored header, ordered children/body and footer; carry the existing instance path and bound row identity. Use those spans for later rows, cell placements, merges and formulas. Keep `RowScope` and `HeaderScope` for values.
2. This can deliver the approved contract without a separate logical-plan type or additional service. It preserves M1/M2 ownership behavior and M3.1/M3.2 parsing/binding. F1 has already established consistent static source scope ownership; there is no architectural requirement for B.
3. Its cost is that the geometry traversal must also answer logical questions: which template level matches a data row, what group owns a footer, which descendants survive omissions, and when to reject a template/data mismatch. Those decisions remain unit-testable through emitted identities/spans, but are less independently visible than in B. Avoid adding another numeric hierarchy stack inside placement; use the already bound links.
4. The renderer changes only if the final output contract needs a routine extension. Its existing simplicity is a benefit of A, not a benefit reserved for B. M3.3/M3.4 would still require explicit authorization before implementation.

### 5.2. B — Add a bounded logical expansion plan

1. Keep the parsed trees and bound rows. Construct a compact per-sheet/per-region schedule describing vertical logical block instances: original source block, body/header/footer role and bound logical owner identity. Parentage remains in the bound rows; horizontal expansion initially remains in the existing geometry code. The separate proposal makes this vertical-only boundary concrete. The schedule has no final Excel coordinates, cloned cells, copied parent graph or renamed JSON properties.
2. Use references to existing rows, source intervals and parsed tokens. A field binding can identify root, ordinary first-record, leaf tuple or header element plus a parent depth; it need not contain a copied object or an eagerly formatted value. A footer keeps the same logical item context even when emitted after its children.
3. Geometry assigns coordinates from the schedule's extents and ordered groups, composes later displacement/crop, and retains the current source-to-instance maps. Existing merge and header ownership then decides which physical copies retain content. Prepare only surviving values and finalize formulas against the frozen geometry. This preserves the current rule that suppressed/removed copies do not resolve fields or introduce spurious errors.
4. The logical schedule owns template/data compatibility and repeat order; geometry owns physical coordinates, row/column properties and collisions. Static source scope ownership already exists before binding through the corrected F1 path. Do not replace it or make the analyzer depend on a data-specific schedule.
5. B is incrementally possible without discarding accepted work. First use the schedule for vertical block instances while reusing horizontal spans, final placement models, retained/displaced content identities, scalar evaluation, formula planning and renderer. Add horizontal grouping to the representation only when it removes a concrete duplicated decision. Do not allocate the Cartesian product of every logical row and horizontal group merely to declare their independent existence.
6. The cost is a new invariant and another traversal/representation to maintain. It is justified if it becomes the authoritative schedule used by placement and context selection. If geometry and `BindInstances` still independently rediscover those decisions, B adds indirection and memory without fixing the problem. No general document IR, plug-in framework, visitors, synthetic worksheet, new public API or extra injected service is required.

### 5.3. C — Generalized data/template preprocessing

1. Validate the current input contract first, then transform each logical row into a wide record whose synthetic fields identify horizontal tuple and original scalar path. Expand the horizontal template into a prepared source strip; subsequent vertical scheduling copies that strip. A single horizontal level makes this straightforward.
2. Multiple horizontal levels need both leaf tuples and intermediate owner groups. Flattening leaves alone loses parent heading identity, parent-only columns, repeated sibling block reuse and empty-parent structure. Keep a side structure describing every horizontal prefix/owner and the source provenance of expanded cells. Retain vertical logical parents separately so `../` never becomes a synthetic-field naming heuristic.
3. This can be made correct for any finite supported depth, but then C has recreated much of B plus a wide value table and an expanded template. Actually mutating an XLSX template early adds a second coordinate system: formulas, merges and metadata must be bound to original identities and transformed consistently through both preprocessing and later expansion/crop.
4. Flattening data also does not flatten nested vertical semantics. Footer placement still needs the source tree joined to the ordered data hierarchy. A completely expanded intermediate worksheet would merely move nearly all geometry/rendering work into preprocessing and duplicate output-sized structures.
5. A compact reference-only wide view would reduce copying, but once source/node/parent identities are retained and template mutation is avoided, that view approaches B. Synthetic field slots add little over the current ordered record arrays and tuple indices. C is therefore feasible, but is not a simpler replacement for this engine.

## 6. Concrete scenario comparison

### 6.1. One vertical level and one horizontal level

1. **Fixture:** two logical rows, three header elements, one authored leaf column and one ordinary-name column. Each logical row has three contiguous intersection records. After crop, each repeated row contains its ordinary first-record name followed by three tuple values; headings follow their three elements.
2. **A:** group and validate records, emit two vertical spans and three horizontal instances, combine their source identities into placements, bind first-record/tuple values and finalize formulas. The current two-axis implementation contains the necessary machinery.
3. **B:** schedule two logical body instances referencing the same bound records and reuse the existing three horizontal instances; placement assigns the same coordinates. Extra scheduling buys little for this case, and must not be justified by claiming A has a complex renderer.
4. **C:** create two wide records and copy the leaf template three times with synthetic names, then repeat vertically twice. This is C's best case. It still needs header bindings, formula provenance, valid arity, styles and one final crop, beyond merely renaming fields.

### 6.2. Three vertical levels with footer-first source ordering

1. **Fixture:** source rows carry levels `90,40,10`. The source tree is level 10 footer around level 40 footer around level 90 body. Input is ordered `10 P,40 C1,90 G1,90 G2,40 C2,90 G3`. With one physical row per block, output order is `G1,G2,C1,G3,C2,P`, six rows. The template has children before parents; the input still establishes each parent before its descendants.
2. **A:** walk bound children under P and each C, emit grandchildren then the appropriate footer using C/P contexts. Assign each block its next row. Do not infer a parent from preceding template rows, sort the data or attach earlier input children to a later parent.
3. **B:** schedule body G1, body G2, footer C1, body G3, footer C2, footer P with identities referencing the existing parent links. Placement is a prefix sum of block heights. The schedule is independently assertable before any output Excel coordinate exists.
4. **C:** wide records do not help because this case has no horizontal multiplication. A vertical scheduler must still produce exactly that order and preserve logical contexts before copying prepared rows. If C instead traverses input once and copies each matching source row immediately, it emits parent footers too early.
5. The grammar is already covered by [NestedTests:15](../../../MonoReport.Tests/Services/Feature012NestedTests.cs#L15) and [footer ownership:50](../../../MonoReport.Tests/Services/Feature012NestedTests.cs#L50), but full nested output is not currently implemented. A source-order change in the input itself is a separate hierarchy case, potentially R2; footer-first template support does not authorize backward parent inference.

### 6.3. Two horizontal levels with varying collection lengths

1. **Fixture:** outer Bids has two elements; the root Criteria collection has 0, 1 or 3 elements in different inputs. Parent D:E owns D; child E repeats. Width of the repeated strip is `2 × (1 + criteriaCount)`: 2, 4 or 8 physical columns, even if D has width zero. With three criteria, pre-crop parent headings span D:G and H:K. Matrix arity is six, or one descriptor when Criteria is empty.
2. **A:** recursive horizontal spans emit each parent's own column, followed by its child instances. Existing merge/header ownership retains each parent heading once. **B:** retain exactly that horizontal path; its vertical-only schedule introduces no separate horizontal model. Both assign those widths and use existing merge projection for the authored merge. Neither treats physical width as record arity.
3. **C:** flatten six leaf values, but separately preserve two parent instances and their own columns. Copying six undifferentiated tiles would duplicate parents and lose the two surviving parent-only columns in the empty-child case. Prefix ownership and source merges must therefore accompany the expanded strip.
4. Varying lengths **per parent within one report** are a different case: e.g. Alpha has one criterion and Beta has three. The current contract uses separate root collections and their complete Cartesian product; per-bid criteria lists are explicitly deferred in [feature-spec.md:121](feature-spec.md#L121). A/B/C do not authorize ragged data. The actionable current alternative is a common root Criteria list with explicit placeholders for missing values, or a separately approved data-model extension. Such an extension would need child-collection resolution and new tuple offsets/arity rules; wide fields alone do not solve it.

### 6.4. Two horizontal levels combined with two vertical levels

1. **Fixture:** two bids × two criteria gives four records per logical row. Data contains parent P with children C1/C2 and parent Q with child C3. An authored parent header/footer surrounds a two-row child block. Logical output has five data items, 20 matrix records and ten physical rows: P header, four child rows, P footer, Q header, two child rows, Q footer. The repeated horizontal strip has six columns when each bid has one own column and two child columns.
2. **A:** join the parsed two-level vertical tree to bound parent/child identities, emit the ten row positions and share the worksheet's horizontal instances. Both rows of each child reuse the same four-record tuple set. **B:** express those ten physical-row contributions as seven block instances, each retaining its logical row and parent; layout combines their row extents with the independent horizontal groups.
3. **C:** create five wide records, each retaining four tuple values per selected field, and a six-column prepared strip. Vertical grouping still needs the two-level scheduler. Cloning an entire record per physical child row is unnecessary; expanding both axes into a second full intermediate sheet is output-sized duplication.
4. This is approved behavior, not current public nested support: [spec A9](feature-spec.md#L202), [M3.14](implementation-plan.md#L206). Accepted evidence for the simpler multirow case already checks that two physical rows reuse one tuple set in [TwoAxisTests:154](../../../MonoReport.Tests/Services/Feature012TwoAxisTests.cs#L154).

### 6.5. Parent and grandparent fields

1. **Fixture:** P at level 10 has Name `P-first`; C at 40 has `C-first`; G at 90 has different values in its first and second tuples. In G's second tuple, `{Name}/{../Name}/{../../Name}` uses G's second record, C's first record and P's first record. Missing/null in those first ancestor records must not fall back to another tuple or the root.
2. **A:** M3.2 already supplies this with `RowScope` over bound parent links, independent of footer position. Physical placement retains the selected logical item and tuple. **B:** retain those same identities as scope selections on logical blocks/field bindings; do not copy ancestors into every cell. Coordinates can then change without changing lookup.
3. **C:** a synthetic tuple-specific Name slot says nothing about which logical parent owns it. Retain stable vertical context references or eagerly resolve parent values with complete missing/null/path provenance. Copying parent/grandparent values into every wide row introduces repeated data and does not solve ancestor validation.
4. [HierarchyTests:15](../../../MonoReport.Tests/Services/Feature012BindingTests.Hierarchy.cs#L15) checks actual scalar preparation and source paths; [HierarchyTests:222](../../../MonoReport.Tests/Services/Feature012BindingTests.Hierarchy.cs#L222) distinguishes missing/null without fallback. Horizontal header `../` instead walks prior header elements; neither axis implicitly injects the other into its parent chain.

### 6.6. R2: incompatible template and data hierarchies

1. **Fixture:** template source order `10,40,20` parses as level 10 header → level 20 footer → level 40 body. Data order `10 P,40 X,20 Y` binds X and Y as siblings under P. The template needs X inside a level-20 group; input does not establish one. By contrast `10 P,20 Y,40 X` supplies the compatible hierarchy and can correctly render `P,X,Y` under this footer layout.
2. **A:** compare template owner ancestry with bound row ancestry while selecting blocks, before producing unsafe placements. **B:** make this a schedule-construction check: no level-40 block can be scheduled under Y when X's bound parent is P. **C:** keep and check those original parent identities before flattening; wide records that discard them cannot diagnose the mismatch reliably.
3. **Recommendation for M3.4 consideration:** reject this concrete incompatible case before rendering, identifying source block/control and indexed data group, expected level-20 ownership and actual level-10 parent. Offer either re-authoring template blocks to match the intended numeric hierarchy or having the producer supply correctly nested input in its intended order. Do not silently sort, reparent, infer ancestry from path text or drop X. This is a proposed bounded integrity check, not a new comprehensive hierarchy validator or an already approved recovery policy.
4. A scheduler or IR reveals the disagreement; it does not decide which structure should win. That product decision remains with the Owner. Keep R1 missing-level omission/recovery distinct: do not reject every absent level under an R2 check and thereby preempt M3.5's approved descendant-preservation behavior.

### 6.7. Empty collections and uneven siblings

1. **Fixture:** P has no vertical children; Q has three; two horizontal parents share an empty child collection. With a parent header/footer, output retains each real parent instance, emits no child body for P and three child blocks for Q. The horizontal product is empty, so each logical vertical item uses one descriptor; both parent-only heading columns survive. An empty outer horizontal collection removes its descendants and headings. An empty vertical collection emits no vertical repetitions.
2. **A:** existing cardinality normalization and recursive source geometry provide the inputs; later vertical traversal must retain parents independently of child counts. **B:** absent children are an empty ordered child set, not missing contexts or fabricated rows; parent instances still schedule their own blocks. Geometry removes zero-width child groups while keeping surviving physical own columns.
3. **C:** a widened representation must derive its shape from explicit header cardinalities, descriptors, zero-child parent ownership and the vertical group tree. Inferring one rectangular shape from the first sibling would lose valid differences. Empty leaf fields cannot carry a surviving parent heading unless its separate owner survives. Do not add fictitious intersections or duplicate the first sibling's shape across others.
4. Unequal counts of **vertical sibling subtrees** are valid. Repeated horizontal template sibling blocks at the same level reuse that level's collection and tuple positions, even if their authored widths differ; they do not multiply data arity. Unequal record counts for logical rows sharing the same positive horizontal product are invalid, as are deferred per-parent horizontal child lists. All alternatives preserve these distinctions.
5. Existing [geometry cases](../../../MonoReport.Tests/Services/Feature012GeometryTests.cs#L65), [sibling tuple reuse](../../../MonoReport.Tests/Services/Feature012TwoAxisTests.cs#L61) and [empty-reference case](../../../MonoReport.Tests/Services/Feature012TwoAxisTests.cs#L45) provide useful regression anchors. A removed formula vanishes with its cell; a surviving formula with an unsafe empty image still fails. No alternative gets to substitute zero automatically.

## 7. Complexity, memory and arbitrary depth

1. Let N be logical vertical items, R input records, L the product of distinct horizontal collection counts, D maximum nesting depth, F selected cross fields, S source blocks/cells, I emitted logical block/group instances and C final authored populated/styled cell placements. For an intersecting region, R is N × L when L is positive, otherwise N descriptors. Independent regions outside the horizontal strip retain arity one. These variables describe the contract, not measured performance.
2. Grouping and stack-based data hierarchy binding can be O(R + N), with O(R) JsonElement handles/indexing and O(N + D) hierarchy bookkeeping. The current bound arrays hold JsonElement handles rather than deep-cloned JSON. Shared Parent links avoid storing an ancestor array on every logical row. Creating a scope on demand still walks up to D ancestors; current `BindInstances` constructs paths/scopes per placement. Do not describe all current processing as depth-independent.
3. A and compact B need source trees, bound records and emitted group/span identities, plus the existing O(C) prepared placement/value structures. B adds approximately O(I) schedule entries if source blocks and logical owner identities are shared. Full vertical instance paths may also require O(sum of scheduled item depths), shared between each item's header/body/footer; do not hide that cost behind an O(I) claim. It can avoid a separate per-cell logical structure by keeping ownership at block level. A fully materialized B entry per cell, each copying D ancestors, would instead add O(C × D) metadata and defeat its purpose.
4. A widened scalar table adds approximately N × (ordinaryFieldCount + F × L) value slots, plus F × L synthetic field definitions for a positive product, while source data may remain alive. Strings/objects need not be deep-copied, but slots, row/schema objects and some boxed values still cost memory. A prepared horizontal template adds another widened source representation; a fully expanded worksheet adds O(C) XML/data beside the eventual output.
5. **Wide records do not inherently create an extra exponential blow-up relative to already dense input.** If every level has k elements, L = k to the number of horizontal levels; this product is already required by the approved input/output model for all alternatives. The avoidable costs are copying selected fields, duplicating parent headings/contexts per leaf, dense unused slots and retaining multiple expanded representations. No representation can remove the cost of actually required intersections without changing the contract.
6. Recursive horizontal groups contain prefix instances as well as leaves. For a chain of h levels, the number of header instances follows the sum of prefix products; flattening h labels into every leaf can require h × L bindings and loses sharing. Own columns add widths at intermediate levels: width(node) = itemCount(node) × (ownColumnCount + sum of expanded child widths). With one own column at each of three levels and counts 2,3,4, width is 32, not 24 leaves. [The earlier assessment](architecture-assessment.md#L43) proves this recurrence only as model research; rendered deeper-horizontal acceptance remains M4.
7. Arbitrary model depth is practical in A/B and structurally possible in C, without a hardcoded one/two-level cap. It does not mean unlimited resources. Current vertical parsing/binding use iteration, while horizontal collection/width/emission and some identity processing are recursive. Deep source trees, ancestor traversal and record equality/hashing can add costs. Use explicit traversal stacks or shared identities where actual supported-depth evidence requires them; do not promise unbounded call-stack safety or introduce a depth limit without a product need.
8. Actual current allocation/runtime is not proven linear in R + C: [EmitCells:35](../../../MonoReport/Services/Xlsx/XlsxGeometryPlanner.Cells.cs#L35) scans source rows for each row span and source cells for column spans; owner/reference processing has additional scans. Runtime and peak-memory comparisons need the planned bounded M6 measurements, not inferred speedups from type counts.

## 8. Comparative judgment

| Criterion | A — existing architecture | B — compact logical schedule | C — wide data and rewritten template |
| --- | --- | --- | --- |
| Correctness, determinism and ownership | Sufficient with tree-derived scopes, explicit template/data matching and reuse of bound parents. More logical decisions remain inside placement. | Makes block ownership/order/context directly inspectable before coordinates. Correct only if consumers share it rather than rederive it. | Correctness possible, but flattening requires side metadata to preserve parent/tuple/source ownership and empty cases. Early mutation adds provenance risks. |
| Implementation complexity | Lowest additional structural cost; extend accepted traversal/models. Nested scheduling remains substantial work. | Moderate bounded model/traversal cost; can reuse accepted components. A generic IR would be unnecessary overhead. | Highest migration cost: schema/name generation, widened templates, provenance and all nested scheduling/geometry still required. |
| Maintainability | Fewer representations, but placement and scope selection can drift if their logical decisions remain duplicated. | Explicit contracts make future nested changes easier to localize; requires clear single ownership of decisions. | Synthetic naming and multiple source/expanded coordinate systems add maintenance. Keeping full structure erodes the simplicity claim. |
| Testability and separation | Test source trees, bindings and final span/owner maps. Existing renderer is already narrow. | Adds coordinate-independent block-order/context assertions; geometry tests then focus on physical projection. | Can test normalization separately, but must also prove equivalence/provenance through template mutation and final rendering. |
| Performance and memory | Reuses compact handles/intervals plus output placements. Existing scan costs remain. | Adds O(I) block entries and shared owner paths; no measured speedup. Can become wasteful if eagerly expanded per cell or if path copying is ignored. | Extra wide slots/schema and expanded template coexist with source/output. Dense-input asymptotics can match A/B, but avoidable constants/copies rise. |
| Preservation of accepted work | Direct continuation. | Preserves trees, bindings, neutral resolver, identity maps, merge/formula safety and renderer; introduce incrementally. | Can reuse final backend, but broad data/template preprocessing replaces more accepted intermediate behavior and needs extensive equivalence verification. |

1. A is not architecturally wrong, and F1 is corrected without B. The approved separation already keeps the renderer simple. Its main remaining design risk is implementing nested logical scheduling and runtime ownership selection inconsistently between geometry and binding; the corrected static scope path must simply be reused.
2. B is recommended narrowly because the next substantial work is exactly that nested schedule, and it is useful to inspect before coordinates exist. A compact vertical block schedule can clarify M3.3/M3.4 without discarding M3.1/M3.2 or redesigning the output backend. If its concrete Developer plan duplicates existing spans/decisions rather than removing a duplicated responsibility, choose A instead.
3. C can be convenient for a constrained single-horizontal-level product because tuple fields map directly to a prepared strip. For Feature 012, the required parent-only columns, arbitrary depth, footer layouts, descriptors and reference integrity force it to retain substantial structural metadata. It mainly relocates complexity and adds storage; no current implementation evidence supports replacing the accepted architecture with it.
