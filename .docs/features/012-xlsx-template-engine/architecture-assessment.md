# Feature 012 — Architecture assessment

1. **Updated:** 2026-10-20. The Product Owner's nested horizontal model, bounded merge adjustment, blank-control-row table boundaries, physical PrintArea cropping, empty-axis descriptors, native types, Core + CLI + HTTP scope, and extension of existing interfaces supersede the initial recommendations. The [Feature Spec](feature-spec.md) records those decisions. No production implementation or Implementation Plan is approved by this research.
2. **Recommendation:** retain the existing Open XML SDK; eliminate ClosedXML.Parser and full ClosedXML from the proposed runtime dependency graph. Use a bounded internal reference-token parser/transformer, recursive instance geometry and one final workbook plan. Keep ClosedXML.Parser only as an optional isolated research comparator. This is a capability-bounded recommendation, not a claim to parse all Excel formulas.
3. **Planning readiness:** ready to prepare the Developer-owned Implementation Plan against the revised specification. The important product questions raised in the first assessment are resolved. The plan must make existing-interface compatibility, HTTP structured success-warning transport, constructor/DI composition and focused remaining verification concrete before implementation.
4. **Work boundary:** only Feature 012 documentation and isolated research sources/evidence changed. No production code/dependency, controlling Skill, Git index, commit or publishing operation changed. Research was executed under `/private/tmp/feature012-followup/`; previous evidence under `/private/tmp/feature012-research/` is retained as historical evidence, not the current authoring model.

## 3. Recursive geometry and merge ownership

1. Represent a horizontal node by source interval, associated level/collection, own source columns, ordered child nodes and instance path. For each collection item, emit the authored sequence: own columns occur once; each child is expanded recursively in its original position. A node width is its collection count multiplied by the sum of its own physical columns and its expanded children. Width-zero columns count as physical columns; an empty collection contributes no instances.
2. Retain vertical region identity, logical-row/ancestor instance paths, horizontal node/tuple paths and source cell identity. A source cell may produce zero, one or many output cells. Parent-only data fields use the ordinary first-record scope; header fields use the associated header collection. Leaf fields select the matching positional record. Parent-only columns do not add matrix records.
3. Parent header rows render their expressions once per parent, independently of the number of child copies. Child header rows render per child. Collections are associated by header markers, while separate top rows carry the geometry levels; E can therefore be marked at both levels without two tokens occupying one cell.
4. Merge ownership is explicit. A parent-owned merge that fully encloses a child projects its authored boundaries through that child's final interval. Apply the same operation to each physical parent instance. This adjusts an existing range, not a synthesized presentation choice. Preserve the original anchor value and authored cell/style properties.
5. A projected merge with one surviving cell is emitted as that ordinary cell; an empty owner emits neither merge nor content. Reject partial-child/cross-owner overlaps whose output image is disjoint, crosses another parent or loses nonanchor data. Do not join neighboring copies, reconstruct arbitrary merge patterns or infer new headings.
6. Table ownership comes only from the PrintArea, horizontal controls and consecutive vertical marker runs. Header/deeper-body/footer grammar must be unambiguous within a run; use an unmarked control row to separate independent runs. Printed separator/static rows stay outside repeated ownership. Side-by-side independently growing row bands with incompatible shared row heights are rejected rather than repaired.
7. The one outer horizontal tree is worksheet-wide through the printed row bands. Multiple vertical regions may share it or occupy static columns beside it. Worksheet column widths are global; move content to the right consistently and reject incompatible shared-axis assumptions. A second unrelated horizontal root is outside initial scope.
8. Compose placement with final PrintArea cropping before formula/merge rendering. Initially require a finite rectangular PrintArea on each retained sheet; reject missing/disjoint areas rather than invent boundaries. Drop disposable external content; reject retained references to it when no correct surviving referent exists. Preserve supported print/view/drawing/metadata coordinates or reject affected unsupported structures.

## 4. Empty input normalization

1. Let L be the product of the distinct horizontal collection cardinalities. With L greater than zero, a contiguous `$path` group has exactly L ordered records. With L equal to zero, it has exactly one descriptor. Build vertical hierarchy from integer `$level`, preserving order; never sort paths or parse slashes as ancestry.
2. In descriptor mode, ordinary row and parent-only data fields use the descriptor. Nonempty outer collections still render parent-only columns and header values; empty children render no columns. With no outer instances, no descendant or orphan criterion columns are emitted. A template with no horizontal markers uses ordinary vertical-only record semantics and may omit `$path`.
3. Empty geometry does not authorize discarding ordinary rows. It also does not authorize replacing arbitrary formulas with zero. A removed leaf formula disappears; a surviving reference with an empty image fails with source cell, reference and remedy. A safe authoring alternative is to keep that total inside the disappearing block or over an explicitly retained range.
4. Validate group cardinality, path contiguity/non-reappearance and consistent integer levels. Full positional records can be permuted without detection because they contain no independent horizontal IDs; document producer responsibility rather than claim semantic order validation.

## 5. SDK versus formula parser: exact division of responsibility

| Capability | Existing Open XML SDK | Additional internal work / value of ClosedXML.Parser |
| --- | --- | --- |
| Package parts, relationships, worksheet cells, styles, merge elements, print settings | Available through package/typed XML APIs | Need feature-specific geometry and affected-feature handling, whichever parser is selected |
| Formula text, attributes, cached values and shared-master/follower metadata | CellFormula/CellValue expose storage; calcPr exposes recalculation flags | SDK does not tokenize operands, interpret references, bind scopes, expand shared formulas or adjust references after XML edits |
| A1 reference identification, quoted strings/sheet names, dollar flags and range endpoints | Not a reference transformation service | Internal scanner or external parser required; regex replacement is insufficient |
| Function names/operators, arbitrary ordinary function calls | Stored as text | Bounded token parsing can preserve them without evaluation; ClosedXML.Parser supplies a much broader Excel grammar |
| Names, cross-sheet and reference dependencies | Parts/defined-name expressions are accessible | Application must resolve sheet/name scope and map identities; an external parser does not select the right report group/instance |
| Relative copy and structural relocation | No automatic semantic rewrite | Must apply separate copy/geometry rules. Shared follower normalization reuses copy semantics but needs package-aware validation |
| Formula evaluation | No engine supplied | Explicitly out of scope; neither approach is selected to evaluate formulas |

1. Microsoft documents formulas as text in `<f>` with optional cached `<v>` results, not an executable reference service. See [CellFormula](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.spreadsheet.cellformula) and [formula storage/cache behavior](https://learn.microsoft.com/en-us/office/open-xml/spreadsheet/working-with-formulas). Typed element access and schema validation cannot supply the missing scope/geometry semantics.
2. The internal research scanner is about 150 lines, plus its runner/checks; this is a feasibility size, not an estimate of production-complete code. It reads strings with doubled quotes, escaped quoted/unquoted sheet prefixes, bounded A1 cells/rectangles and flags, numbers/exponents, ordinary function identifiers, declared names and operator tokens. It edits only reference spans in reverse source order. It performs no arithmetic, function execution, type inference or general Excel grammar validation.
3. It explicitly prevents `LOG10` from becoming a cell reference, `1E10` from exposing an E10 reference, and `"D8"` from changing with the actual D8 operand. It rejects unclosed quotes/parentheses, unrecognized tokens and unresolved names. Valid formula input remains the template author's responsibility; lexical coverage is not proof that every syntactically possible Excel formula is valid or supported.
4. Initial reference support is bounded A1 cells/rectangles, copy flags, same-workbook sheet qualification, and safely resolved simple names. Preserve arbitrary ordinary function names over safe explicit operands, including future-prefixed functions. Detect constructed references, special formula groups and unsupported operand forms and fail with actionable diagnostics.

### 5.2 Reference safety and calculation

1. Bind references to source identity and owner scope before computing final coordinates. A group subtotal uses its own descendants; an intersection formula uses its tuple; a static total refers to the intended global region. `$` prevents copy displacement, not structural relocation. Ambiguous absolute references into repeated cells fail rather than pick the first result.
2. Classify mapped references as a unique cell, contiguous rectangle, disjoint set or empty. Never turn a scalar into a range or take a bounding rectangle that includes another group's totals. Reject disjoint/empty images initially; avoid function-specific union synthesis or replacing the author's chosen aggregate with another one.
3. Parsed syntax alone cannot safely transform `INDIRECT` strings or geometry-sensitive `OFFSET`. A broad parser also cannot infer the author's intent for them. Formula-valued/recursive names, structured/external/3-D/whole-axis operands, spills and array/data-table groups remain unsupported when affected unless specifically verified. Existing explicit union operands may be preserved only when each operand maps safely; no new union is synthesized.
4. Normalize shared scalar formula followers from their masters with copy semantics, then apply relocation/crop. This common-input handling needs a real XLSX fixture during implementation; neither the old nor new package spike proves it. Traverse all sheets and dependent names/metadata before mutating any sheet.
5. Preserve authored function names and semantics. `SUBTOTAL` ignores nested subtotals while `SUM` does not; manually hidden rows and hidden columns also differ. Do not rewrite business results to look plausible. See [Microsoft's SUBTOTAL semantics](https://support.microsoft.com/en-us/excel/functions/subtotal-function).
6. Remove stale formula caches and obsolete calculation-chain state when appropriate; request automatic full recalculation. Do not evaluate formulas in MonoReport. Helper rows/columns are an alternative only for a concrete approved case, not the default and not content secretly retained outside PrintArea.

7. **F-M312-1 — Owner-approved option 3, 2026-10-23:** preserve lexical endpoint order, source spans, sheet/name identities and each endpoint's row/column absolute flags for finite A1 formula ranges. Either axis may descend independently. Shared followers copy directly from the master in source coordinates and are reparsed. At the formula-to-geometry boundary normalize row and column bounds independently; geometry retains increasing rectangles. Restore each axis's original orientation during relocation and attach the original endpoint flags. Equal endpoints retain range syntax; equal source axes use the existing increasing orientation if expansion separates their output bounds. Increasing operands retain existing output. See the [architecture investigation](reviews/f-m312-1-architecture.md), whose proposal is approved by this decision; its historical investigation and manual-verification limitations remain evidence, not completed implementation checks. This is a bounded M3.12 correction: no grammar expansion beyond endpoint orientation, general parser/evaluator/reference framework, shared output, public nested activation or F-001 semantics change. PrintArea, shared membership, geometry and all existing projection safety constraints remain unchanged.

## 6. Native values and shared MonoReport infrastructure

1. Existing [TemplateLanguageParser](../../../MonoReport/Services/TemplateLanguageParser.cs) already provides strict scalar paths, braces/escapes and single built-in formatter semantics. Reuse them for cell strings; keep XLSX geometry markers separate. Never tokenize formula array-constant braces as template fields or reparse inserted data.
2. [DataResolver](../../../MonoReport/Services/DataResolver.cs) implements the needed missing/null/present and current/root/parent lookup rules but accepts a MergeContext containing Word state. Extract only a small neutral scope input/overload; preserve DOCX behavior. [ValueFormatter](../../../MonoReport/Services/ValueFormatter.cs) returns text; do not pass raw native numbers through it by default.
3. A complete unformatted field preserves a number/Boolean/string type. Interpolation or explicit number/date/casing/spellout formatting returns text. Preserve authored number formats and reject unsafe numeric precision/type conversions. Numeric-looking strings stay strings; data strings beginning with `=` stay text.
4. Excel native dates can be numeric serials with number formats; the workbook system controls the serial interpretation. The observed 1,462-day difference agrees with [Microsoft's date-system documentation](https://support.microsoft.com/en-us/excel/date-systems-in-excel). Preserve existing dates, the workbook flag and date-styled numeric bindings. Keep ISO strings textual and explicit MonoReport date formatters textual; automatic typed-date inference is deferred rather than guessed from display style.
5. The fictitious 1900 leap-day serial, fractional times, timezone conversion and negative/out-of-range date policies are not established by the modern-date probe. Preserving authored native serials does not require converting them into .NET dates. Add focused edge fixtures if conversion is proposed; no new date syntax or implicit conversion is approved here.
6. Reuse Feature 010's parse-once/source-to-copy and operation-isolation principles, Feature 011's safe preservation/actionable rejection boundary and Feature 008's deterministic bounded errors/no-partial-output policy. Their DOCX structural plans and identities are not spreadsheet plans.

## 8. Fidelity and rejection envelope

1. Support ordinary cell content/types, authored styles, widths/heights/hidden states, valid owned merges, printing and supported formula/reference forms. Keep parent-owned structural range adjustment distinct from inventing visual layout. Rich-text spans and shared strings need explicit cell adapters/fixtures; never cross cell boundaries during tokenization.
2. Preserve retained safe names, tables, charts, drawings, CF, validation and comments only when their coordinates and dependencies remain correct through expansion and crop. Drop disposable external artifacts; reject straddling/affected structures without bounded verified handlers. Do not strip required inside-report parts to force a successful package.
3. Static source-part preservation was demonstrated previously, but final cropping often makes formerly static anchors affected. The full operation footprint includes later-table displacement, workbook references and removed margins. Being outside a repeat body or passing schema validation does not establish safety.
4. Keep rejection diagnostic/actionable, for example identify an incomplete matrix path, the merge crossing child ownership, a reference to discarded content or an unsupported table whose range is moved. Avoid a speculative taxonomy or exhaustive OOXML framework. Unsupported cases are documented limits, not silent data loss.

## 9. Revised implementation sequence and gates

1. **Planning:** prepare the Implementation Plan from the revised spec/roadmap and approved decisions; select no new runtime parser dependency, concretize existing-interface/constructor compatibility and HTTP success warnings, and define proportionate verification. No production work begins under this research authorization.
2. **Foundation:** package format dispatch through existing façades, PrintArea/control inventory, neutral scalar scope adaptation, native value handling, diagnostics and recursive two-axis source/instance/range types. Establish negative unsupported-feature and resource checks immediately.
3. **Early working two-axis slice:** mandatory nested parent/child geometry, zero-width own column, one company heading, bounded merge projection/collapse, one vertical block, a formula above/details/below, both empty modes and marker-run boundaries. Use the internal transformer and physical cropping, not a vertical-only engine awaiting replacement.
4. **Nested groups and multiple tables:** arbitrary numeric levels, multirow children, headers/footers, same-name independent runs, zero-height separator, shared horizontal columns, scoped group/grand/cross-sheet formulas. Normalize shared formulas and verify known disjoint/empty/absolute failures before claiming formula support.
5. **Full hierarchy and interfaces:** deepen the same recursive tree, complete the reference/metadata envelope and native date preservation; wire CLI and existing HTTP generate/analyze routes, MIME/format metadata, structured warnings and DOCX regression coverage. No separate XLSX API family.
6. **Final compatibility/capacity:** test representative approved workbooks, only the agreed affected-feature handlers, realistic dimensions/formula counts and distribution closure. Run focused automated structural/formula/transport tests plus manual Excel visual/calculation/repair verification. Automated Excel is not required.
7. The highest-risk work remains identity/scope reference binding, merge ownership, crop-linked metadata and backward-compatible public transport/composition. Removing a parser package does not remove those risks. Internal lexical boundaries add owned maintenance, but the demonstrated bounded subset does not justify a general Excel grammar dependency yet.
8. The earlier Core-only 6–10 engineer-week estimate is superseded: scope and geometry changed and now include public adapters/backward compatibility. Do not reuse it as a commitment. Estimate the concrete Developer plan after transport and compatibility work are specified; no production performance or calendar commitment is asserted here.
