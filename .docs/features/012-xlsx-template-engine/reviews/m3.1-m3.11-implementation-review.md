## Findings (ordered Critical/High/Medium/Low)

### Critical/High

#### F-001: Partially overlapping owner ranges are silently truncated (wrong formula) instead of rejected
- **Severity:** High (correctness / data integrity). Violates spec §6.7 and `docs/xlsx-template-compatibility.md` line 9 ("empty, discarded, disjoint or ambiguous images reject").
- **Files/lines (evidence):**
  - `MonoReport/Services/Xlsx/XlsxGeometryPlanner.Owners.cs:78-134` — `ProjectReference`: when `affected` content owners exist, it carves out each affected owner address from `remaining` pieces (lines ~95-104), projects remaining pieces via `AxisImage` over all spans matching compatible owner (108-114), adds images only for *compatible* owners (114-116), computes bounding box/contiguity over images only (119-133). Incompatible owners (different vertical/horizontal owner paths/roles) are cut out but produce no images and are not treated as "disjoint/discarded" gaps.
  - `MonoReport/Services/Xlsx/XlsxGeometryPlanner.Merges.cs:9-44` — `ProjectInstances`/`AxisImage` behavior as used.
  - `MonoReport/Services/Xlsx/XlsxFormulaPlanner.cs:117-157` — relocation uses `ProjectReference` result; rejection only when `!image.Complete || image.Kind is Empty/Disjoint/Ambiguous || (!range && image.Kind!=Cell)` (150-152). Silent truncation yields a valid non-empty rectangle in practice.
- **Reproduction (real pipeline):**
  - Template: row 2 parent header `H:{Name}`, row 3 child body with `C3 = SUM(B2:B3)`.  
  - Observed output formula: `SUM(A2:A2)` (header operand silently dropped).  
  - Also confirmed via direct `XlsxGeometryPlanner.ProjectReference` probe (`A1:B2` targeting header-owned B2 → `A1:B1`, `Complete=True`); two-leaf range → `Disjoint`. Root cause matches the cutout+contiguity check above.
- **Impact:** Formulas can compute over wrong ranges with no diagnostic; silent corruption of calculated results. Affects any formula in one owner referencing a range that partially overlaps a different owner/role (header/body/leaf boundaries, merge anchors, nested owner boundaries).
- **Remedy (must fix):**
  1. When projecting a reference range that intersects any content owner address, if *any* part of the original range is removed/cut out because it belongs to an *incompatible* owner (and cannot be satisfied by compatible owners/descendant rules), treat as `Disjoint`/rejected (do not silently drop). 
  2. Track "covered" area of original range explicitly (union of images from compatible owners + images from projected remaining pieces that correspond to original cells) and reject if coverage < original range or if removed cells exist without compensation. 
  3. Add a regression test covering body/leaf formula partially overlapping header-owned cells (and merge-anchor case). Ensure error uses `UnsafeImage` with message per compatibility policy.
- **Milestone:** Belongs to M3.1–M3.3/M3.7 geometry+formula relocation (core correctness). Not M3.12+.

### Medium

#### F-002: Whitespace-only "normal" formula passes `Read` length check
- **Severity:** Medium (acceptance/robustness)
- **File/line:** `MonoReport/Services/Xlsx/XlsxFormulaReferences.cs:127` — `if (text.Length == 0) throw Unsafe(... "Supply a nonempty scalar formula...");` only rejects empty string; whitespace-only strings (e.g. spaces/tabs) pass `Read` and may propagate.
- **Impact:** Could allow whitespace-only formulas to slip through; error messages/behavior may be unclear.
- **Remedy:** Treat whitespace-only as empty (e.g. `string.IsNullOrWhiteSpace(text)`) before/at the check.

#### F-003: Defined-name `<definedName>` child elements not rejected
- **Severity:** Medium (contract strictness vs. documented restrictions)
- **Files/lines:** `MonoReport/Services/Xlsx/XlsxFormulaReferences.Names.cs:46-49` — only checks attribute namespaces/allowed names and `hidden` values; does not reject child elements. `MonoReport/Services/Xlsx/XlsxFormulaPlanner.cs:59` assigns `names[name.Index].Value = ...` (overwrites Value). 
- **Impact:** If a defined name has child elements (unsupported metadata/function constructs), they could be dropped or behavior unexpected; better to fail fast per "Remove unsupported function/macro metadata..." guidance.
- **Remedy:** Explicitly reject if `xml.Elements().Any()` (or non-whitespace child content) beyond allowed structure, consistent with other strict validations.

#### F-004: Duplicate `CellInstanceId` would surface as generic exception, not diagnostic
- **Severity:** Medium (error quality)
- **Files/lines:** `MonoReport/Services/Xlsx/XlsxTemplatePlanner.Instances.cs:63` does `prepared.Add(cell.Id, ...)` (no check); `MonoReport/Services/Xlsx/XlsxFormulaPlanner.cs:75` does `formulas.Add(cell.Id, ...)`. Dictionary `Add` throws `ArgumentException` on duplicate keys.
- **Impact:** Duplicate instance identity would produce a non-diagnostic exception rather than a structured `TemplateException` with location/context.
- **Remedy:** Detect duplicates and report via `context.Report`/throw `Unsafe`/structured diagnostic with location.

#### F-005: `GroupBlocks` only collects Header/Footer (asymmetric scope) — undocumented
- **Severity:** Medium (maintainability/docs clarity)
- **Files/lines:** `MonoReport/Services/Xlsx/XlsxFormulaPlanner.cs:97-108` — only pushes `node.Header` and `node.Footer` into blocks; body/leaf use exact-owner rules. This asymmetry is intentional per M3.7 (group ranges cover descendants later) but not documented in code/comments.
- **Impact:** Easy to misread as a bug; future changes could confuse scope.
- **Remedy:** Add a short comment explaining M3.7 deferral and why body/leaf use exact-owner/absolute-anchor rules.

## Coverage gaps (meaningful missing behavior/tests)
- **Cross-role partial overlap:** No existing test covers body/leaf formula referencing a range that partially overlaps a different owner (header vs body). This is the gap that allowed F-001 to go undetected. Add targeted test in `Feature012FormulaTests.Groups.cs` or a new formula test.
- **Whitespace-only formulas:** No explicit test for whitespace-only formula strings.
- **Defined-name with child elements:** No test for `<definedName>` containing child elements.
- **Duplicate instance IDs:** Hard to trigger naturally; consider adding a guard test or just ensure diagnostic path exists.

## Architecture assessment
- **Separation of concerns:** Good — formula scanning (`XlsxFormulaReferences`), geometry/projection (`XlsxGeometryPlanner`), planning/binding (`XlsxTemplatePlanner`), relocation/finalization (`XlsxFormulaPlanner`) are reasonably isolated.
- **M3.11 implementation:** Correctly does worksheet-local shared-formula inventory before crop, retains groups in plan, allows followers-before-master, enforces strict metadata/range/membership/overlap rules, and guards downstream (preflight + `RequireScalarFormulas` in `Finalize`). Matches plan and tests.
- **Owner model:** Header owners, displaced sources, merge anchors are handled carefully. The projection logic is complex but mostly sound; the cutout-in-`ProjectReference` needs the coverage fix (F-001).
- **Extensibility:** DOCX/XLSX separation is respected; no premature abstractions.
