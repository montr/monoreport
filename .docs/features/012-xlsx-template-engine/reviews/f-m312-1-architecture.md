## 2. Why the restriction exists: evidence and inference

1. **Documented contract:** Spec §6.3/§6.9 supports relative, absolute and mixed finite A1 cells/rectangles; §6.11 requires shared-follower normalization. Plan §4.4.2 requires master-to-follower copying with dollar flags before relocation. Neither these documents nor the relevant architecture decisions state that formula endpoints must increase. The compatibility policy likewise does not publish this restriction. Its current shared-formula rejection describes the public milestone guard, not a permanent endpoint limitation.
2. **History:** repository history for `XlsxFormulaReferences.cs` identifies commit `868dd6adfb212e10089c992b862257e3f2aaf96d`, dated 2026-10-22, as the introduction of the parser's ordering check. `git blame` attributes current lines 101–102 to that commit. Its message is only “feature 012 - M2 WiP”; it supplies no rationale. No earlier documented product decision for the restriction was found in the relevant Feature artifacts.
3. **Research antecedent:** [InternalReferences.cs](../research-spikes/InternalReferences.cs) reads both range endpoints without this ordering rejection. Research demonstrated a bounded scanner and supplied geometry, not generic safe relocation or Excel behavior for crossed shared followers. The restriction therefore cannot be described as a documented requirement inherited from that scanner.
4. **Current mechanical reason, verified by code:** [Read, References.cs:96–106](../../../../MonoReport/Services/Xlsx/XlsxFormulaReferences.cs#L96) guarantees that `First` is upper-left and `Last` is lower-right. [Relocate, FormulaPlanner.cs:138](../../../../MonoReport/Services/Xlsx/XlsxFormulaPlanner.cs#L138) constructs `XlsxRectangle` directly from those endpoints. `XlsxRectangle` does not normalize or validate its constructor; its `Contains`, `Height` and `Width` assume increasing coordinates. Projection algorithms and output formatting rely on this invariant.
5. **Likely rationale, inference only:** rejecting descending syntax was a convenient way to protect those geometric assumptions while implementing the bounded M2 subset. Safe rejection fits the project's general integrity policy. There is no evidence that the original author investigated Excel descending-range semantics or deliberately selected a product limitation. Do not substitute this plausible implementation explanation for an original documented rationale.
6. **Existing inconsistency:** [Copy_Honors_each_dollar_flag_without_rewriting_literals](../../../../MonoReport.Tests/Services/Feature012FormulaTests.cs#L102) already expects `SUM(H12:$E$10)` after a positive two-axis copy. `Copy` deliberately preserves endpoint identity and can produce descending text; `Read` cannot consume that text. M3.12's copy-then-reparse path exposes this older inconsistency. The copy test proves MonoReport's intended text transformation, not Excel execution.

## 4. Excel semantics: documented, derived and unverified

1. **Verified documentation:** Microsoft's [MS-XLSX formula grammar](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-xlsx/3d025add-118d-4413-9856-ab65712ec1b0) defines an A1 area as two independently valid cells separated by a colon, with row/column absolute markers. It supplies dimension limits but no increasing-endpoint condition in that production. Microsoft's [reference-operator documentation](https://support.microsoft.com/en-gb/excel/calculation-operators-and-precedence-in-excel) describes the colon as including the cells between both references. A descending spelling denotes a rectangle, not reverse traversal or an empty set. Applying those rules to particular crossed coordinates below is a semantic deduction, not a newly observed Excel run.
2. **Verified copy rule:** Microsoft's [relative, absolute and mixed reference documentation](https://support.microsoft.com/en-us/excel/switch-between-relative-absolute-and-mixed-references) fixes each dollar-marked coordinate and adjusts each relative coordinate on copy. Consequently, copying `A3:$C$3` four columns right gives endpoint identities `E3:$C$3`, whose geometric extent is C3:E3. Copying that formula one further column right gives `F3:$C$3`, extent C3:F3. This is an application of documented rules; exact formula-bar spelling is not asserted.
3. **Verified shared storage rule:** the ISO remarks reproduced in Microsoft's [CellFormula documentation](https://learn.microsoft.com/en-gb/dotnet/api/documentformat.openxml.spreadsheet.cellformula?view=openxml-2.8.1) determine a follower from its position relative to the master and compare shared formulas through R1C1 representation. Redundant follower text does not override the master. Shared formula normalization means expanding that representation; it does not require sorting A1 operand text.
4. **Derived two-dimensional semantics:** for finite same-sheet cell endpoints, the referenced addresses are the inclusive row interval crossed with the inclusive column interval. Either or both axes may descend. `E1:$C$3` covers C1:E3. Dollar flags affect subsequent copying, not that current rectangle. This reasoning stays within the approved finite A1 envelope; it does not establish support for computed endpoints, arrays, whole axes, unions synthesized by the engine or other unsupported forms.
5. **Not empirically verified here:** Excel's exact displayed spelling, internal canonicalization, saved XML, persistence of a shared group across a crossing, and subsequent copies after open/save/reopen on a named Excel version. No Excel/LibreOffice execution or browser automation ran. The M3.12 review's statement that Excel accepts the specific crossed example is consistent with the documentation but includes no recorded Excel version/fixture/run. Prior Feature 012 LibreOffice research does not cover this case and is not an Excel oracle.
6. **Fixture qualification:** the existing review probe is a useful source-parser reproduction, not a complete successful-workbook oracle. Its B3 master uses `SUM(A3:$C$3)` while PrintArea starts at B3: A3 is outside crop, and the master formula also includes its own cell. After removing the ordering failure, independent crop/shared-output checks can still reject it. A public success proof needs retained operands, no circular formula, and authorized M3.13 support; the current probe does not establish public success after a parser correction.

## 5. Canonicalization and subsequent copying

1. Equal current rectangles do not by themselves establish equivalent later copying. For `E3:$C$3`, replacing only addresses with ordered bounds while leaving flags in their old slots yields `C3:$E$3`. Both currently cover C3:E3, but after a rightward copy the former covers C3:F3 and the latter D3:E3. This is the precise risk in retaining current relocation formatting after removing the parser check.
2. Correct canonicalization **can** preserve later-copy semantics. For the same-row example, `$C$3:E3` retains each coordinate's fixed/relative behavior and copies to `$C$3:F3`. It is not inherently incorrect merely because endpoint order changed. The M3.12 review's proposed canonical alternative is valid for that example.
3. A whole-point swap does not solve general rectangles. For `E1:$C$3`, swapping endpoints gives `$C$3:E1`, which still descends in rows. Independent axis normalization carrying each coordinate's own flag gives `$C1:E$3`. A subsequent down/right copy produces `$C2:F$3`, covering C2:F3, just as copying the preserved spelling produces `F2:$C$3`. Keeping the old flag slots while merely taking minimum/maximum addresses is incorrect.
4. Within worksheet bounds, correct per-axis canonicalization and preserved-order copying are geometrically equivalent under further copies: each axis retains the same two coordinate/flag pairs, and copying applies the same delta independently to each relative member before taking that axis's minimum/maximum. Pairing rows and columns into a different pair of corners does not change their Cartesian rectangle. This is an algebraic argument from the documented rules, not proof of Excel's chosen serialization.
5. Do not collapse an authored range to a scalar when its endpoints meet. `C3:$C$3` currently denotes one cell but has different copy behavior from either scalar endpoint. Preserve `IsRange`, both endpoints and all flags, including equality cases. Stable handling of equal coordinates also avoids unnecessary changes to existing increasing operands.

## 6. Comparison of the three options

| Criterion | 1. Keep and document restriction | 2. Canonicalize after copying | 3. Preserve endpoints; normalize geometry |
| --- | --- | --- | --- |
| Correctness | Safely rejects crossed copies; does not satisfy the full mixed-copy contract. | Correct for copied ranges only if normalization is per axis with the associated flags, including equal-coordinate cases. | Preserves source/copy intent directly; requires normalized geometry input and orientation-aware relocation output together. |
| Implementation complexity | Lowest code cost; requires honest diagnostics, authoring guidance and approved requirement reduction. | Small copy change for the one-row probe; general solution needs row/column flag reassociation and reparsed spans. Existing geometry/output can then remain increasing. | Bounded parser/geometry-boundary/formatter change; existing endpoint model, copy routine and geometry algorithms remain. No canonical-text construction is required during copying. |
| Feature 012 compatibility | Material limitation against Spec §6.3/§6.9/§6.11 and M3.12; cannot silently adopt it. | Repairs follower crossing while retaining an unexplained difference between authored descending operands and identical copied operands. Extending canonicalization to all parser entry points is a broader variant of this option. | Best fit for finite A1 rectangles and existing preservation/copy commitments. Authored and copied operands share one rule. |
| Later copying | Unsupported crossed cases fail before output. | Equivalent when every coordinate retains its own flag; naïve sorting may silently change results later. | Original endpoints/flags remain available; output must preserve their relation to the relocated bounds. |
| Compatibility risk | Existing safe failures remain; valid Excel authoring is unnecessarily rejected. | Changes exact copied text and existing copy-test expectations. Does not resolve authored descending input as stated. | Previously rejected finite operands reach existing safety checks. Previously increasing operands should retain exact output and behavior. |
| F-001 | Leaves F-001 unresolved on already accepted increasing ranges. | Can expose F-001 after allowing a follower to reach geometry. | Same exposure; normalized bounds provide the correct domain for any approved coverage correction. |

1. **Practical author value:** support normal mixed anchors whose relative side crosses the fixed side during shared normalization or later author copying. The author should not need to understand MonoReport's geometric representation to express a finite Excel rectangle.
2. **Simpler rejection alternative:** if option 1 is selected, report the group/member, copied operand and crossing, and advise ordinary per-cell increasing formulas with coordinate flags correctly reassociated, or re-author the shared formula/group to avoid crossing. Merely re-saving as scalar formulas is insufficient if the scalar spelling remains descending. Changing both endpoints to absolute/relative can alter intent. Adding helpers is unnecessary for this bounded case.
3. **Recommendation:** option 3 avoids a new public limitation and retains the existing syntax/copy representation. Option 2 is a defensible short implementation if the Owner explicitly accepts authored descending operands remaining unsupported, but that restriction has no demonstrated product value. A general canonicalizing parser could also be correct; it adds text/flag normalization that preserving the existing endpoints does not need.

## 7. Proposed bounded design and F-001 interaction

1. **Parsing/copying:** retain lexical endpoint order, flags, qualifiers, sheet/name identities and source spans. Remove only the formula-operand order rejection after approval. Keep finite dimension checks, malformed-token rejection, supported-name rules and shared-group inventory unchanged. Continue source copying followed by reparsing before owner relocation.
2. **Geometry boundary:** derive an increasing source rectangle using the smaller/larger row coordinates and smaller/larger column coordinates. A small local helper or derived value suffices; the Developer can choose its location. Keep `XlsxRectangle`, interval projection and merge geometry ordered. Never treat lexical endpoint order as row/column ordering.
3. **Relocated text:** after a faithful rectangle image has been proved, map each endpoint's row to the corresponding low/high output row according to its original row orientation, and independently map its column according to column orientation. Retain each endpoint's existing row/column dollar flags. For ties, preserve the current first-low/last-high convention on that axis; a degenerate source range can legitimately expand structurally. Preserve range syntax even for a single-cell image. Increasing operands therefore keep existing formatting. Do not project two endpoint scalars separately: that loses full-interior coverage and can reject legitimate descendant expansion or miss holes.
4. **Scope safety:** orientation does not justify selecting new owners. Keep descendant/global/leaf/absolute-anchor selection and the mixed-owner comparison. An accepted spelling still rejects if its mapped image is unsafe. This is Excel-compatible finite-reference handling within Feature 012's declared safe-transformation envelope, not a promise to emulate every Excel edit operation.
5. **F-001 remains independent and unresolved:** its current defect is loss of distinct source portions through owner/span filtering despite contiguous surviving output. It occurs for increasing `B2:B3`; endpoint normalization cannot fix it. The [pending F-001 proposal](f-001-architecture.md) requires full compatible source-domain coverage in ordinary intervals and content-owner cutouts, plus the existing output-shape proof. For a descending operand, that source domain must be the entire normalized rectangle, including blank addresses and interior intervals.
6. Both projections in the mixed-flag comparison need the proposed F-001 completeness validation, not only matching `Kind`/`Rectangle`. Retain displaced-identity rejection before owner union. Do not widen scope, accept partial-source contraction, synthesize unions, or relax merge collapse rules to make a reversed operand pass. Formula completeness and merge preservation remain different consumers of the same normalized geometry.
7. Resolving F-M312-1 can make previously rejected inputs reach the existing F-001 defect. An orientation-only patch must not claim complete range safety or M3.13 acceptance while that defect remains. Owner authorization and verification for F-001 are separate; this report does not approve or implement that proposal. Development order can be chosen by the Owner, but shared-output completion must account for both findings.
