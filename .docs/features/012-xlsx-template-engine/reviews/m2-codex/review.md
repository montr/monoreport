## 3. Code quality and architecture assessment

1. **Existing project rules:** no additional confirmed service-construction, static-service or reusable-operation-state violation was found in the reviewed production changes. XLSX services use instance methods, supplied dependencies and null guards; mutable data, diagnostics, instance dictionaries and package handles are operation-local. Private static helpers and constants are consistent with the rules. Regular facade constructors support the approved compatibility overloads. The three functional findings are contract/integrity defects, not style preferences.
2. **DI factories are currently necessary.** [MonoReportServiceCollectionExtensions.cs:14](/Users/blackish/Projects/monoreport/MonoReport/MonoReportServiceCollectionExtensions.cs:14) manually resolves facade constructor arguments, but the full-format constructors of [MergeEngine.cs:24](/Users/blackish/Projects/monoreport/MonoReport/Services/MergeEngine.cs:24) and [TemplateAnalyzer.cs:24](/Users/blackish/Projects/monoreport/MonoReport/Services/TemplateAnalyzer.cs:24) are internal. The public constructors intentionally retain legacy DOCX composition. Replacing the two registrations with type-based `TryAddTransient<T>()` cannot select those internal constructors. An independent temporary-container replacement reproduced XLSX analysis falling through the Word path with `template.unsupported_structure`. The factories are explicitly approved in plan section 3.1.3 and are composition-root wiring, not a service locator hidden inside business logic. Keep `TryAdd`, transience and consumer overrides. Other XLSX registrations already use type-based registration. No safe one-line facade registration simplification is available within the current constructor/accessibility contract.
3. **Concrete maintainability concern:** two orchestration/geometry paths encode overlapping validation responsibilities. The all-static path produces a plan usable by formula preflight; the repeated/mixed path returns null and follows a different route. F3 is direct evidence of drift across those paths. Correct that shared invariant as part of F3; a general planning framework or wholesale rewrite is unnecessary. F1/F2 similarly show that cell suppression and merge-anchor content decisions are not fully represented in the geometry used by consumers. Repair the ownership contract at those boundaries rather than patching emitted XML after validation.
4. **Separation of concerns:** the internal XLSX namespace, explicit sheet/cell/instance models and neutral `DataScope`/requirement accumulation provide useful format boundaries. Shared public APIs do not expose SpreadsheetML. M2 does not change the shared parser/resolver/formatter algorithms or Word rendering. Formula scanning remains separate from reference binding and rendering. `XlsxTemplatePlanner` handles several related stages across partial files, but its size alone is not a defect; no additional injected stage or generalized format registry is justified by this review.
5. **Organization, optional:** a future functional `Core / Docx / Xlsx` grouping could colocate each format's services, plans and supporting types and make shared language/dispatch components easier to identify. Current `Services/Xlsx` and `Models/Xlsx` already isolate the new format and match the approved plan. Moving files/namespaces now would add review noise without resolving F1–F3. This is a future cleanup option, not an M2 gate or authority to split assemblies/public APIs.
6. **Tests:** exact formula strings, independent tuple values, merge coordinates, native types, zero-size states, raw sentinel checks and schema checks are meaningful. The 99/100/101 resolution counters detect plausible evaluation-cap failures. Important composition gaps remain: merge collapse only exercises a retained anchor before the child; parent-heading suppression is tested without dependent formulas; static-image parity is tested only in all-static workbooks. Several low-level formula tests bind a supplied formula against prepared placements rather than exercising the entire public pipeline. Preserve those focused tests, but add the public combinations in F1–F3. No test-count or coverage target is recommended.
7. **Documentation, nonblocking:** README line 5 and the XLSX compatibility document foreground Feature/M2/M3 labels; CLI help and OpenAPI also mention implementation milestones, and OpenAPI analysis describes a “preflight” slice. These are accurate progress notes but poor user-facing authoring guidance. Before final documentation delivery, describe currently available behavior and practical remedies directly, and provide a compact XLSX authoring/data walkthrough under the already approved sample/documentation work. Keep historical milestone evidence in Feature documents. No change to the current product envelope is implied.

## 6. Diagnostic resource bounds

1. **The 100-error limit is not a general discovery/work/memory bound.** [XlsxTemplatePlanner.cs:26](/Users/blackish/Projects/monoreport/MonoReport/Services/Xlsx/XlsxTemplatePlanner.cs:26) retains source diagnostics before selection; each retained source cell is parsed. The planner retains cell plans, tokens and dependencies. [TemplateRequirementBuilder.cs:38](/Users/blackish/Projects/monoreport/MonoReport/Services/TemplateRequirementBuilder.cs:38) retains each dependency use at its path nodes; its Diagnostics property materializes all conflicted uses into an array. The planner appends those results, orders the combined sequence and applies `Take(GenerationDiagnosticPolicy.ErrorLimit)` at line 111. Therefore only the published prefix/context list is bounded here. LINQ may optimize selection, but `Take` does not undo upstream discovery, materialization or source buffering; no assumption of a full sort versus optimized prefix selection is needed for this conclusion.
2. **Source-order correctness justifies complete dependency discovery.** A late field, including one on a later worksheet, can conflict with an earlier field. Stopping source traversal at the first 100 encountered syntax errors would regress accepted M1 F4 by excluding earlier-source conflicts discovered later. The existing 97–101 syntax/conflict and cross-sheet regressions remain valid and passed. Do not replace the current logic with first-100-discovered collection or deduplication.
3. **Small independent observation:** public Analyze on one source row with 101 versus 1,001 `{!}` cells published 100 errors in both cases. Final runner observations were respectively 737,336 versus 3,485,360 allocated bytes on the calling thread and approximately 1.24 versus 5.37 ms. These are single, small diagnostic probes, not a capacity benchmark or allocation SLA. They support the code-inspection conclusion that source preparation grows beyond 100 errors; neither case showed practical exhaustion.
4. **M2 interaction:** source parse/conflict errors stop before repetition, so they are not automatically multiplied by the Cartesian output. Runtime scalar binding genuinely stops at exactly 100 errors/resolutions, as independently executed 99/100/101 counter tests demonstrate. However, [XlsxTemplateHandler.cs:57](/Users/blackish/Projects/monoreport/MonoReport/Services/Xlsx/XlsxTemplateHandler.cs:57) materializes the repeated workbook before binding values; binding/formula ordering also buffers/sorts placements. A compact valid template with many logical rows, wide headers and missing fields can allocate a large plan before the first 100 failures are published. Excel row/column checks bound axes, not total populated-cell memory. Successful warnings remain a separate complete collection, not part of the 100-error cap.
5. **Classification:** no confirmed practical resource-exhaustion defect was reproduced. Complete source/dependency preparation is an acceptable current correctness tradeoff within the approved in-memory design. Growth of diagnostics, dependency uses, placements and warnings is a **capacity risk requiring the already planned M6 measurement/R1 decision**. The existing counters cover source/package bytes, cells, source formulas, resolved fields and output cells, but do not yet provide the full stage/allocation/peak-memory and emitted-formula/reference-token/matrix accounting required for M6 reconciliation. Do not describe the current cap as bounding total work or claim deployment adequacy from these probes.
6. **Proportionate recommendation:** retain source-ordered publication and the runtime stop behavior. Include error-heavy source templates and repeated missing-field reports in the approved bounded M6 measurements, alongside normal workloads; observe peak memory and time by stage before choosing any numerical ceiling. If discovery retention is a measured problem, consider bounded prefix retention only with a design that still admits earlier uses implicated by later conflicts. If placement dominates, address the measured planning/allocation issue rather than rewriting diagnostic selection for elegance. No new ceiling, warning truncation, streaming architecture or algorithm change is approved by this review.
