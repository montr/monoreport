## 1. Verdict

1. **Needs revision.** The recursive two-axis geometry, physical crop, bounded reference transformer, owned merge projection and existing-interface delivery substantially follow the approved requirements. The plan nevertheless conflicts with the latest warning decisions, introduces a verified Word-package acceptance regression, and leaves the first combined slice inside oversized implementation phases. Revise those points and the formula-test selection before approval; this review grants no implementation authorization.
2. The 60–89 engineer-day estimate remains an uncertain planning hypothesis. Removing duplicate warning infrastructure and speculative compatibility work, keeping shared-code extraction narrow, and decomposing the first slice justify re-estimation; repository evidence does not establish a reliable replacement total or promise that the effort can be halved.

## 2. Findings

1. **F1 — Major — The warning architecture contradicts the latest Product Owner decisions. Confirmed plan conflict.**

   **Evidence:** Plan section 3.2, lines 62–63, introduces `ReportDiagnostic`, `MergeResult.Diagnostics` and two warning projections. Section 3.3, lines 71–72, serializes the new model and adds a parallel structured DOCX list through `DocumentRenderer` and `MergeContext`. The component table, line 36, and M5, line 140, require that DOCX adapter. The current [MergeResult](../../../MonoReport/Models/MergeResult.cs), line 3, already exposes `Warnings`; [MergeDiagnostic](../../../MonoReport/Models/MergeDiagnostic.cs), lines 3–9, already carries message, source and data-path context. The owner now explicitly requires that single warning model and collection.

   **Impact:** These tasks add public surface, duplicate warning storage/projection and DOCX changes that are no longer authorized design choices. The plan's instruction to leave successful DOCX CLI diagnostics unchanged, line 72, also conflicts with the current decision to send successful warnings to stderr. The existing [CLI](../../../MonoReport.Cli/Services/CliApplication.cs), lines 67–90, publishes the document and returns without emitting successful warnings.

   **Smallest fix:** Delete `ReportDiagnostic`, `MergeResult.Diagnostics`, parallel warning lists and the DOCX warning-code adapter from the proposed work. Use `MergeResult.Warnings` throughout. An optional non-positional nullable `MergeDiagnostic.Code` can carry stable XLSX codes; existing DOCX warnings can leave it unset. Emit successful warnings to CLI stderr for either format. The format-neutral HTTP multipart writer must serialize the same warning collection for DOCX and XLSX, including an explicit empty array, without generating DOCX-specific codes or parsing messages. Describe warning severity through the warning collection/channel; do not introduce another Core warning model to satisfy the older representation proposal. Keep generation errors on the existing exception/diagnostic path.

2. **F2 — Major — The proposed package allowlist rejects Word package types accepted today. Verified proposed behavior regression.**

   **Evidence:** Plan section 3.1, line 55, accepts ordinary DOCX/XLSX only and rejects macro-enabled/other package types. [DocxStoryReader](../../../MonoReport/Services/DocxStoryReader.cs), lines 17–28, currently calls `WordprocessingDocument.Open` without that additional filter. In the earlier review turn, a narrow smoke check against the existing Release CLI accepted synthetic DOCX, DOTX, DOCM and DOTM main-part types: each analysis returned exit 0 and `valid=true`; each generation returned exit 0, nonempty document bytes and empty stderr. The current source still matches the inspected path. Feature Spec section 2, item 7, requires preserving existing DOCX inputs and behavior.

   **Impact:** A new discriminator would reject previously processable Word-family templates before reaching the existing renderer. This is a functional regression even though there are no external clients. The smoke check proves acceptance of those main-part types, not exhaustive macro preservation or Office fidelity.

   **Smallest fix:** Detect and route the Word-family package kinds already accepted by the existing path; keep the initial spreadsheet path limited to ordinary XLSX. Preserve actual-package detection rather than trusting extensions. Add narrow regression cases for the four observed Word types through analysis and generation. If restricting those inputs is desired, identify it as a proposed product change rather than a routine XLSX implementation detail.

3. **F3 — Major — M1–M3 are too large to serve as sequential Codex/OpenCode session milestones. Confirmed decomposition gap; application-dependent delay is a risk.**

   **Evidence:** Plan section 5, lines 136–143, gives M1 5–7 days, M2 12–17 days and M3 12–18 days. M1 combines public results, dispatch/DI, shared extraction, inventory, recursive models, diagnostics and static processing. M2 combines binding, placements, merges, formula parsing/binding, rendering and crop. The first working combined result is estimated at 17–24 days. Lines 131 and 154 make later phases depend on closing M2, whose closure requires external recalculation of a newly generated workbook.

   **Impact:** Each phase contains several independently fallible algorithms and offers too few explicit resumption points. External-application availability may block otherwise independent implementation. This is not evidence that those algorithms are unnecessary: the approved architecture explicitly requires both-axis geometry and a combined formula/crop slice.

   **Smallest fix:** Retain M1–M6 as reporting phases, but add session-sized checkpoints, each with a bounded behavior, an observable assertion and a focused test group. Split M2 as suggested in section 5 below, and similarly separate M3's vertical grammar, table displacement, name/sheet binding and shared-formula work. Permit independent development to continue while early calculated-value evidence remains explicitly pending. Retain required final Excel/calculation acceptance; never mark pending evidence passed.

4. **F4 — Minor — M2's prescribed checks omit its dedicated formula-test group. Confirmed verification-selection defect.**

   **Evidence:** M2, line 137, introduces formula tokenization/binding and prescribes V3 plus V1 for shared changes. V3, line 191, selects only `Feature012TwoAxisTests`, `Feature012GeometryTests` and `Feature012BindingTests`; V1 selects existing shared/DOCX groups. `Feature012FormulaTests` is selected by V4, line 192, and mapped to M2 formula acceptance in rows A6/A12, lines 165 and 171. These are proposed tests, not tests that already exist or have passed.

   **Impact:** Following the listed milestone commands can omit newly added focused lexer/copy/reference tests at the first formula checkpoint. The combined fixture's assertions are useful but do not substitute for those lexical and negative cases.

   **Smallest fix:** Add the implemented `Feature012FormulaTests` subgroup to the relevant M2 checkpoints, together with the applicable diagnostic negatives. Keep selection narrow; do not require a full solution run after every checkpoint.

5. **F5 — Minor — The blanket requirement to resolve P1–P4 before M1 overstates the remaining decision gate. Confirmed sequencing inconsistency.**

   **Evidence:** Plan lines 132 and 257 require P1–P4 resolution before implementation. However, P4 at lines 213–214 and 250 calls its ceilings unmeasured candidates and requires approval before activation, informed by workloads and measurements. P3 at lines 65 and 249 reuses the existing analyzer schema. The owner has now settled the warning model and multipart direction, superseding substantial parts of P1/P2.

   **Impact:** Already resolved choices may be reopened, while provisional resource numbers become an unnecessary prerequisite for unrelated foundation work.

   **Smallest fix:** Record the supplied decisions in the revised plan without requesting them again. Treat P3's existing-schema mapping as an implementation choice covered by plan approval. Keep Excel dimensions, checked arithmetic and early resource accounting from the start; approve application-specific ceilings before they are activated. Overall implementation-plan approval remains required.

## 3. Unnecessary scope and optional simplifications

1. **Remove rejected warning infrastructure; retain reusable multipart. Required correction, not an optional optimization.** F1 removes the second model/collection and DOCX-specific warning-code work. A single multipart mechanism over document bytes, format metadata and `MergeResult.Warnings` still satisfies the current owner decisions. DOCX reuse must remain part of the mechanism; XLSX-only negotiation is no longer the recommendation.
2. **Avoid speculative compatibility machinery. Optional simplification of implementation choices.** There are no external clients. Do not introduce custom record equality, serialization adapters, compatibility façades or a frozen warning JSON shape to protect hypothetical consumers. An optional `Code` property does not justify a parallel model. Focus verification on existing DOCX rendering, input/stream ownership, current repository construction and DI usages, and binary/error behavior. Existing explicit constructor constraints still apply; preserve callable paths straightforwardly where required rather than inventing additional composition modes or constructing service defaults internally. No claim is made that current functional regressions are acceptable.
3. **Keep component boundaries provisional. Optional simplification.** Plan section 2, lines 25–46, turns each conceptual stage into a concrete injected service and several intermediate models. Feature Spec section 9 requires separation at least conceptually, not a service per stage. Reader/cell adaptation or binding/template planning can share a concrete implementation when that avoids duplicate traversal and boilerplate; merge projection can remain close to geometry. Preserve a clear formula boundary and the final geometry contract. Consolidation trades smaller initial composition for potentially larger classes; choose it based on actual code, not file-count targets.
4. **Extract only the small shared mechanisms. Optional simplification.** [DataResolver](../../../MonoReport/Services/DataResolver.cs), lines 12–49, needs a neutral scope input, not a generalized context framework. [TemplateAnalyzer](../../../MonoReport/Services/TemplateAnalyzer.cs), lines 56–138, already isolates dependency accumulation. Reuse the existing payload when suitable, retain operation-local mutable accumulation, and avoid reworking Word structural planning. [UnifiedTemplateTests](../../../MonoReport.Tests/Services/UnifiedTemplateTests.cs), lines 208–261, already tests conflicts, first-use ordering and duplicate occurrences; reuse it instead of creating duplicate DOCX suites.
5. **Bound metadata handlers by concrete fixtures. Optional scope-control refinement.** The plan correctly permits actionable rejection of affected unsupported tables, charts, drawings, conditional formatting and validation. Preserve that boundary. Define the actual initial print-title, break and pane transformations before estimating them; keep unknown/unproven affected cases actionable rather than building a general OOXML dependency or repair framework. This still meets the accepted preserve/transform/reject policy and retains necessary document-integrity checks.
6. **Bring thin CLI/HTTP wiring forward. Optional sequencing simplification.** Current [DocumentEndpoints](../../../MonoReport.Api/Services/DocumentEndpoints.cs), lines 30–33, hardcodes DOCX MIME/filename. Once Core static XLSX works, add correct MIME/filename selection and basic CLI/analyzer parity before waiting for all of M4. Complete multipart as its own focused checkpoint. This exposes integration issues earlier; it does not require another public route or XLSX façade.
7. **Re-estimate a lean task breakdown instead of applying an arbitrary discount.** Remove the now-rejected warning tasks and hypothetical client compatibility work, and estimate the smaller checkpoints. Separate implementation effort, contingency and acceptance waiting; removing an application scheduling blocker reduces elapsed delay but does not itself prove engineer-day savings. Retain formula ownership, merge safety, physical crop, deterministic diagnostics, native precision/date behavior and required transports. The research [README](research-spikes/README.md), lines 14 and 40, explicitly leaves generic marker inference, arbitrary bindings, shared packages and realistic capacity unproved; neither the spike's size nor its 171 matching transformations establishes production effort. Do not reuse the superseded Core-only estimate from Architecture Assessment section 9, item 8.

## 4. Owner decisions applied and remaining approval items

1. **Single warning model — settled.** Use only `MergeDiagnostic` for successful warning entries, exposed by `MergeResult.Warnings`. No `ReportDiagnostic`, `MergeResult.Diagnostics` or parallel warning collections. The existing generation-error model remains separate from successful warnings.
2. **Optional stable code — settled permission.** A nullable, non-positional `MergeDiagnostic.Code` is a reasonable small addition for XLSX assertions and actionable diagnostics. It need not be populated for existing DOCX warnings. No DOCX-wide refactor, new severity model or custom backward-compatibility layer follows from this permission.
3. **CLI warning channel — settled.** Emit successful warnings to stderr for either format and leave binary stdout clean. The earlier instruction to keep DOCX successful stderr unchanged is superseded. Ordinary rendering/error/exit and output-on-generation-failure behavior remains subject to regression checks.
4. **HTTP warning transport — settled.** Preserve default binary responses; opt-in `Accept: multipart/mixed` returns the document plus JSON warnings from the same operation. Use a format-neutral writer over the existing warning model and reuse it for DOCX. Retain correct MIME/filename, an explicit empty warning array and preparation before response publication. This review does not reopen multipart selection or recommend XLSX-only support. Remaining JSON member naming and routine media-type handling can be specified in the plan without another product gate.
5. **No external clients — settled scope guidance.** Preserve existing DOCX functionality and real repository contracts without engineering compatibility mechanisms for imaginary clients. The previous concern about new `MergeResult.Diagnostics` state changing DOCX record equality is superseded by eliminating that property; it is not a reason to implement equality infrastructure. Lightweight construction/DI checks remain useful where the actual composition changes.
6. **P1–P4 reconciliation.** P1 must drop its rejected warning surface; required format identification can remain a small result property or another concrete internal mechanism, with no format registry. P2 retains generic multipart and loses the DOCX warning adapter. P3 needs no new schema vocabulary or separate approval ceremony. P4's numerical ceilings and representative workload remain genuine owner decisions before activation; no resource SLA or public configuration is implicitly approved.
7. **Implementation approval — still pending.** Revise the plan to reflect these decisions and the confirmed defects, then obtain the existing required plan approval. Do not add a mandatory reviewer role, new acceptance workflow or additional status file. No Git mutation is authorized by this review.
