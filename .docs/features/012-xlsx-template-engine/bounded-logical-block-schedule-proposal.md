# Feature 012 — Bounded vertical logical block schedule proposal

## 1. Recommendation and decision boundary

1. **Draft for Owner review, 2026-10-22. Recommend bounded B:** an immutable sequence of vertical block instances between existing binding and geometry. Its smallest useful form contains three small records and one role enum, shares existing source blocks and vertical instance identities, and leaves horizontal expansion in the existing geometry planner. Do not build a second template tree, data hierarchy, field resolver or worksheet representation.
2. B's expected benefit is independently testable runtime block ownership/order and a geometry method that consumes that decision rather than making it. It does not simplify the already narrow renderer, repair F1 again or establish a performance improvement. A, extending geometry directly, remains a valid and smaller fallback. Section 8 explains why the limited extra representation may still be useful and when to reject it.
3. M1/M2/M3.1/M3.2 are accepted. The bounded F1/F2 corrections are complete and verified; [the correction record](implementation-progress.md#L178) reports 17 regression cases, 429 affected tests and 710 normal solution tests passing. These are attributed results, not tests rerun for this proposal. The Owner favors investigation of B but has approved no architecture change.
4. This task changes only this proposal and the sanitized [preprocessing assessment](preprocessing-architecture-assessment.md). The implementation plan, specification, decisions, progress, code and tests are protected. M3.3/M3.4, full M3.14 integration and public nested generation remain unauthorized. The public nested-generation guard remains in place; all implementation/checkpoint changes below are drafts inside this document only.
5. Review R2 is considered at M3.4; R1 missing-level ancestor behavior remains M3.5; full public analyzer-scope integration remains M3.14. Neither B nor its proposed mismatch check decides those later behaviors by implication.

## 3. Minimal proposed model

### 3.1. Records and fields

| Proposed internal type | Fields | Meaning and allocation boundary |
| --- | --- | --- |
| `XlsxLogicalSheetSchedule` | `SheetId: uint`; `Regions: ImmutableArray<XlsxVerticalRegionSchedule>` | Matches one existing sheet. Regions retain template source order, with an empty array for a sheet without vertical regions. |
| `XlsxVerticalRegionSchedule` | `RegionId: int`; `Blocks: ImmutableArray<XlsxLogicalBlockInstance>` | One existing source region and its block instances in final logical emission order. An empty collection yields no block entries. |
| `XlsxLogicalBlockInstance` | `Source: XlsxVerticalBlock`; `Role: XlsxLogicalBlockRole`; `Owner: VerticalInstancePath` | References one existing source block and the selected logical data owner. Header/footer entries for an item share the same Owner object. No copied row data, scope or final coordinate. |
| `XlsxLogicalBlockRole` | `Header`, `Body`, `Footer` | Records which property of the existing source node supplied Source. The role makes assertions/review explicit; it is not another template syntax or a physical span kind. |

1. These are proposed records, not files/types already implemented. A single `Models/Xlsx/XlsxLogicalSchedule.cs` would suffice if approved. Construction belongs to an instance method on the existing XlsxTemplatePlanner, with helpers in a proposed `XlsxTemplatePlanner.Scheduling.cs` partial. No new injected service or dependency is necessary.
2. Source retains authored row identifiers because the consumer must know which template rows to copy. **Coordinate-independent means no output row/column, OutputFirst, crop offset, worksheet XML clone, projected merge or formula address in the schedule.** Source intervals are references to existing template content, not a second placement algorithm.
3. Owner reuses the existing VerticalInstancePath, with `RegionId` and `LogicalRows` defined as bound first-record indices from root to current item. The current item is the **last** index. A flat item still has exactly one index, preserving accepted identities. The owning sheet supplies sheet scope; two independent regions using the same collection remain distinct.
4. A block instance is identified by sheet, region, owner path, original source block and role. Sequence position determines emission order and is not a permanent ID. Do not assign new synthetic row IDs or interpret FirstIndex as a logical-array offset: with four records per item, successive first-record indices may be 0,4,8.
5. Create one canonical immutable Owner path per scheduled logical item and share it across that item's header/body/footer and resulting spans. Use scalar region/first-record keys for operation-local lookup; do not recursively hash/compare XlsxLogicalRow records with their Parent chains. Existing record/ImmutableArray equality is not a substitute for explicitly defined sequence identity when paths are independently constructed.
6. The existing region rows provide a first-record-index lookup for recovering the current XlsxLogicalRow. Parent and ChildFirstIndices stay on those rows. The schedule contains no extra Parent/Children graph, copied ancestors, tuple arrays, field-expression list, resolved scalar values or diagnostic collection.
7. Store no total height or subtree count as a second authority. Geometry derives a region's repeated row contribution by checked summation of Source block heights. A traversal can count entries while constructing the immutable array, but must not maintain another independently mutable ordering model.

### 3.2. Invariants

1. Every schedule sheet/region resolves to the corresponding existing template and bound data. Each Source is the actual Header/Body/Footer block on a parsed node, and Role agrees with that property. It is never a reconstructed whole-region rectangle for a nested item.
2. Every Owner resolves to one bound logical row in that region; its path follows the existing Parent links and ends at that row's FirstIndex. No component reconstructs parentage from level comparisons or `$path` text after BindHierarchy.
3. All rows in a multirow Source block share one Owner and reuse the same tuple records. Physical row count never multiplies input arity or creates additional logical items.
4. An item with both header and footer has one logical owner, referenced by two entries separated by its ordered child entries. Footer emission changes presentation order, never parentage or the current scalar context.
5. Empty child sets add zero child entries. Existing parent headers/footers can still have entries. Static rows and separators are absent from Blocks; geometry emits each source gap once. An empty entire region removes its repeated rows and preserves subsequent static content under existing crop/displacement rules.
6. Under the initial nested domain, source/data ownership must be compatible. A source role and input item cannot be paired merely because their levels occur somewhere in both inputs. Section 6 bounds R2 validation and keeps missing-level recovery separate.
7. The source tree, bound hierarchy and schedule are immutable per operation. Geometry consumes Blocks in order without selecting rows by level, issuing omission warnings again, or traversing the data hierarchy. Values use the owner already carried into placements; they do not reschedule blocks.
8. A valid schedule alone is insufficient for output. Geometry, merges, formulas and metadata still must pass their existing safety checks before rendering any returned report. No permissive fallback may hide an invalid plan.

## 4. Construction and exact integration points

### 4.1. Proposed construction

1. Keep Plan/Prepare/Structure, BindSheet, GroupRecords, ValidateArity and BindHierarchy unchanged. After all sheets bind successfully, the repeated-report branch of XlsxTemplateHandler.Merge would call proposed `XlsxTemplatePlanner.ScheduleSheet(templateSheet, boundSheet, context)` for each sheet in workbook order. The static-workbook branch and Analyze do not call it.
2. The flat adapter preserves today's single-level branch exactly: visit bound rows in input order, emit the existing Root.Body for matching levels and report the existing XlsxMissingLevel warning for each omitted item with the same source control and indexed data path. Do not add Parent links to the deliberately unbound flat rows or change `{../Name}` behavior; that is R1/M3.5.
3. For compatible nested input at M3.4, build an operation-local FirstIndex lookup, enumerate existing roots in input order and use an explicit traversal stack over source-node/bound-row pairs. Read Children and ChildFirstIndices from the existing structures. Enter an item by appending its Header when present; append Body when present; visit its compatible ordered children; append Footer on exit. The current grammar gives leaves a Body and wrappers headers/footers; it does not require inventing a wrapper body.
4. Pairing validates existing source owners against existing data owners; it does not construct either hierarchy. Before publishing a schedule, ensure each relevant matched data item has its intended source owner and was scheduled once per authored role. In particular, detect a level-40 item that would otherwise be ignored while searching only under expected level-20 owners. Source-order arrays and child indices are authoritative; numeric sorting of data is prohibited.
5. Construct each Owner path from the bound ancestry once per item, retaining the same path for its header/footer. The optional lookup cache is operation state, not mutable service state. A footer-only source still uses the input parent object that precedes its descendants in data order.
6. For unmatched or missing-ancestor situations outside the completed checkpoint, keep an explicit unsupported boundary rather than guessing recovery. The flat adapter remains accepted behavior; nested missing-level preservation is implemented only under M3.5 authorization. An absent child collection with no actual descendant items is simply empty, not an incompatible hierarchy.
7. Existing context diagnostics remain the only diagnostic channel. Flat warning message/code/source/data path and encounter order must remain unchanged; the handler's existing final warning ordering remains. New R2 failure handling follows the existing coded structural-data mechanism after Owner selection. Do not resolve fields during scheduling or change the 100-error value-resolution cap.

If a helper inside geometry proves equally clear and adequately testable, the representation is optional rather than inherently better.

## 5. Horizontal, value, merge and formula contracts

1. **Explicitly defer horizontal scheduling.** Keep Structure's XlsxHorizontalNode tree, HorizontalSpans, HorizontalInstancePath and header bindings. Their checked recursive width/own-column behavior already works for accepted cases. A vertical schedule entry does not carry a horizontal tuple or expand into one entry per leaf tuple. Geometry combines row and column spans at the existing EmitCells boundary.
2. The current BindInstances leaf test and mixed-radix tuple calculation remain authoritative: a leaf in bid b and criterion c selects b × criterionCount + c; repeated sibling template blocks reuse that tuple. Parent-only columns use the ordinary first record. HeaderScope uses preceding horizontal levels, never a vertical ancestor. These decisions are not copied into B.
3. Bind surviving cells only after ProjectMerges/PlanHeaderOwners decides content owners and suppression. Retained anchors keep their source, value context and style; suppressed and removed copies do not resolve scalar fields. Keep native numeric/Boolean handling, unsafe-number rejection, text escaping, explicit formatting, missing/null diagnostics and inert inserted values unchanged.
4. **Multiple spans per logical owner are a concrete integration hazard.** Currently ProjectMerges takes every region RowSpan's Vertical value without deduplication ([Merges:85](../../../MonoReport/Services/Xlsx/XlsxGeometryPlanner.Merges.cs#L85)). A future parent header/footer yields two spans for the same owner. Both A and B must select distinct compatible owners per source merge before projecting; otherwise they can project the same merge twice and falsely report overlap. This is reasoning about the future nested path, not a currently reachable public defect.
5. Preserve merge semantics: only authored merges, bounded parent-owned horizontal projection, one-cell collapse, disappearing empty owners, nonanchor style preservation and rejection of meaningful nonanchor data loss or unsafe/cross-owner images. Merges spanning independently repeated vertical blocks need proven ownership and a faithful image; this proposal adds no general vertical merge-repair handler.
6. Existing [content/displaced owner handling](../../../MonoReport/Services/Xlsx/XlsxGeometryPlanner.Owners.cs#L8) must survive scheduling changes. A physical blank source overwritten by a retained merge anchor cannot become an alias to that anchor. Preserve accepted [M2OwnershipTests](../../../MonoReport.Tests/Services/Feature012M2OwnershipTests.cs#L64) rather than replacing them with schedule-only assertions.
7. Finalize formulas only after every sheet's geometry and content ownership are safe. Relative/absolute/mixed flags, crop, global static totals and unique/contiguous/empty/disjoint/ambiguous reference images keep their existing contracts. Full owner paths supply useful future identity, but group descendant range binding remains M3.7 and cross-sheet/name/shared handling remains at its existing checkpoints. Do not broaden equality predicates to prefixes indiscriminately or infer an aggregate's business intent.
8. An empty horizontal product still has one descriptor per logical row. Vertical scheduling is unchanged by whether the product is zero; column geometry decides which leaf cells disappear and which parent-only columns survive. A disappearing formula is absent; a surviving formula with an unsafe empty referent still fails. No fabricated intersections, universal zero substitutions or implicit ISO-date conversion are introduced.
9. Preserve deterministic source/data locations, existing warning/error models, bounded diagnostics, input ownership, operation isolation and no partial output across Core/CLI/HTTP. B has no public API or transport effect. Any later public nested capability change must retain an actionable guard for still unsupported cases.

## 6. R2 and R1 boundary

1. Template source order `10,40,20` is accepted grammar: level 10 header, level 20 footer, level 40 body nested inside level 20. Input `10 P,40 X,20 Y` binds X and Y as siblings. The schedule cannot place X under Y without changing the producer's hierarchy. Even though all levels appear, the join is incompatible.
2. **Proposed M3.4 decision:** reject this concrete mismatch using existing GenerationInvalidData, identifying the level-40 source control/block and X's indexed input path, expected level-20 ownership and actual level-10 parent. With source rows 3/4/5 and arity one, those locations are source A4 and `$.Items[1]`. Offer re-authoring the source hierarchy or producer-supplied input in the intended parent-before-descendant order. Never sort/reparent internally, infer ancestry from path prefixes or silently omit X.
3. Compatible input `10 P,20 Y,40 X` produces header P, body X, footer Y. In B the owner paths are `[0]`, `[0,1,2]`, `[0,1]`; in A the same bound owners must be carried directly into spans. Empty input produces no entries and is not a mismatch.
4. This is a bounded compatibility check during M3.4, not an exhaustive hierarchy validation feature. It needs Owner approval before adoption. An implementation must detect incompatible matched-owner chains without rejecting every omitted level or choosing an unapproved recovery policy.
5. **R1 stays M3.5.** Single-level source regions currently bypass BindHierarchy, and [HierarchyTests:167](../../../MonoReport.Tests/Services/Feature012BindingTests.Hierarchy.cs#L167) pins root fallback for an omitted ancestor. Preserve that accepted baseline during extraction. Later recovery can retain logical ancestors while omitting their rendering, but the schedule must not supply that behavior early.
6. If an expected middle source level is absent yet deeper input items exist, or an unmatched input ancestor surrounds renderable descendants, do not label every case R2 or silently discard descendants. Keep the incomplete nested recovery path guarded until M3.5 determines safe ownership. An expected child level with no children or descendants simply contributes zero repeated child blocks; a parent header/footer may remain.

## 7. Seven scenario walkthroughs for A and bounded B

1. These are expected outcomes reasoned from the approved contract, not newly executed workbook tests. Cross-reference to the assessment: its section 6.1 is covered by 7.1/7.2 below; 6.2 by 7.3; 6.3 by 7.4; 6.4 by 7.5; 6.5 by 7.6; and 6.6/6.7 by 7.7. Thus all seven original scenarios remain represented, including empties and uneven siblings.

### 7.1. Flat vertical repetition and a multirow body

1. Source Body is rows 3–4 at level 10; two input rows have first-record indices 0/1, with no horizontal axis. A printed static tail follows at source row 5. Logical order is Body(0), Body(1); after cropping from row 3, physical rows are 1–2, 3–4 and one tail row 5. Each two-row body consumes one logical record.
2. **A:** a direct geometry helper selects the two items and emits their two-row source spans, then the tail. **B:** Blocks contains two entries sharing the original Body reference, with Owner paths `[0]` and `[1]`; geometry emits the same spans and one static gap/tail. No additional scalar binding structure exists.
3. This flat multirow behavior is already supported ([TwoAxisTests:154](../../../MonoReport.Tests/Services/Feature012TwoAxisTests.cs#L154)). B adds no product capability here. It must match accepted output and warning behavior before any nested traversal is enabled. With an empty input collection, no Body entry/span remains and the tail appears once.

### 7.2. Flat horizontal repetition

1. One horizontal header level has three elements and one leaf source column; optionally two flat logical vertical rows each have three contiguous tuple records. Header owners are horizontal item 0,1,2. Every ordinary row field uses tuple 0; leaf fields use tuple 0,1,2 in order.
2. **A:** HorizontalSpans supplies the three column instances; direct vertical spans combine with them in EmitCells. **B:** use identical horizontal spans and tuple selection. With vertical rows, Blocks has two body entries, not six. With no vertical region, schedule Regions is empty and header rows follow the existing printed static-row path.
3. Already supported responsibilities remain unchanged. Introducing three new logical column entries would enlarge B without removing any current horizontal interpretation, so it is explicitly outside the smallest proposal.

### 7.3. Three-level footer-first vertical source

1. Source rows have levels `90,40,10`. Input is `10 P,40 C1,90 G1,90 G2,40 C2,90 G3`, with first-record indices 0–5. Expected blocks in order are Body(G1), Body(G2), Footer(C1), Body(G3), Footer(C2), Footer(P). With one source row per block, the region contributes six physical rows with values `G1,G2,C1,G3,C2,P`.
2. **A:** geometry must recursively enter the source/data pair, emit children and then the correct footer while accumulating output rows. **B:** the scheduler emits exactly those six entries; corresponding owner paths are `[0,1,2]`, `[0,1,3]`, `[0,1]`, `[0,4,5]`, `[0,4]`, `[0]`. Geometry only accumulates source block heights.
3. P and C contexts remain bound input parents even when their printed blocks follow children. Source order is not input ancestry. The source tree, internal ancestors and corrected static scopes are already implemented; full nested output is still guarded. The expected schedule and row output require future M3.4 evidence in either approach.

### 7.4. Two horizontal levels with variable cardinality

1. Two Bids and a shared root Criteria collection of size 0/1/3 produce repeated-strip widths 2/4/8 when each parent owns one column. For three criteria, parent headings occupy pre-crop D:G and H:K; after the fixture's crop, C:F and G:J. Product arity is six, or one descriptor at zero criteria. A width-zero own column remains a physical column.
2. **A:** use existing recursive widths/instances and owned merge projection. **B:** use exactly the same code. Its vertical Body entries and owners do not change with criterion count; only their bound Records arity and horizontal placements differ. Empty outer input produces no orphan horizontal children.
3. Accepted tests cover these widths and counts ([GeometryTests:65](../../../MonoReport.Tests/Services/Feature012GeometryTests.cs#L65), [TwoAxisTests:99](../../../MonoReport.Tests/Services/Feature012TwoAxisTests.cs#L99)). Different child collection lengths for individual Bids are deferred by the current complete Cartesian-product contract; neither A nor B admits ragged/per-parent lists. A common Criteria collection with explicit placeholders is the current alternative.

### 7.5. Combined nested vertical and horizontal repetition

1. Two Bids × two Criteria require four records per logical item. Data items are P, C1, C2, Q, C3 with first-record indices 0,4,8,12,16. P owns C1/C2; Q owns C3. Source parents have a one-row header/footer and each child has a two-row Body. The repeated strip has six columns with one own column per bid.
2. Expected logical order is Header(P), Body(C1), Body(C2), Footer(P), Header(Q), Body(C3), Footer(Q): seven block instances and ten region rows. Their owner paths are `[0]`, `[0,4]`, `[0,8]`, `[0]`, `[12]`, `[12,16]`, `[12]`. Both rows of C1 select the same four-record set at input positions 4–7; C2 uses 8–11 and C3 uses 16–19.
3. **A:** generate those seven spans directly with recursive geometry and correct owner lifetimes. **B:** publish those seven entries and combine them with the existing horizontal spans. Header/footer entries share their parent's canonical owner; source cells distinguish their authored content. Only physical placement creates the ten output rows and per-cell intersections.
4. Merge-owner deduplication and current-item selection must work under both approaches. The approved four-intersection integration criterion remains M3.14; this walkthrough does not claim that parsed public nested output or group formulas already work. M3.3 can prove the child Body's two-row unit internally; M3.4 supplies wrapping/order.

### 7.6. Parent and grandparent fields

1. At levels 10/40/90, P's first Name is `P-first`, C's is `C-first`, and G's second tuple is `G-second`. In that G leaf cell, `{Name}/{../Name}/{../../Name}` must produce `G-second/C-first/P-first`. A physical footer location or another tuple's ancestor value must not change that result.
2. **A:** carry a full owner path into the span and let BindInstances choose its last bound item, then call existing RowScope with the existing horizontal tuple. **B:** the same path originates on the logical block and is copied into the span; no field values appear in the schedule. Neither approach replaces RowScope/DataResolver or duplicates static scope projection.
3. Missing/null ancestor values remain distinct and use the first ancestor record's data path; never fall back to another tuple/root. Existing [HierarchyTests:222](../../../MonoReport.Tests/Services/Feature012BindingTests.Hierarchy.cs#L222) already asserts this internally. Completed F1 tests cover footer-first static canonical paths and shared tree identity; public nested rendering remains pending. Header parent fields still use HeaderScope separately.

### 7.7. Incompatible hierarchy, empty collections and uneven siblings

1. For R2's source `10,40,20` and data `10 P,40 X,20 Y`, **A** detects incompatibility while matching source/data owners inside geometry; **B** detects it while constructing Blocks. Neither emits a success that hides X or assigns it to Y. The proposed failure and compatible counterpart are specified in section 6; no policy is adopted by this document.
2. With a compatible two-level source, P has no children and Q has three. For source parent headers/footers and child bodies, expected block order is Header(P), Footer(P), Header(Q), Body(C1), Body(C2), Body(C3), Footer(Q). **A** emits spans directly; **B** emits seven entries with the same bound parent identities. An empty vertical collection contributes zero repeated entries/spans, while static rows survive once.
3.
