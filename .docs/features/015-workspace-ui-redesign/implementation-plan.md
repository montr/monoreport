1. ## 2. Investigation and reuse findings

1. [App.tsx](../../../MonoReport.UI/src/App.tsx) already has Data and Preview regions, example loading, upload/drop validation, original-file downloads, generation, and request/revision guards. Recompose these workflows rather than rebuild the application. `invalidateOperation` currently deletes the result on edits, template changes, and generation attempts. Keep the existing stale-request protection and make only the necessary result-retention change; introduce no additional concurrency infrastructure.
2. [MonacoJsonEditor.tsx](../../../MonoReport.UI/src/components/MonacoJsonEditor.tsx) owns one model and replaces its value from props. Reuse that single-model approach and Monaco's automatic layout. Preserve dataset text and unsaved changes in session records, resetting Undo/Redo on every dataset switch. Do not retain per-dataset models or view-state history. The installed editor exposes Format Document and clipboard commands; no `toggleWordWrap` command was found in its shipped source, so use its public `wordWrap` option through a small editor action when needed. Copy must retain the current whole-dataset behavior when there is no selection.
3. [DocxPreview.tsx](../../../MonoReport.UI/src/components/DocxPreview.tsx) and [XlsxPreview.tsx](../../../MonoReport.UI/src/components/XlsxPreview.tsx) accept File/Blob sources and already isolate stale rendering work. Preserve their integrations, XLSX worker cleanup, selected-cell formula/value bar, loading/failure feedback, worksheet controls, and original-byte downloads. DOCX currently renders pages without an application zoom/page toolbar; do not promise controls absent from that integration or introduce a second viewer engine.
4. [package.json](../../../MonoReport.UI/package.json) pins Ant Design 6.6.8. Its installed `Splitter` supports controlled panel sizes, limits, orientation, collapse, `destroyOnHidden`, and separate `splitBarSize`/`splitTriggerSize` tokens. Stage 2 replaces the former custom `Splitter.tsx`, its pointer handling, and layout CSS variables with [WorkspaceLayout.tsx](../../../MonoReport.UI/src/components/WorkspaceLayout.tsx). Retain the existing desktop/narrow size preferences and approximately 850px stacked-layout breakpoint. The [official Splitter API](https://ant.design/components/splitter/) confirms these public capabilities.
5. The installed native splitter dragger has separator ARIA values but no focus target or arrow-key resizing; its collapse controls support Enter/Space. The Product Owner accepts the native library behavior and defers additional accessibility functionality, including the current custom splitter's arrow-key resizing, as recorded in Section 4.1.
6. `Dropdown.Button` remains exported locally but is deprecated in favor of `Space.Compact` with `Button` and `Dropdown`. Use that supported native composition for Analyze and its arrow, as permitted by the spec's equivalent-control clause. This is an implementation choice, not a new custom split-button component. See the [official implementation](https://github.com/ant-design/ant-design/blob/master/components/dropdown/dropdown-button.tsx) and [Dropdown documentation](https://ant.design/components/dropdown/).
7. [analysis.ts](../../../MonoReport.UI/src/services/analysis.ts) and [types.ts](../../../MonoReport.UI/src/types.ts) already describe `valid`, errors, warnings, recursive requirements, and occurrences. Requirements distinguish only object, array, generic value, and boolean; occurrences contain kind, expression, path, part, and location. There are no scalar number/date/string types or semantic field descriptions. Invalid analysis currently throws `AnalysisFailure`, losing the rest of the parsed response; a minimal client adjustment should preserve that structured payload for display while continuing to reject invalid templates for sample generation. No Analyzer/backend change is needed.
8. [sampleJson.ts](../../../MonoReport.UI/src/services/sampleJson.ts) is a recursive empty-scaffold converter: generic values become empty strings, booleans false, shaped arrays one object, and childless arrays empty. It has no random mode or configurable count. Extend this focused conversion for the approved settings; do not infer richer types or introduce a separate generation pipeline. Proposed limits and semantics require the decision in Section 4.2.
9. [generation.ts](../../../MonoReport.UI/src/services/generation.ts) already validates binary DOCX/XLSX responses, normalizes diagnostics, and preserves safe filenames. Continue generating independently of Analyze. The current binary response path does not supply detailed successful-generation warnings; display actual analysis warnings and operation failures without claiming a new multipart-warning integration.
10. Example manifest validation, atomic template/data loading, and race protection can be reused from App. [examples.json](../../../MonoReport.UI/public/examples.json) supplies DOCX/XLSX grouping and the default example; do not hardcode mockup example names. Current startup always loads that default and has no context restoration.
11. A source search found no production Clear Local Data handler, JSON disk-open/save service, IndexedDB store, or workspace persistence. Existing production storage consists of `monoreport.playground.splitter.desktop` and `monoreport.playground.splitter.mobile`. Clearing therefore needs a narrowly defined implementation, not reuse of an assumed handler or a blanket storage clear.
12. Existing [App tests](../../../MonoReport.UI/src/App.test.tsx) cover API payloads, atomic examples, stale requests, uploads, format switching, and downloads. Several explicitly expect result deletion and generated JSON replacement; update those expectations when the approved behavior changes, while preserving race and byte-integrity checks. Viewer tests remain valuable regression coverage. JSDOM mocks do not establish real viewer, layout, picker, or permission behavior.

## 3. Implementation boundaries

1. Keep workspace records as data: dataset identity, source kind, current text, saved/loaded baseline, optional file handle, and active selection; template identity/source and optional handle; last successful result and minimal freshness state; operation and diagnostic records. Dirty JSON, result freshness, current operation, and last generation outcome are distinct facts. Reuse existing request/revision guards without a new concurrency layer. Keep editor history outside dataset records and reset it on switching.
2. Keep new file, persistence, and sample-conversion business logic in focused service instances with externally supplied browser/API dependencies. Keep React components/hooks responsible for UI composition and lifecycle. Reuse existing service entry points; do not refactor unrelated services just to change their style or introduce a generic state/command/storage framework.
3. Use `Flex`/`Space`, native buttons/icons, grouped dropdown menus, `Radio.Group`/`Radio.Button`, `Splitter.Panel`, `Tabs`, `Modal`, `Form`, `InputNumber`, `Upload.Dragger`, `Empty`, and standard semantic feedback. Show the one active Dataset/Template filenames as non-interactive text, with source tooltips and a truncation-safe grouped dirty indicator. Do not add file selectors. Use existing ConfigProvider and theme tokens; Example filenames use `colorTextTertiary`, Local filenames use `colorText`.
4. Keep the Dataset editor always visible, including when empty; retain Dataset Open, Save, Save As, Format, Word wrap and Copy, but no Dataset Close. Preserve template/result Download and their distinct Close semantics. Keep original file associations, download fallback, unsaved-change safeguards and Example behavior.
5. One active Dataset and one active Template belong to the workspace; the last successful Result is separate. Selecting an Example loads its Dataset and Template; subsequently opening a Local file replaces only that resource. Do not show the Example title. Preserve bounded file-handle restoration without recent-file selectors.
6. Confine changes to the UI and this active Feature's implementation records. No new dependencies, backend contracts, build/CI changes, persistent content library, logging backend, cloud storage, Projects, or viewer replacement are planned.

## 4. Technical limitations and approval decisions

### 4.1. Native splitter accessibility — approved decision

1. **Approved by the Product Owner:** use the native Ant Design Splitter as provided. Add no custom keyboard resizing, focusable dragger button, accessibility adapter, or replacement pointer handling.
2. Defer accessibility functionality beyond what the existing libraries provide. Preserve their built-in behavior and visible focus where available; native splitter arrow-key resizing is not an acceptance requirement. This decision needs no further approval before Stage 2.
3. **Final Stage 2 Product Owner decision (2026-10-29):** use native splitter defaults wherever possible, without application-specific panel minimums, maximums, container measurement, or splitter theme overrides. Enable native collapse/restore for both Data and Document panels and remove redundant Hide panel/Show document commands. Preserve independent desktop/narrow split preferences through native collapse/restore. This supersedes the original panel-bound and application visibility-control choices.

### 4.2. Generate JSON semantics and bounds

1. **Approved by the Product Owner for Stage 4 (2026-10-30):** default count 10, positive integers with no arbitrary per-collection maximum, applied recursively to arrays whose object fields are known. Preserve empty childless arrays because their element shape is unknown. Empty mode retains empty strings/false; Random mode produces sample strings for generic values and random booleans. Neither mode promises realistic numbers, dates, formatter-compatible values, or valid data-dependent XLSX cardinality.
2. **Approved aggregate limit:** 100,000 generated array elements across all nesting levels and sibling collections. Preflight the complete count before allocation; reject exceeding the limit without a partial dataset or changes to existing datasets. Keep this guard internal, not a third modal setting. This decision supersedes the earlier proposed 1–100 count range and 10,000-element limit.
3. Reuse a successful analysis for the same template identity/revision. JSON edits alone do not invalidate template analysis. When analysis is missing, Generate JSON performs it once and includes that work in its measured duration. Invalid analysis cannot produce a dataset. Preserve existing guidance that generated data is a starting point, not semantic validation.

### 4.3. File access and restoration

1. Native open/save pickers and handle permissions have limited browser availability and require a secure context and user activation. Detect actual capabilities instead of assuming a browser brand. Handle persistence does not guarantee persistent permission. See [open picker](https://developer.mozilla.org/en-US/docs/Web/API/Window/showOpenFilePicker), [save picker](https://developer.mozilla.org/en-US/docs/Web/API/Window/showSaveFilePicker), and [permission requests](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemHandle/requestPermission).
2. Current supported path: native picker, original-handle Save, Save As to a selected location, and bounded IndexedDB handle restoration. In browsers without direct saving, keep Save and Save As available through the existing JSON download fallback; do not add a separate Dataset Download action. A file acquired through ordinary upload/drop may have no reusable handle even in a capable browser; preserve its existing association rules and do not claim an overwrite occurred.
3. Store handles and small context metadata only. Proposed routine bound: ten recent JSON handles and ten recent template handles, deduplicated by file identity; trimming remembered entries must not close current in-memory datasets. Store selected example/source identity and active-entry metadata separately from content. No JSON text, template binaries, generated documents, or Output events enter persistent storage.
4. Dirty/generated in-memory content consequently cannot be recovered after a reload; disk restoration reopens current disk bytes. Upload-only files also need reselection. Never silently replace an unrestorable last context with the default example. **Product Owner approval required before Stage 5** for the minimal recovery UI: an Ant Design Alert with a user-initiated Reopen/Grant access action beside the affected context, retaining names and accessible entries. Automatic mount-time permission prompts cannot satisfy user-activation requirements.
5. Where IndexedDB, handle cloning, or permission APIs are unavailable, keep the live session usable and explain the restoration limitation. Missing/deleted files and denied permissions are recoverable states. An asynchronous restore must not overwrite newer user actions.

### 4.4. Clear Local Data scope

1. **Product Owner approval required before Stage 5:** because no clearing handler exists, implement a standard confirmation that removes only the two existing splitter preference keys, the Word wrap preference `monoreport.playground.editor.wordWrap` approved in the final Stage 3 corrections, and the workspace metadata and handle records introduced by this Feature. Inventory the exact new keys/store names during implementation and include them in review evidence. Never call unrestricted `localStorage.clear()`, delete unrelated databases/site storage, or delete source files.
2. Confirmation must explain local preferences/reopen references, session Output history, and any unsaved session work being discarded. **Product Owner decision:** Clear Local Data also clears the current session's Output history. On acceptance, use the existing invalidation mechanisms to cancel pending work, clear owned persistence, current workspace context, and Output, then open the manifest's default example without automatic generation. Cancellation leaves the complete workspace, including Output, unchanged.
3. The fallback labels, bounded recent list, and handle-only policy are already approved in the spec; clearing session Output is also approved. Do not reopen those product decisions. The remaining approval concerns the recovery UI and persistent-storage clearing scope described above.

## 7. Stage 3 — Session datasets, local file actions, and editor commands

**Status: Accepted (2026-10-30)**

### Implementation and verification notes

1. **Review submission (2026-10-29):** implemented under the Product Owner's explicit Stage 3 authorization following Stage 2 acceptance. Stage 4 is unstarted. Generate JSON remains the transitional Data-menu scaffold command; explicit Analyze, settings, complete diagnostics, Output, persistence, and Clear Local Data remain deferred to their approved stages.
2. App now holds multiple session datasets with identity, source kind, text, baseline, and optional reusable handle. Native Select switches without discarding edits; Generate uses the active dataset. Generated scaffolds open as new dirty datasets, including when their text matches an existing dataset. Example loading uses one standard dirty-discard safeguard, replaces only the active dataset after validated assets arrive, and preserves other session datasets. Dirty Close uses the same safeguard; closing the last dataset exposes Empty with Open or Upload. Example names are context labels; original JSON filenames are used for Save As and Download.
3. The injected LocalFiles service detects secure open and save capabilities independently, filters native picker types, reads and validates JSON before selecting it, compares handles by entry identity, and writes exact captured text before closing the writable stream. Native Open adds or activates existing entries without overwriting unsaved session edits. Save writes the current handle or acquires a destination for unbacked data; Save As changes the record's handle/name only after successful writing. A destination already open in another dataset is rejected before writing. Cancellation, unavailable files, denied/revoked access, and write failures preserve current work. Failed writes abort the stream. The saved snapshot becomes the baseline only for its original record, so newer edits or another active dataset remain dirty.
4. Template records retain original File objects and optional handles for Stage 5. Native Open acquires handles; ordinary upload/drop remains a handle-free fallback. Selection, replacement, Close, and reactivation preserve all datasets and the successful result. Closing the active template removes it from the selector and exposes the existing empty state; other opened templates remain selectable. Currentness compares the active dataset identity/text and template File with the last successful generation inputs, using the existing revision/request guards for pending work. Switching back to unchanged inputs is Ready; saving alone does not change freshness.
5. Monaco retains one owned model.
