# Feature 021 — MonoReport Template Authoring Skill + MCP Server

## 1. Status and authority

1. **Status: requirements consolidated; complete Feature/architecture approval pending.** Updated 2026-11-12 after Samples 1–5. This task authorizes documentation only, not implementation or an Implementation Plan.
2. **Product Owner requirements:** enable Codex and OpenCode to create/fix DOCX/XLSX templates, preserving formatting and connected-engine correctness. The current request additionally establishes a portable Skill with reusable scripts and agent references, general `formatters.md`, Fast/Full modes, optional structural descriptions, multiple completed-report inputs, and explicit time/token efficiency goals. Detailed policies below remain proposals where identified.
3. **Approved architecture D1:** host MCP in the existing Service API. Hybrid transport (D2), context/binding (D4/D6), and detailed tooling/mode policies remain recommendations awaiting approval. Experiment success does not approve them. [Architecture](architecture.md) separates existing capabilities, observed findings, proposed decisions, and future integration.
4. The existing [DOCX compatibility contract](../../../docs/docx-template-compatibility.md) and [XLSX compatibility contract](../../../docs/xlsx-template-compatibility.md) remain authoritative. This Feature proposes no engine behavior, syntax, or compatibility changes.

## 2. User outcomes

1. Create a new supported template from a request, optional JSON, and zero, one, or several completed reports from the same report family. An optional natural-language description can identify report structure, dynamic/static fields, independent dimensions, calculations, intended repetition, and empty-case behavior; no formal schema or special authoring language is required.
2. Convert selected content in an existing document into template expressions or supported repeated regions while retaining unrelated content and formatting.
3. Diagnose and fix an existing template using engine diagnostics, authoritative documentation, and actual formatter registrations.
4. Return the editable template, representative test data when appropriate, a generated example when generation succeeds, and a concise statement of changes and verification performed.
5. Explain unsupported requests and unresolved defects. Do not silently remove document features, change supplied JSON semantics, or report success based solely on a readable ZIP or successful analysis.
6. Produce a useful Fast result with essential checks or run Full validation, including on an existing Fast result without unnecessary reauthoring. Report the selected mode, actual dataset used for each result, completed checks, assumptions, and remaining limitations.

## 3. Recommended implementation boundary

1. **D1 — deployment, confirmed:** add an MCP endpoint to the existing Service API. Recommend Streamable HTTP at `/mcp`, sharing the Service's engine services, formatter registrations, generation defaults, and documentation build. Local stdio and a separate adapter executable are outside the first-release scope; see architecture section 3 for alternatives and the proposed remote file contract.
2. **D2 — revised recommendation, Hybrid:** expose exact-build documentation and registered formatter discovery through two MCP tools. Perform analysis, Sample JSON, and generation through the existing REST multipart operations. This replaces the earlier, unapproved five-tool/base64 proposal; it does not change D1. Reuse the existing Sample Generator rather than reconstruct XLSX data from the requirement tree.
3. **D3 — editing:** the Skill coordinates available local document/package tools and uses the connected Service for analysis and generation over REST. Initially support new ordinary templates and targeted edits to compatible existing files. Do not build a general document editor or promise lossless arbitrary Office editing. A dedicated MonoReport editing tool is excluded unless representative authoring trials demonstrate a concrete need and the Product Owner approves that addition.
4. **D4 — server identity:** omit a separate server-info operation. Include engine/build identity, documentation revision, relevant effective settings, and the Service's explicitly configured external REST API base URL in the documentation index response. Use MCP connection metadata for protocol identity without assuming that handshake metadata or connection configuration is visible to the model.
5. **D5 — portable tooling:** one `monoreport` Skill contains reusable inspection, REST transport, and verification scripts plus concise agent-oriented DOCX/XLSX references and `formatters.md`. Prioritize mechanisms demonstrated across the experiments, not wholesale promotion of their source-specific scripts. Runtime/distribution details and the precise initial helper set remain proposed; local execution, network permission, and suitable REST credentials remain prerequisites of Hybrid.
6. Exclude new engine features, custom formatter loading, plugin marketplaces/installers, cloud storage, arbitrary URL fetching, Office automation, formula calculation, rendering infrastructure, UI changes, and compatibility-contract changes. Existing library capabilities do not imply support for every authoring or editing operation.
7. **Future only:** possible reuse in Playground with an AI agent runtime and external model-provider APIs, including OpenCode Inference, is an integration consideration. Provider adapters, credentials, runtime hosting, browser execution, and Playground UI are outside Feature 021 implementation scope.

## 4. MCP and REST integration requirements

1. **Analysis over REST:** use `POST /api/documents/analyze` with the `template` file part. Preserve the returned validity, errors, warnings, requirements, occurrences, and semantic hints. Inspect `valid` even on HTTP 200. Analysis needs no JSON and must not mutate the input.
2. **Generation over REST:** use `POST /api/documents/render` with a `template` file, a `data` text field containing JSON, and optional `culture`. Explicitly request `Accept: multipart/mixed` to obtain the document plus `diagnostics.json` containing format, filename, and full warnings. Preserve structured Problem Details on failure, including available diagnostic locations, formatter/data paths, trace ID, and `limitReached`. Validate the complete response before publishing a separate local output. Effective generation options and engine identity are not existing per-response REST fields; use advertised Service defaults and the requested culture without inventing values or adding REST metadata by default.
3. **Sample JSON over REST:** use `POST /api/documents/sample` with `template` and optional `itemsPerCollection`/`values` text fields. Preserve returned data and warnings, or failure diagnostics. Label generated values as synthetic. Respect existing limits; successful sample creation is not proof that every runtime value or branch works.
4. **Documentation:** retrieve engine-matched source guides/contracts by document/topic identifier. Skill agent references provide compact authoring decisions, recipes, pitfalls, and check selection, rather than duplicate human guides. Keep agent guidance versioned against the documented engine; unknown/mismatched versions require qualification, not fallback to remembered syntax. `formatters.md` covers invocation/binding, culture, scalar/null/missing behavior, literal validation, and XLSX text-output consequences; discover available names/parameters from the connected API/MCP, not a bundled catalog.
5. **Documentation provenance:** identify the loaded engine version and build/revision where available, documentation revision, and relevant defaults/limits. Report unknown identities honestly. A release must bind engine and documentation artifacts at packaging time; an unverified external engine replacement must not retain a false documentation match.
6. **Formatter discovery:** list actual registered string invocation keys and the selected implementation's parameter names, types, required flags, positional target, and optional semantic hint. Same-key replacements, custom-only registrations, and absent optional packages must be represented accurately. Resolve metadata in the operation scope; do not cache scoped formatter instances or create a second registration inventory.
7. **Formatter limits:** existing metadata is structural, not a complete behavioral manual. Do not invent descriptions, defaults, allowed values, examples, or supported input domains for custom formatters. Static built-in documentation does not override a replacement registration. Validate literal constraints through existing analysis and runtime constraints through generation.
8. **Connection-to-REST binding, proposed D6:** select one MCP connection, obtain its advertised external API base URL, and resolve the existing relative operation routes under that base without losing proxy/tenant path prefixes. Do not infer REST by stripping `/mcp`, read untrusted Host/forwarded headers as configuration, or guess localhost. Pin the connection, API base, and REST credential context together. On explicit switching, refresh docs/metadata and binding. Multiple connections must remain separate even when their engine versions match.
9. **File handling:** transmit original file bytes through existing multipart requests and save response bytes locally. Keep binary payloads and large JSON out of model-visible text. No base64 document MCP tool, server artifact store, upload handles, or server fetch-URL mechanism is proposed. Existing request-size limits and normal ASP.NET multipart buffering apply; do not claim the current server never uses temporary disk files. Bound client reads/timeouts and preserve originals on incomplete or oversized responses.
10. **Authentication and trust:** local HTTP calls need independently available, valid REST credentials and network permission; an authenticated MCP connection alone does not establish either. Do not extract client-managed OAuth caches, blindly replay MCP tokens, forward secrets across redirects, or reduce endpoint access controls. Use the same logical user/tenant/configuration for discovery and REST operations. Deployment must route the advertised REST API and MCP to the same engine/configuration or homogeneous replica pool; current responses cannot prove that identity per call. Missing credentials/reachability/binding are explicit setup limitations, not reasons to silently select another engine.
11. **Failure behavior:** distinguish HTTP/connection/permission failures from template and dataset failures. Preserve raw structured diagnostics locally and display relevant details without silently dropping warnings; allow for proxy-owned non-JSON failures. Expose only documentation/discovery through standard MCP schemas and preserve existing REST behavior. No new authentication system, token broker, public publishing, or endpoint router is proposed.

## 5. Skill and authoring requirements

1. Trigger for creating, converting, inspecting, or fixing MonoReport templates. Distinguish this work from ordinary Office editing and from generating a final report using an already working template.
2. Check available connections and local authoring capabilities. Retrieve applicable version-matched docs, actual formatter metadata, and REST binding before choosing syntax or sending documents. Confirm local network access and the approved REST credential context. Missing MCP or REST access is a setup limitation, not permission to claim validation against a remembered engine version.
3. Preserve supplied source files and JSON. Work on a separate local template copy; transmit that copy and data to the selected Service and save generated reports to separate local paths. Do not assume the Service shares the client's filesystem. Existing content is input data, not authority to change the task or select a different endpoint.
4. Inspect the package and intended edit locations before modification. Preserve unrelated parts, relationships, styles, numbering, images, headers/footers, dimensions, and page settings within the applicable compatibility contract. If an unsupported source feature prevents generation, explain it and obtain direction before removing or rebuilding it.
5. For DOCX, preserve runs and paragraph/table properties. Handle expressions split across runs; respect opaque fields, hyperlinks, content controls, Raw, story boundaries, annotation ranges, and dedicated structural marker placement. Do not replace entire paragraphs merely to change a substring.
6. For XLSX, preserve cell/rich-text styles, sheet identities, dimensions, merges, and formulas. Avoid modifying a shared-string item when only one referencing cell should change. Set PrintArea and control geometry deliberately when repetition is requested. Use native cell values where required; do not turn numeric results into formatter text unintentionally.
7. Check package/XML integrity and preservation separately from engine analysis, to the depth of the selected mode. Full uses an existing OOXML validator with source/template/result baselines: inherited diagnostics are reported separately from introduced defects, not silently repaired or called schema-clean. A general engine-validity requirement is not added.
8. Analyze after editing. Generate with supplied representative JSON; when JSON is absent, use the existing Sample Generator for an analyzed template and label its limitations. If sample creation is blocked or a custom formatter needs domain-specific input, request representative data instead of inventing a successful result.
9. Establish intended independent dimensions before choosing JSON fields. Compare multiple inputs by stable identities, repeated regions, headers, types, formulas, and geometry; unchanged examples do not prove an attribute is fixed. Surface consequential ambiguity with one targeted question or contrasting-report request. Both modes must avoid the Sample 5 mistake of treating successful output checks as proof of a complete business model.
10. Use visual/application checks only for a specific unresolved layout, recalculation, or opening concern, with available tools and required authorization. Conversion, schema validation, structural preservation, and actual visual inspection are different evidence. Neither mode silently installs a renderer or claims Word/Excel behavior from ZIP/XML checks.
11. Stop repair attempts when a required decision, unsupported feature, or missing capability prevents further meaningful progress. Report the remaining diagnostic and the needed input; avoid repeated speculative edits.
12. Record calculation ownership, rounding, aggregation order, and currency assumptions. DOCX totals are supplied data unless otherwise supported; XLSX source text-numbers, native numbers, formulas, and number formats must remain distinct. Changing numeric semantics or subtotal meaning requires explicit intent.
13. For XLSX, inventory supplier-only versus independently repeated criterion columns, hidden/styled blanks, complete horizontal block markers, contiguous vertical control runs, merges, PrintArea, and formula ownership. Verify source-to-template edits separately from original-data reconstruction and changed-data output. Empty children may invalidate retained subtotal targets; report this template-specific boundary rather than invent dummy data or a universal nonempty-group rule.

### 5.1. Fast and Full modes — requested capability; proposed check policy

| Mode | Required result/check boundary | Deferred or conditional work |
|---|---|---|
| Fast | Resolve material model ambiguity; bounded package/feature inspection; safe separate output; Analyze and representative generation with full diagnostics; verify essential values, types, repetition counts, and affected geometry/formula targets. Compare source/original-data reconstruction where source data is recoverable, using targeted checks. | Broad changed/empty-case matrices, exhaustive part/property diffs, and SDK baseline validation belong to Full unless a concrete risk requires them earlier. Successful HTTP/ZIP extraction alone is not a verified Fast result. |
| Full | Fast essentials plus independent-axis changes/reordering, selected growth/contraction/empty cases, expected arithmetic/binding, source/template/result structural and property comparisons, and OOXML diagnostic baselines. Choose cases for distinct risks; do not repeat redundant variants. | Rendering/application checks remain risk-based, and formula-reference/type checks do not claim Excel recalculation. Missing required validation capability yields an explicitly incomplete Full result. |

1. Full can validate a saved Fast template/data/result set without altering it. Reuse evidence only when artifact hashes, actual datasets, engine context, and check coverage still match; run additional generations only for missing scenarios. A repair is a separate requested action, not an implicit part of validation.
2. Mode selection/default and automatic escalation remain D7 approval questions. A Fast label never waives data/formatting integrity, exposes secrets, or resolves unknown business intent by assumption. Link outputs to actual datasets and list completed/deferred checks in either mode.
3. **Efficiency requirement:** measure end-to-end elapsed time, time to first meaningfully verified output, additional Full-validation time, attempts/retries, and available token/tool-output metrics. Record measurement boundaries and waits; do not equate HTTP latency with total time, invent token totals, or claim savings from incomparable samples. Use bounded inspection, progressive documentation reads, cached baselines, batched validator execution, and concise evidence-linked reports. No numeric SLA is approved.

## 6. Proposed acceptance criteria

1. **Client portability:** the same Skill package is discovered and used in supported Codex and OpenCode versions. Each client completes at least one new-template and one existing-template repair scenario for each format using MCP documentation/discovery and REST document operations. Record client versions, local runtime/HTTP prerequisites, permitted network access, and authentication arrangement.
2. **New DOCX:** from a description and JSON, create a formatted document with scalar fields, a supported table-row loop, and a Boolean condition; analysis succeeds and generated text, row counts, and branch behavior match the data, including an empty collection and both Boolean values.
3. **DOCX repair/preservation:** repair a split-run expression in an existing styled document containing a table, header/footer, numbering, and an image. Preserve unrelated parts and relevant run/paragraph properties. Confirm generated values and retained content; record visual results separately.
4. **New XLSX:** verify ordinary native numeric cells/A1 formulas and a repeating sheet with deliberate PrintArea/control geometry. Where suppliers and criteria are intended to vary independently, change criterion count and order while suppliers/items stay fixed, then vary suppliers independently. Distinct intersection values must verify positional mapping, hidden parent-only columns, merge ownership, and subtotal references through data alone; Sample 5 did not establish this capability.
5. **XLSX repair/preservation:** fix a template expression in a styled rich-text/shared-string cell without changing another cell sharing its original text. Retain unrelated styles, dimensions, merges, and supported formulas. Verify both the edited template and generated output.
6. **Existing-engine parity:** representative success and rejection cases return the same substantive analysis/generation/sample results through the Skill's REST workflow and direct library calls under equivalent registrations/options. Preserve all generation warnings through negotiated multipart output. Include HTTP 200 analysis with `valid: false` and a structurally valid template that fails with incompatible JSON. No second MCP generation path or independent defaults appear.
7. **Formatter configuration:** test a custom key, a replacement for a built-in key with different parameters, an absent optional formatter, and a scoped formatter dependency. Discovery agrees with analysis and generation; no absent formatter is advertised, no replaced built-in rules are assumed, and scope disposal remains correct.
8. **Documentation matching:** run two identifiable builds/document bundles and prove each serves its own documentation. Detect or explicitly report an unverifiable bundle/engine match. Show actual defaults and optional formatter availability without treating static examples as configuration discovery.
9. **Connection isolation/proxy binding:** connect two deployments with different formatter configurations, including two instances sharing one origin under different prefixes. Include an externally rewritten MCP path and API prefix. The selected MCP advertises the correct REST base; uploads and metadata stay in that logical deployment/user/tenant. Switching reloads binding/docs/metadata. Missing or mismatched binding, unavailable API credentials, and unexpected redirects stop uploads. Deployment configuration/tests must establish engine equivalence; matching formatter lists alone are not proof.
10. **Unsupported content:** DOCX tracked revisions and XLSX charts/Excel Tables produce actionable diagnostics and leave originals intact. The Skill proposes the needed change without silently discarding content or weakening contracts.
11. **Artifacts/errors:** malformed JSON/packages, oversized or interrupted transfers, malformed/truncated multipart, proxy HTML errors, missing diagnostics, and client output collisions fail safely. Upload and save representative binary documents in both clients without manual payload transcription, preserving exact attachment bytes. Validate warning metadata and MIME framing before publishing output. Failed generation returns no document; incomplete transfer publishes no new report. Preserve warnings and diagnostic locations. Existing REST and deployment access controls remain effective.
12. **Honest verification:** distinguish requested mode, actual check coverage, schema baseline, preservation, semantic completeness, and application evidence. Reproduce Sample 4's inherited-diagnostic classification and Sample 5's empty-child formula rejection without changing engine contracts. Optional rendering/recalculation verifies only the selected concern; report absent Word/Excel evidence explicitly.
13. **No scope expansion:** no new parser, second Sample Generator, formatter registry, dynamic plugin loader, general editing framework, server routing layer, or duplicated template manual is introduced. Acceptance failures requiring broader editing capabilities return to the Product Owner for scope review.
14. **Descriptions and multiple reports:** accept an optional structural description and contrasting completed reports; record observed differences, declared invariants, unresolved assumptions, and expected variation tests before authoring. Conflicting examples/descriptions require clarification. A single report with two unchanged criteria cannot establish fixed criteria.
15. **Mode continuation and efficiency:** produce Fast and run Full against that saved result without reauthoring; verify unchanged inputs and provenance, missing-coverage execution, and honest incomplete outcomes. Collect comparable timing/token evidence for both paths; unknown tokens remain unknown and no unmeasured savings claim is accepted.
16. **Agent resources:** verify the same Skill/scripts and task-focused references work in Codex/OpenCode without repository implementation access. `formatters.md` provides general rules; connected custom/replaced/absent registrations control actual usage. Inspection handles namespaces, DOCX run/style classes, XLSX cell types/shared strings/geometry; experiment-specific regexes and blanket brace/external-link checks are not generic guarantees.

## 7. Approval questions

1. **D1 — resolved:** the Product Owner selected an MCP endpoint in the existing Service API. Streamable HTTP at `/mcp` remains proposed. This decision does not require binary document operations to use MCP, and no local stdio host is proposed.
2. **D2 — revised:** approve Hybrid: two MCP tools for documentation/formatter discovery, and existing REST operations for analysis, Sample JSON, and generation? MCP-only remains an evaluated alternative, not a second initial implementation.
3. **D3:** approve the initial boundary of new ordinary templates and targeted compatible-file edits, with preservation checks and no general editing tool? Broader transformations require evidence and separately approved scope.
4. **D4–D5:** approve the proposed context envelope and initial reusable script scope/priorities? Portable scripts and agent references are requested requirements; exact packaging/runtime choices remain routine within approved scope. A dedicated editor/DSL is not justified by the five trials.
5. **D6:** approve deployment-configured external REST binding and a first-release prerequisite of local REST network access plus independently provisioned REST credentials where needed? MCP-only OAuth/tunnel deployments without a usable local REST path would remain unsupported until separately addressed.
6. **D7:** approve the proposed Fast/Full check boundaries, default mode, and escalation policy? The two modes and Full-on-Fast continuation are requested requirements; no mode default or numeric performance budget was established by the experiments.
7. Approval of the proposal does not authorize implementation or an Implementation Plan unless the Product Owner explicitly requests that next step. Future Playground/provider integration is not included in such approval.
