# Sample 5 — XLSX template authoring experiment

1. **Outcome:** authored a reusable tender template with hierarchical lot/item rows and horizontally repeated supplier blocks. The initial authored workbook passed analysis and generation without template redesign. Five datasets generated without warnings; a sixth demonstrated the supported formula boundary. All work is confined to this experiment directory. No production code, Feature decisions, compatibility contracts, previous experiments, existing templates, test fixtures, Git state, agents, or Office rendering were used or changed, except the explicitly recorded early source inspections below.

2. **Deliverables:** [template](output/skill-sample-5.template.xlsx), [extracted original JSON](output/skill-sample-5.json), and [modified-data result](output/skill-sample-5.result.xlsx). The result uses [modified data](evidence/modified-data.json), rather than the original-data JSON. [Original reconstruction](evidence/original.result.xlsx) is retained separately. Scripts are experiment-specific authoring, REST response extraction, and independent verification; no editor or DSL was created.

3. **Inferred model:** a root title; ordered suppliers; and a flat hierarchical `Items` collection carrying `$level` and contiguous `$path` groups. Level 1 supplies a lot name and its subtotal footer; level 2 supplies item name, quantity, unit price, and lead days. Every logical lot/item has one record per supplier in supplier order. With no suppliers, one descriptor record preserves each logical row. Unit price and lead days are fixed business criteria, not an inferred variable dimension. Supplier repetition includes all three source columns: hidden item name, price, and lead days. The trailing blank styled column and the closing note remain outside this block.

4. **Authoring:** preserved the source package and used targeted DOM edits only in `xl/workbook.xml` and `xl/worksheets/sheet1.xml`. Reduced the two suppliers and two items to one supplier/item seed; added top and left controls outside PrintArea `Tender!B2:G10`. Three adjacent `$h(1)` controls define the supplier block. One contiguous level-1/level-2/level-1 control run defines lot header, detail, and subtotal. Relative parent paths generate the item/lot label. The authored subtotal ranges cover the single detail seed and expand with its generated rows. [Initial-attempt record](evidence/initial-attempt.json) records the independent design.

5. **Source value semantics:** quantities, prices, and lead days are source inline strings, including `2.00` and `1,200.00`; extracted JSON deliberately preserves their types and exact text. Original-data generation reproduces all text values and formulas. Excel SUM over these source text cells ignores their values; treating the source as numeric would silently change behavior. The modified dataset deliberately supplies numeric prices and lead days, which generate native Excel numbers using the existing price/lead number format. Quantities remain strings because their source style is General; no unrequested number-format change was made. Subtotals retain the source's simple column sums, including lead-day sums; they are not quantity-weighted costs.

6. **Original reconstruction:** all 61 source cells match their reconstructed coordinates, values/types, formula text, and style indices. All row attributes, column widths/styles/hidden zero-width columns, merges, sheet views/selections, sheet format defaults, margins, landscape setup, dimensions, and PrintArea match. Both supplier merges return to `C3:E3` and `F3:H3`. [Independent verification](evidence/verification.json) and [source inventory](evidence/source-inventory.json) contain detailed evidence.

7. **Changed cardinalities:** the published modified result has three suppliers and two lots with three and one items. Its geometry is `A1:L14`, with supplier merges `C3:E3`, `F3:H3`, and `I3:K3`. Devices subtotal formulas target only rows 6–8; Furniture subtotal formulas target only row 11. Twelve subtotal formulas are independently checked, including numeric operand types, exact references, operand existence, and expected sums. Devices price sums are 330, 310, and 354; Furniture price sums are 400, 380, and 425. A separate one-supplier dataset verifies contraction to `A1:F10`.

8. **Empty collections:** empty `Items` generates `A1:I6`, retaining supplier headings and the note while removing all lot/detail/subtotal rows. Empty suppliers generate `A1:C10`, retaining ordinary item/quantity rows and lot labels while removing supplier columns, their merges, and formulas. Both succeed with zero warnings. A nonempty lot with no child items is rejected with HTTP 422, `template.xlsx_unsafe_formula`: the subtotal's seed range has no retained target. Full errors and locations are in [empty-lot evidence](evidence/empty-lot-error.json). The final template preserves its formulas and exposes this limitation; it does not substitute constants, remove totals, or add dummy items. Analysis alone does not detect this data-dependent failure.

9. **Package and worksheet integrity:** every ZIP entry passes CRC and every XML/relationship part parses. Package entry sets are unchanged. All seven unrelated parts remain byte-identical to the source in the template and every successful result: package relationships, workbook relationships, styles, theme, core properties, application properties, and content types. Fonts, borders, fills, and number-format definitions therefore remain intact. Generated cells, row attributes, column properties, merges, formulas, PrintArea, dimensions, footer position, and style ownership are checked against independently mapped source geometry. Controls and placeholders are absent from results; formula caches are absent and recalculation is requested. See [preservation evidence](evidence/package-preservation.json) and [artifact hashes](evidence/artifact-hashes.json).

10. **Validation baseline:** DocumentFormat.OpenXml 3.5.1 reports zero validation errors for the source, template, and all five successful generated workbooks. There are no pre-existing schema errors and no newly introduced schema errors. This is separate from the source's valid but potentially surprising text-number/SUM semantics. [Raw validation](evidence/openxml-validation.json) and [baseline comparison](evidence/openxml-baseline-comparison.json) retain the evidence. The small validator uses the installed package and validates all seven files in one invocation.

11. **API and provenance:** used the supplied `http://localhost:3000/`, live OpenAPI, `POST /api/documents/analyze`, and `POST /api/documents/render` with `Accept: multipart/mixed`. The analyzer returned `valid: true`, no errors, and no warnings. HTTP responses, binary MIME bodies, full diagnostics, and request durations are retained under `evidence/`; [API summary](evidence/api-cases.json) records all six cases. No formatter was required. Engine build identity and an exact match between repository documentation and the loaded server are unknown; REST does not attest them.

12. **Experimental validity and source inspection:** no previous experiment solutions, existing templates, or test fixtures were inspected at any stage. Before the later instruction restricting further implementation inspection, planner files were read to determine contiguous multi-column geometry markers and lot header/detail/footer control ownership: `XlsxTemplatePlanner.Controls.cs`, `.Structure.cs`, `.Vertical.cs`, and `.Hierarchy.cs`. The published guide demonstrates these concepts but leaves the complete multi-column marker and contiguous-run rules implicit. `DocumentEndpoints.cs` and route matches in `Program.cs` were also inspected for multipart transport; this was avoidable using Feature 021 guidance and live OpenAPI. Project files were read to identify an installed validator dependency. No implementation inspection followed the clarification. [Inspection provenance](evidence/inspection-provenance.json) identifies each question, file, missing documentation detail, and answer. These early reads limit the experiment's independence from implementation knowledge; the trial was continued without restarting.

13. **Timing and efficiency:** measured wall time from the first tool batch: first independently verified output **268.526 seconds (4:29)**; completed verification, including SDK baseline comparison, **340.222 seconds (5:40)**. [Timings](evidence/timings.json) records task completion separately, and [API summary](evidence/api-cases.json) records individual request durations of approximately 11–20 ms. Exact token usage is unavailable and is not estimated. Initial broad documentation/status output was unnecessarily large. One authoring-script bracket error was corrected before template creation. One MIME extraction error included the HTTP status line as a MIME header; it was corrected and the cases completed. The template itself required no corrective revision. Local API access required sandbox escalation; the server was not restarted or reconfigured.

14. **Unverified behavior and limits:** no spreadsheet application was launched, so visual appearance, pagination, printing, actual Excel recalculation, and application opening are unverified. Exact geometry/style preservation and independent SUM expectations provide evidence without claiming rendered fidelity or calculated caches. Arbitrary Unicode/long labels may change layout; no render concern specific to the supplied data required visual tooling. Cross-sheet references, defined names other than PrintArea, dynamic criteria, and unsupported workbook features are absent from this source and were not invented or tested. No discrepancy requiring a compatibility-contract change was found.

15. **Concrete Skill/tooling lessons:** teach complete supplier-block geometry explicitly, including a marker in every repeated column and hidden-column ownership. Document contiguous vertical header/detail/footer controls and the positional tuple count, distinguishing repeated columns from repeated tuples. Inspect source scalar types before numerical coercion. Preserve namespaces and unrelated package bytes when editing, then verify original reconstruction before expanding cases. Reuse a narrow, tested MIME response helper that excludes the HTTP status line, checks content types and part count, and retains structured failures. Validate source and outputs together to distinguish inherited OOXML issues. Offer empty-child subtotal rejection as a concrete boundary; a general promise of empty-collection support would be misleading. These are recommendations for future Skill guidance and tooling, not changes to Feature architecture or production documentation.
