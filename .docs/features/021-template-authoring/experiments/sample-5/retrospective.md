# Sample 5 retrospective

1. **Finding and model choice — observed.** The template varies suppliers, lots, and items, but fixes comparison criteria as `Price` and `LeadDays`. It has no criteria collection or second horizontal level. The [initial attempt](evidence/initial-attempt.json) explicitly records that choice. Separate labels, units, and subtotal columns made a fixed supplier record plausible; repeating complete three-column blocks also preserved hidden item-name columns simply. However, one completed report establishes the current shape, not which dimensions may vary. There was no user statement establishing fixed criteria. The earlier findings' description of them as “fixed business criteria” overstated the evidence. Preservation succeeded; completeness of the inferred reusable model was not established.

2. **Recognition opportunity — assessment.** Initial inspection already showed two header tiers: merged supplier headings and repeated criterion labels beneath them. That should have produced two candidate interpretations before authoring: a supplier record with fixed attributes, or supplier × criterion dimensions. Reading the guide's combined example was a second opportunity. A short dimension inventory should ask: can suppliers and criteria independently change count, identity, or order; are criteria shared across suppliers; which columns belong only to suppliers; and how do totals behave for each criterion? A description such as “the same selected criteria appear under every supplier, and the criterion list varies by report” would resolve the central ambiguity. The original request's broad cardinality requirement did not explicitly answer it; I should have surfaced the consequential assumption.

3. **Multiple reports — hypothesis.** Completed reports from the same report family could resolve the fixed-count ambiguity if one changes supplier count while retaining criteria, and another changes criterion count while retaining suppliers. Stable supplier/item identities and a criterion reorder would make correspondence clearer. Two reports where both counts change together provide weaker evidence; several reports with unchanged criteria cannot prove criteria are fixed. Examples still do not establish every allowed future variation or empty-case policy. Targeted examples plus a brief statement of invariants would be stronger than more arbitrary samples.

4. **Documentation and implementation inspection — observed.** The [guide](../../../../../docs/xlsx-template-guide.md#combining-both-directions) explicitly describes suppliers × criteria, `$h(1)`/`$h(2)`, separate header collections, and positional product records. The [contract](../../../../../docs/xlsx-template-compatibility.md) supports nested horizontal blocks, parent-only columns, combined expansion, and safely owned merges. Documentation was sufficient to identify the missing dimension; this was primarily a modeling failure. Early source reads resolved less explicit authoring details: `XlsxTemplatePlanner.Controls.cs`/`.Structure.cs` showed markers in every adjacent column of a multi-column block; `.Vertical.cs`/`.Hierarchy.cs` clarified contiguous header/detail/footer controls and ancestry. [Provenance](evidence/inspection-provenance.json) records these reads. API endpoint inspection was avoidable using existing REST guidance and live OpenAPI; project metadata identified the validator dependency. No implementation was inspected after the restriction. The documented capabilities justify considering a nested design, but do not verify that a particular replacement preserves this workbook's hidden columns, merges, formulas, and empty cases. No replacement was tested here.

5. **Why verification passed — observed.** Original reconstruction, three-supplier/two-lot expansion, one-supplier contraction, empty items, empty suppliers, formatting/package checks, and OOXML validation all passed while criterion count remained two. The verifier independently checked generated geometry and values, but encoded the same semantic assumption: three columns per supplier and fixed `Price`/`LeadDays` fields. Analyzer validity and zero schema errors cannot discover omitted business variability. **Missing acceptance test:** keep suppliers and items fixed; change criteria from two to three, then to one, and reorder them through data alone. Require matching headers, distinct sentinel values at every supplier–criterion intersection, preserved supplier-only hidden columns, correct merges, and valid subtotal references without editing the template. The current model cannot express that test. Define the expected outcome before implementation; assess empty criteria separately under the contract.

6. **Empty-lot failure — observed and bounded.** The authoring decision retained a parent subtotal referencing the repeated child seed, `SUM(E7:E7)`/`SUM(F7:F7)`. A lot descriptor without children removes those targets while keeping the subtotal. The API correctly rejected the removed references with HTTP 422, `template.xlsx_unsafe_formula`, consistent with the contract. This is a formula-relocation boundary, not a general inability to represent empty collections, and not caused by the missing criterion dimension. “Each retained lot must contain an item” is a constraint of this authored template, not an established business rule or universal engine input constraint. Original text-number semantics are a separate issue. No verified empty-lot alternative exists in this trial; changing totals or excluding empty lots would require explicit intended behavior and verification.

7. **Time and avoidable work — measured checkpoints, approximate attribution.** [Timings](evidence/timings.json) record 407.428 seconds; the execution trace supports this breakdown. Intervals include authoring/thinking and tool overhead, not isolated CPU measurements.

   | Elapsed interval | Work visible in trace |

   The six retained render requests total **0.094 s**; this excludes earlier attempts and analysis. Restore reports **52 ms**; the 71-second validation interval must not be attributed wholly to restore/build. Avoidable work included oversized/truncated reads, repeat documentation retrieval, unnecessary API implementation inspection, script syntax/MIME repairs, and a lengthy findings document. Preservation verification was valuable; generating additional cases before testing every candidate independent dimension gave misplaced confidence. Exact token usage and savings from proposed improvements are unknown.

8. **Prioritized improvements — recommendations, not implemented.** First, require a compact dimension inventory before choosing JSON properties: evidence, candidate independent axes, fixed attributes, supplier-only columns, unresolved assumptions, and one acceptance scenario per axis. Ask one targeted question or request contrasting reports when evidence cannot settle a material choice. Second, extend agent guidance around the existing nested-horizontal example with explicit marker geometry, hidden parent-only column ownership, tuple ordering/counts, merge/formula constraints, and empty-child boundaries; more generic examples would have lower value. Third, provide a small reusable package inventory/comparison utility, reliable HTTP/MIME helper, and batched baseline validator. These tools should expose evidence and check selected invariants, without deciding business dimensions or introducing an editor/DSL. Finally, keep output bounded, read relevant documentation sections once, parallelize independent read-only inspection, compile-check authoring scripts before API calls, and retain detailed evidence outside concise findings. User guidance should request permitted variations and empty-group/criterion-total policies alongside the report. The highest priority is a correct model before faster mechanics.
