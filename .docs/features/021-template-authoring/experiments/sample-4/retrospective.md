# Sample 4 retrospective — XLSX authoring

1. **Hierarchy inference was straightforward; choosing reusable geometry required care.** Observed: ten merged department headings alternate with ten identically styled employee rows per department. Department, Name, and Position were the only dynamic fields. The fixed ten-employee pattern was source data, not a template constraint: [verification](evidence/verification.json) passed department sizes 2, 0, and 12, plus an eleventh department. The authoring decision was to retain one department row and one employee row while preserving the static header and blank margins. No ambiguous hierarchy was encountered; this does not establish feasibility for irregular or deeper reports.

2. **Repetition controls and PrintArea must be planned together.** Observed in [author.py](author.py): $level(1).Data and $level(2).Data select department and employee layouts from a flat, ordered array. An empty department is a parent record with no children; an empty array removes both repeated layouts. PrintArea is a cropping boundary, so using the existing blank column A for controls would have removed the report's left margin. Instead, report columns moved right, controls occupied A3/A4, and PrintArea became B1:E4. Cell references, column definitions, dimensions, selection, and the department merge moved together. C3:E3 then expanded into B:D merges in output. Styled empty merge cells and row attributes were retained, as were margins, paper size, orientation, and view settings. The original-data worksheet was even byte-identical to the input; seven unrelated package parts were unchanged in every case.

3. **Failures belonged to inspection and verification setup, not the template.** Observed: the initial template passed [Analyzer](evidence/analyze.json) and every generation case without warnings or template revision. An inspection search incorrectly assumed an XML prefix; the worksheet used a default namespace. Printing all employee rows also consumed output unnecessarily. Local API access and a malformed curl data argument caused request failures, recorded in [authoring failures](evidence/authoring-failures.json). Validator compilation required correcting an unavailable NuGet audit lookup. Separately, [SDK validation](evidence/openxml-baseline-comparison.json) found two pre-existing source defects: horizontalDpi and verticalDpi were zero. Input, template, and all results had identical diagnostics, with none introduced. Preserving source settings was deliberate; successful generation did not establish schema cleanliness.

4. **About 2m 15s followed the first verified result.** Observed [timestamps](evidence/timings.json), elapsed from experiment start:

   | Checkpoint | Elapsed | Work since previous checkpoint |
   |---|---:|---|
   | First verified original-data result | 2m 36.629s | Value, repetition, geometry, and preservation checks |
   | All five data cases verified | 2m 53.021s | 16.392s: modified, expanded, empty, and empty-child cases |
   | SDK validation complete | 4m 06.408s | 73.387s: validator preparation/build, retry, validation, source diagnostic review, and package/hash evidence |
   | Evidence complete | 4m 51.438s | 45.030s: findings, explicit diagnostic baseline comparison, full workbook equivalence check, and cleanup |

   These intervals do not isolate execution, reasoning, or writing time. Hypothesis: an already available XLSX validator and compact preservation report could shorten the latter stages without removing checks. No measured speedup exists. The empty-child case adds little beyond the modified case's empty department; future coverage could combine those checks while retaining whole-array emptiness and growth coverage.

5. **Prioritize XLSX-aware inspection and comparison in reusable Skills.** Proposed, not implemented: instructions should explain level-ordered records, empty-group representation, control placement outside PrintArea, and the distinction between Analyzer success and data-dependent geometry. A bounded inspector should resolve sheet relationships and XML namespaces, summarize repeated row/style patterns, show representative rows, and inventory merges, defined names, print settings, panes, breaks, formulas, and unsupported structures. It should handle inline/shared strings and native cell types; this sample's extractor handles inline text only. Verification tools should compare values/types, styled blanks, row/column properties, merge ownership and ranges, PrintArea, selections, package parts, and source-versus-result SDK diagnostics. Keep source baselines loaded once rather than reopening them for each case. The successful narrow edits were sample-specific regex operations, not evidence that arbitrary XLSX coordinate changes are safe. No general editor is justified by this experiment.

6. **Sample 5 should target the untested spreadsheet behavior.** Proposed priority, conditional on its input: horizontal or combined repetition with positional $path binding; formulas whose ranges expand or disappear; native numbers, dates, and number formats; multirow blocks and merges spanning repeated boundaries; and multiple sheets with cross-sheet references or defined names. Shared strings and richer text also remain outside this extractor's demonstrated coverage. Panes, manual breaks, and Print Titles need compatibility inspection before choosing repetition. Excel opening, recalculation, pagination, and visual rendering remain untested; examine them only for a specific unresolved concern and with required authorization. Sample 4's XML equivalence supports structural preservation, not application-level layout or repair-free opening.
