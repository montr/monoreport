# Sample 1 authoring retrospective

## 1. Evidence and conclusion

1. Reviewed the authoring conversation/tool trace, [findings](findings.md), scripts, HTTP evidence, preservation results, schema validation, and preview comparison. **Observation** below means demonstrated by that execution or its artifacts; **proposal** means an improvement whose benefit has not yet been measured. This retrospective adds no implementation or architecture decision.
2. The first template worked without repair. Most avoidable work concerned discovery output, verification setup, and preview handling rather than expression syntax or OOXML editing. The strongest improvements belong in Skill instructions and small local helpers; this trial does not justify a DSL, custom editor, or engine change.

## 2. What worked and what remained ambiguous

1. **Document understanding — observation:** the initial inspection printed body paragraphs and table cells, exposing one eight-column table with a header and three analogous material records. Formatting comparisons subsequently confirmed the rows shared a suitable prototype. Column headings supplied the JSON field meanings. Project/contractor details stayed static; count, aggregate, and amount-in-words became dynamic because they depend on the materials. See [extraction and mapping](author.py#L20) and [preservation results](evidence/verification.json).
2. **Ambiguity — observation:** the request did not supply a schema or say whether summaries should be computed, supplied, or left literal. Supplying them was a reasonable conservative choice, but it creates caller obligations. Per-row currency became dynamic while summary USD stayed static; the result is scoped to the original project's USD estimate. This assumption was communicated and documented, without asking an unnecessary clarification question. The [representative JSON](output/skill-sample-1.json) has three items, whereas the delivered result uses [two-materials.json](evidence/two-materials.json); linking each generated artifact to its actual input is essential.
3. **OOXML — observation:** no editing failure occurred. A source-specific patch replaced known text nodes and the contiguous material region, cloned formatted cells for marker/data rows, and copied unrelated entries. This avoided whole-document XML normalization. All five source file parts were byte-identical after generation with original data; reduced/empty results changed only the main document. [Authoring](author.py#L45) and [verification](evidence/verification.json) support those preservation claims.
4. **Boundary — observation:** this was a five-part package with no difficult annotations, merges, images, other stories, or split-run values. The regex assumes literal single-line row markup, and summary replacements require globally unique exact text. Those assumptions succeeded here; they are not reusable editing guarantees. Harder documents require structural selection and their applicable compatibility checks, not broader regexes.
5. **Documentation — observation:** the [guide's Loops section](../../../../../docs/docx-template-guide.md#loops) directly answered dedicated marker-row placement, removal, header placement, and empty collections. Formatter/culture guidance enabled ISO dates and English numeric output; the [compatibility contract](../../../../../docs/docx-template-compatibility.md) defined the hazards to inspect. No syntax gap blocked authoring. REST multipart details and endpoint discovery came from Feature research, API source, and live OpenAPI rather than the Word-oriented guide. A Skill reference can point to those sources without duplicating the template manual.

## 4. REST and verification: value versus overhead

1. **REST count — observation:** seven successful HTTP calls to MonoReport occurred: two OpenAPI GETs, one formatter GET, one Analyze POST, and three Render POSTs. The first OpenAPI response was printed/truncated; the second saved it. Six would have supplied the same evidence by saving discovery once. There was also one failed sandboxed root request. No Analyze/Render request failed or needed retry; no Sample JSON or formatter-execution call was necessary.
2. **Response handling — observation:** Analyze was checked for `valid`, errors, warnings, requirements, and occurrences. Generation requested multipart diagnostics; Python's standard MIME parser extracted one DOCX and one diagnostics part and checked framing/ZIP readability before publication. All warnings arrays were empty. A narrow transport helper would remove repeated curl/MIME assembly while retaining full responses locally; no new API format is needed.
3. **Actual defect detection — observation:** the failed preservation assertion caught an error in the verification harness. No ZIP, schema, field, repetition, or formatting defect was discovered in the template. Passing safeguards should not be described as having caught document corruption.
4. **High-value safeguards:** field-by-field checks and row counts for 3, 2, and 0 records establish behavior beyond Analyze. Part comparison and exact original-data reconstruction strongly support preservation. Decimal arithmetic checks support the inferred dataset. Five zero-error SDK validations establish a separate structural check; source/result previews establish limited visual evidence. See [verification](evidence/verification.json), [SDK results](evidence/openxml-validation.json), and [preview comparison](evidence/preview/comparison.json). None establishes Microsoft Word appearance or absence of Word repair prompts.
5. **Potential excess — assessment:** custom OPC/content-type/relationship checks overlapped with SDK validation for this tiny package. Keep inexpensive part/CRC checks, targeted value/property assertions, and SDK validation; avoid rebuilding a parallel general validator. Three PDF exports were defensible preservation evidence in a first experiment, but routine workflows can avoid rendering a second package with identical part contents unless renderer reproducibility is itself under test. Whole-package-byte equality must remain an optional strong result, not a universal engine promise.
6. **Do not reuse sample assumptions as generic checks:** [verify.py](verify.py#L37) parses every file part as XML, rejects external relationships, and assumes final section properties; its later blanket brace check would reject legitimate literal content. Formatting comparison also ignores `xml:space`, so it alone cannot prove whitespace preservation. These did not invalidate this sample's exact reconstruction, but a reusable checker must distinguish XML/binary parts, preserve supported external links and literals, and compare whitespace deliberately. This is a portability limitation observed in code, not an observed output failure.

## 5. Avoidable effort and token use

1. **Measured trace evidence:** the first OpenAPI tool result reported approximately 14,741 output tokens and 1,831 lines, much of it irrelevant schemas. The initial combined Feature-document read reported approximately 17,748 tokens. A later formatter/dependency command reported approximately 7,758 tokens and 630 lines, largely because the NuGet manifest included its release history. Outputs were truncated. These are tool-reported output estimates, not billed-token totals; no supported total-time or token-savings estimate is available.
2. **Avoidable reading:** all three Feature Skills were read even though developer/reviewer workflows were not needed. Feature documents, API source, and metadata were dumped broadly before being narrowed. Save complete discovery locally, print only paths/request fields and selected formatter metadata, and read relevant headings/ranges once. Source inspection remains a fallback when live discovery leaves a concrete question.
3. **Measured setup overhead:** the successful validator build log reports 21.17 seconds; the failed build trace reports 21.21 seconds. They overlapped, so summing them would misstate elapsed time. [Authoring](author.py) required 100 lines versus 149 for [verification](verify.py), plus a 27-line validator and 20-line project. This supports reusing verification setup, not concluding that checks should be removed.
4. The original [findings](findings.md) is 20,086 bytes and repeats preservation/limitations across sections. Future reports can link machine-readable evidence once and summarize decisions, failures, and unverified behavior. Do not print large JSON or binary evidence merely because it was saved.

## 7. Lessons for subsequent experiments

1. Retain independent inference and conservative static content; explicitly record dependent summaries, currency, formatting culture, and who supplies calculations. Link each generated file to its dataset.
2. Use one harder, focused DOCX case to test the limits actually absent here: split runs, differing row formatting, or an object/annotation interacting with repetition. Do not silently generalize the sample-specific regex patcher.
3. Carry transport and bounded inspection practices into XLSX, but consult its own contract first. DOCX row markers, all-parts-as-XML assumptions, and text-oriented comparisons are not transferable spreadsheet rules. Spreadsheet types, shared strings, formulas, and geometry need their own targeted checks; this experiment supplies no XLSX evidence.
4. Preserve the same standard of proof with less narration: Analyze plus generated values/cardinality, part/property comparison, suitable structural validation, and explicitly scoped visual review. Native Word inspection remains outstanding for Sample 1. Proposed helper benefits should be measured in the next authorized trial before expanding tooling scope.
