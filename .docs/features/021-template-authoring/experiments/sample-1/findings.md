# Feature 021: first practical DOCX authoring experiment

## 1. Outcome and scope

1. **Successful for this sample.** Codex independently converted the completed estimate into a reusable materials-table template. The first authored template passed analysis and generated correct three-material, two-material, and empty-material reports without engine warnings. No template repair was necessary. This is evidence for targeted authoring of this simple report, not acceptance of Feature 021 or proof of preservation for arbitrary DOCX files.
2. The original three-material generation reproduces the uncompressed bytes of every source package entry, including the complete main document XML. The two-material and empty generations change only the main document part as expected. Formatting properties and unrelated content remain structurally identical.
3. Open XML SDK validation passed for the source, template, and all three generated reports. Source and non-empty reports were also rendered and inspected through LibreOffice. **No document was opened or visually inspected in Microsoft Word.** Word repair prompts, Word-specific font substitution, and Word pagination remain unverified.
4. Experiment date: 2026-11-12, Europe/Moscow. Feature 021 specification and architecture, project rules, the DOCX guide, and compatibility contract were reviewed. The feature-architect Skill supplied approach-selection and limitation-reporting guidance. No Feature implementation, Implementation Plan, architecture change, production/test change, delegation, browser automation, or Git mutation occurred.
5. No existing MonoReport example templates, sample JSON, test fixtures, earlier solutions, or other experimental outputs were read during authoring or subsequently. Relevant API routing/endpoint source was inspected. All created experiment artifacts are under this directory; the input remains unchanged.

## 2. Inspection and inferred data model

1. The source contains a title, project and contractor information, a materials heading, one table, three summary paragraphs, and final section properties. The table has eight columns: Reference, Delivery date, Material, Quantity, Unit, Unit price, Line total, and Currency. One header row precedes three material rows. Inspection found the same formatting structure in all three material rows, making one row an appropriate repeat prototype.
2. The package has five file parts and three ZIP directory entries. The file parts are content types, package relationships, main document, styles, and document relationships. There are no header/footer parts or references, images, numbering definitions, nested tables, merged cells, fields, content controls, hyperlinks, comments, bookmarks, or tracked changes. Consequently this experiment does not demonstrate handling of those more difficult structures.
3. Representative data were extracted into `output/skill-sample-1.json`. Its `Materials` array contains three objects with `Reference`, `DeliveryDate`, `Name`, `Quantity`, `Unit`, `UnitPrice`, `LineTotal`, and `Currency`. Dates were normalized to ISO date strings; quantities and monetary values are JSON numbers. Source records are MAT-001/2026, MAT-002/2026, and MAT-003/2026, with line totals 50,000.00, 65,430.50, and 10,000.00 USD.
4. `MaterialCount`, `TotalEstimatedCost`, and `AmountInWords` were parameterized because retaining their original literal values would make the report inconsistent when the materials change. Their representative values are 3, 125430.50, and the exact source amount-in-words text. Project, contractor, tax/registration identifiers, address, contact, email, headings, labels, and summary currency remain static.
5. This is a reusable materials region within the original project's USD report. Callers must supply consistent count, unit prices, line totals, aggregate total, and amount-in-words text, and retain USD currency. The template does not calculate these values or enforce financial consistency. Preserving supplied amount-in-words text avoids introducing unnecessary formatter-dependent wording changes. Mixed currencies and variable project identity are outside this experiment.

## 3. Authoring approach and tools

1. `author.py` is a one-off script specific to the inspected source. Python 3.9.6 standard-library ZIP, XML, regular-expression, date, and JSON facilities were sufficient. No new package was installed. The environment lacked lxml; no general document library was needed. A dedicated editing DSL, reusable editing framework, or specialized editor was not built.
2. The script parses the source before editing, checks the expected table/row/text counts, and extracts its data. It then patches only known XML text nodes and the original contiguous three-row region. It does not deserialize and serialize the complete document XML. Every non-document ZIP entry is copied with its original entry metadata and bytes, preserving namespace declarations and unrelated XML lexically.
3. The table retains its original header followed by a dedicated opening marker row, one formatted data row, and a dedicated closing marker row. The markers are `{For:Materials}` and `{/For}`. Each occupies one paragraph in the first cell; the other seven cells contain empty paragraphs. The marker and data rows retain the prototype's cell widths and formatting. Generation removes marker rows and clones the data row once per material.
4. Each material text node was replaced with its corresponding field expression. Delivery date uses the registered date formatter with pattern `dd MMM yyyy`; unit price and line total use the number formatter with pattern `#,##0.00`. The root total uses the same number pattern. All render requests explicitly specify `culture=en-US` to reproduce the source's English dates and numeric separators despite the preserved ru-RU document language setting.
5. Supporting verification used curl 8.7.1; Python's standard email MIME parser for multipart extraction; .NET SDK 10.0.102; existing cached Open XML SDK and Framework 3.5.1 assemblies plus System.IO.Packaging 10.0.2; LibreOffice 26.8.0.3 for PDF conversion; and macOS sips for preview rasters. The isolated validation project disables implicit usings, uses explicit file-level usings, and references existing cached assemblies without downloading dependencies.
6. Microsoft guidance was consulted for [OpenXmlValidator](https://learn.microsoft.com/en-us/office/open-xml/word/how-to-validate-a-word-processing-document). Validation opens packages read-only. Schema validation and rendering are distinct: the [SDK design considerations](https://learn.microsoft.com/en-us/office/open-xml/open-xml-sdk-design-considerations) explain that the SDK does not supply Word layout behavior.

## 4. Actual REST operations

1. The supplied origin was `http://localhost:3000/`. Routes were confirmed from the API composition source and the **running service's** OpenAPI document, not inferred from the Playground root. The live description reports `MonoReport.Api | v1`, API version 1.0.0. It does not establish the exact deployed engine build or prove the repository guide and runtime share a revision. Successful execution verifies the syntax used in this experiment only.

| Method | Actual endpoint | Use and retained evidence |
|---|---|---|
| GET | http://localhost:3000/openapi/v1.json | Live route and request/response discovery; `evidence/openapi.json` and headers |
| GET | http://localhost:3000/api/formatters | Actual registrations and parameter metadata; `evidence/formatters.json` and headers |
| POST | http://localhost:3000/api/documents/analyze | Multipart `template` file; `evidence/analyze.json` and headers |
| POST | http://localhost:3000/api/documents/render | Multipart `template` file, JSON `data` text field, `culture=en-US`; three saved MIME responses and headers |

2. The live OpenAPI also advertises `/api/documents/sample` and `/api/formatters/{name}/execute`; these operations were not called. Existing source data were extracted independently rather than replaced by generated Sample JSON. The required date and number formatters were present in live metadata; the available spellout formatter was unnecessary for the chosen mapping.
3. Analysis returned HTTP 200, `valid: true`, no errors, no warnings, the expected array/summary requirements, and 12 occurrences. See `evidence/analyze.json` for complete paths, locations, and semantic hints. HTTP status alone was not treated as validity evidence.
4. Generation requested `Accept: multipart/mixed`. Each HTTP 200 response was retained intact, parsed as MIME, and checked for one DOCX document and one diagnostics JSON part, expected metadata, absence of MIME parse defects, and a readable ZIP with valid CRCs before saving the document. All three diagnostics files report an empty warnings array. No authentication was requested by this local service; no credentials were obtained or forwarded.

## 6. Formatting and document comparison

1. **Source versus template:** no ZIP entries or package parts were added or removed. Only `word/document.xml` differs. Styles, content types, package relationships, and document relationships are byte-identical. All document XML outside the explicitly replaced material region and summary value nodes retains its original bytes. The original three material rows were replaced by marker/data/marker rows; the template still has four table rows including its header.
2. **Formatting properties:** comparison retained Calibri 11-point defaults, the 16-point bold title, bold labels and header, paragraph spacing, D9E5F2 header shading, 9AA8B5 borders, fixed table layout, the 9,900-twip table width, and column widths 1300/1400/2300/700/700/1100/1400/1000. Page size 11906 by 16838 twips, 1000-twip margins, and header/footer distances remain unchanged. Text-node whitespace attributes were ignored only when comparing formatting signatures; the complete three-material round trip additionally passed exact part-byte comparison.
3. **Template versus generated documents:** marker rows disappear and data-row cardinality follows JSON. Every repeated row retains the prototype's cell, paragraph, and run structure/properties. The header, table properties/grid, static paragraphs, summary run formatting, section properties, styles, and relationships are preserved. In the three-material result, all five file parts are byte-identical to the source. In the two-material and empty results, only the document part differs, and those differences match expected row removal/value substitution.
4. **Visual evidence:** LibreOffice exported the source, three-material result, and two-material result to single-page PDFs in `evidence/preview/`. Source and three-material PNG rasters are byte-identical; comparison hashes are saved in `comparison.json`. The source and two-material white-background JPEG previews were inspected: title, labels, shaded header, borders, column geometry, and summary styling agree. Summaries move upward naturally with the removed row. Existing line wrapping in Reference, Quantity/Currency headers, and the narrow Unit column is present in the source too and was preserved rather than redesigned.
5. The LibreOffice export logged fontconfig warnings. Requested OOXML font properties are unchanged, but exact installed-font selection was not verified. Raster inspection was at approximately 72 dpi. Successful LibreOffice import/export and preview comparison supplement structural checks; they do not establish that Microsoft Word opens without repair or renders identically. The template's longer visible expressions were not visually reviewed in Word, and no large or multipage dataset was exercised.

## 7. Failures, corrections, and limitations

1. Initial sandboxed curl could not connect to localhost. The same user-authorized request succeeded with a network sandbox exception. This was an execution-environment limitation, not an API template diagnostic. Actual successful discovery and render responses were retained.
2. The first preservation assertion incorrectly required the document part to differ in every generated case. The original-data round trip was completely byte-identical, causing that assertion to fail. The check was corrected to allow no changed parts while forbidding unrelated changes. The template and datasets were not changed to obtain success.
3. The first validator build used an unavailable MSBuild UserProfile property and could not resolve cached assemblies. Replacing that path property with HOME resolved the references; the final build had zero warnings/errors. An initial sandboxed LibreOffice conversion exited unsuccessfully without diagnostic output; the same small conversion with a sandbox exception succeeded. Neither issue required changing a DOCX or production code.
4. Initial PNG previews had transparent page backgrounds, obscuring black text against the viewer background. JPEG previews supplied a white background and were used for visual inspection. Original PDFs/PNGs and equality evidence were retained. No document content was altered for preview purposes.
5. This input is unusually small and structurally simple. The trial provides no evidence for split-run expressions, heterogeneous row styling, repeated annotations/identifiers, relationships inside repeated objects, opaque content, merged regions, tracked changes, other stories, or complex pagination. It does not establish OpenCode portability, MCP behavior, authentication portability, engine/documentation build matching, or broader proposed Feature acceptance criteria.
6. No material discrepancy with the DOCX compatibility contract was observed. No production or user-facing documentation correction is needed for this experiment. The remaining Microsoft Word inspection is a verification gap, not an engine failure or a claim of exact visual equivalence.

## 8. Recommendations based on observed work

1. **Structured Inspect: useful, not necessary for this sample.** Raw package inspection easily revealed the only repeat candidate, but required one-off code to enumerate rows/cells, compare formatting, and inventory relationships. A bounded inspection response containing story/table/row/cell locations, visible text with run boundaries, relevant properties, relationships, and compatibility hazards could reduce that manual work. Existing Analyze supplies template occurrences rather than an inventory of an untemplated source. The trial demonstrates authoring convenience value, not a mandatory new endpoint or reliable automatic business-schema inference.
2. **Specialized editing tools: not justified by this trial.** Targeted XML edits plus copying untouched package entries achieved exact original-data reconstruction on the first authoring attempt. No observed editing failure required a DSL, generalized editor, or dedicated MonoReport editing service. Keep the proposed editing boundary until more difficult representative inputs demonstrate a concrete shortcoming.
3. **OOXML guidance: modest, actionable value.** A short authoring reference should emphasize choosing a formatting-equivalent prototype row, keeping each structural marker in its own paragraph/row, preserving cell/run properties and namespace bindings, copying unrelated entries, and comparing part contents rather than ZIP containers. It should explicitly distinguish analysis, schema checks, generated-data verification, and native Word visual review. These were actual decisions and checks needed here; broad new OOXML infrastructure is unnecessary.
4. **HTTP/MIME handling: practical value demonstrated.** Requesting multipart diagnostics and parsing the response with the standard MIME library reliably preserved document bytes and warnings. Endpoint discovery and sandbox access were real setup steps. A narrow existing-client-compatible transport helper could eliminate repeated request/extraction work, as already proposed in Feature 021, without becoming an editor or second engine interface.
5. Before claiming broad authoring fidelity, conduct a separately authorized harder input trial and obtain native Word inspection of representative artifacts. This result supports feasibility of conservative conversion with available general-purpose tools; it does not require changing the approved architecture, scope, engine syntax, or support guarantees.
