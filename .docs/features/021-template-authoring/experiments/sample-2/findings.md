# Feature 021 — DOCX Template Authoring Experiment Sample 2

## 1. Outcome and scope

1. **Feasible for this document on the first authoring attempt.** Codex independently inferred the hierarchy, extracted all source data, authored nested repetition, and validated actual REST-generated reports. The template handles fewer and more orders, more lines within an order, empty line collections, and an empty order collection. No template correction was needed after analysis or generation.
2. The original-data generated report reproduces the source main-document XML exactly except for removal of the newline after its XML declaration. All other 22 package parts are byte-identical. This is strong evidence of design preservation for the original data, beyond a comparison of selected formatting properties.
3. This was an authorized feasibility experiment, not Feature implementation or acceptance of the proposed architecture. Reviewed the Feature 021 specification, relevant architecture/preservation guidance, project Feature Skills, DOCX guide, and DOCX compatibility contract. No Implementation Plan, production code, existing tests, contracts, architecture, prior experiment artifacts, or user-facing documentation were changed. No agents, browser automation, resource-intensive tests, or Git mutations were used.
4. No existing MonoReport sample templates, sample JSON, test fixtures, or previous experiment solutions were consulted, including after validation. The first template remains unchanged: its hash matches [initial-attempt.json](evidence/initial-attempt.json). Existing staged Sample 1 and Feature documents were preserved.

## 3. Independent inspection and data model

1. The source contains a static title and organization/warehouse/period metadata, a report-level count and total, a caption, 20 consecutive order blocks, a final report total, and one final section-properties element. Each order comprises a heading, date/customer paragraph, line-count/total paragraph, complete seven-column detail table, and subtotal paragraph. The input renders to nine pages in the available LibreOffice installation.
2. The inferred hierarchy is a report object containing `Orders`, each containing `Lines`. Order fields include number, date, customer, line count, and total. Line fields include number, SKU, description, quantity, unit, unit price, and total. Organization, warehouse name/address, period, currency, order count, and grand total belong to the root. This preserves order membership rather than flattening all lines into one collection.
3. The source line counts are 8, 9, 6, 9, 9, 6, 9, 6, 10, 5, 9, 10, 8, 5, 6, 7, 5, 7, 9, and 9. All quantity × unit-price calculations, line sums, order totals, subtotals, and the USD 60,206.90 report total reconcile. Repeated SKUs remain separate records in their original order.
4. All table properties, grids, headers, and detail-row formatting are structurally equivalent across source occurrences after excluding text and editing-session identifiers. There are no main-document bookmarks, comments, hyperlinks, content controls, tracked insertions/deletions, vertical merges, drawings, or extra section boundaries obstructing the chosen repeat footprint. This uniformity materially simplifies the experiment; results do not establish feasibility for arbitrary annotated or heterogeneous reports.
5. Dates use ISO JSON strings and the discovered date formatter. Monetary values use invariant decimal strings, supported by the number formatter, avoiding extraction through binary floating-point arithmetic. Counts and totals are explicit data fields. MonoReport formats supplied summaries; it does not calculate these aggregates. Dataset preparation recalculates them, and verification independently checks their arithmetic.

## 4. Authoring approach and REST execution

1. Selected Python standard-library ZIP and namespace-preserving DOM operations. `lxml` and `python-docx` were unavailable; no dependency installation was needed. Only selected text nodes and repeated blocks in `word/document.xml` were edited. Paragraphs were not replaced to change substrings, and existing runs, run/paragraph/table/cell properties, prefixes, namespace declarations, and markup-compatibility bindings were retained.
2. Retained the first order block as the outer prototype and its first detail row as the inner prototype. Dedicated sibling paragraphs delimit the `Orders` loop around the complete order block. Dedicated seven-cell marker rows delimit the `Lines` loop inside the table, with only the first cell containing a marker. Table headers remain outside the inner loop; the order subtotal remains inside the outer loop and outside the inner loop; the final report total and section properties remain outside both loops.
3. Order fields use the current order context, line fields use the current line context, and order currency references use the root path `$.Currency`. Modified cases change currency to EUR, organization, order identifiers, customers, quantities, counts, and totals. This checks actual binding and prevents original literals from accidentally satisfying output checks.
4. Discovered actual endpoints from API route source and the running [OpenAPI response](evidence/openapi.json): `POST /api/documents/analyze`, `POST /api/documents/render`, `POST /api/documents/sample`, and formatter list/execution routes. Retrieved [registered formatter metadata](evidence/formatters.json). Used only registered `date` and `number` formatters, requesting `en-US` culture. Sample generation was unnecessary because source data was available.
5. The supplied origin serves the Playground at `/` and forwards the API operations. Initial sandboxed localhost access failed; an approved network-permission retry succeeded. No credentials or alternate engine were substituted. OpenAPI identifies `MonoReport.Api | v1`, version `1.0.0`; this is not proof of an exact engine build or documentation revision. The reviewed repository documentation's build match to the running engine remains unverified.
6. [Analysis](evidence/analyze.json) returned HTTP 200, `valid: true`, zero errors, zero warnings, 27 occurrences, and the intended nested requirements. Each of five generation calls returned HTTP 200 and zero warnings. All used `Accept: multipart/mixed`. Extraction checked HTTP status, content length, closing boundary, MIME parser defects, exactly one document and one diagnostics part, filename/format agreement, and ZIP integrity before publishing DOCX bytes.

## 6. Layout evidence, cost, and limitations

1. **Conversion is separate from visual inspection.** Before the Product Owner's follow-up, LibreOffice converted the source and all five results to [PDF evidence](evidence/preview/). After the follow-up, no further LibreOffice conversions or visual rendering were performed. Existing PDFs were inspected only for metadata and extracted page text with PDFKit; no drawing or raster rendering occurred.
2. [PDF inspection](evidence/preview/pdf-inspection.json) shows nine pages for both source and original-data output, with exactly identical extracted text on every corresponding page. This supplies layout-engine pagination evidence that ZIP, XML, and schema checks alone cannot establish. The modified 24-line order spans a two-page report, but its detailed visual presentation was not reviewed. No screenshots, pixel comparisons, manual visual inspection, or Microsoft Word opening were performed. Exact cross-application pagination, glyph rendering, clipping, and absence of a Word repair prompt remain unverified.
3. LibreOffice was already installed; installation time was zero. The first sandboxed conversion failed without useful output in approximately 0.19 seconds. The interval from its initial log creation through successful source PDF creation was approximately 27.4 seconds, including the permission retry and intervening task work; this is setup elapsed time, not conversion CPU time. The successful source command returned in approximately 1.0 second, original-data conversion in approximately 0.6 seconds, and the four-variant batch reached its last PDF approximately 1.1 seconds after log creation. These are observed tool waits/file timestamps, not a controlled benchmark or precisely isolated startup measurements. See [timing evidence](evidence/preview/timing.json) and conversion logs.
4. Conversion logs include fontconfig cache warnings but successful PDF exports. A separate temporary LibreOffice profile was used. No font setup, renderer installation, GUI automation, or document resave through LibreOffice was necessary. The original DOCX artifacts were not changed by conversion.
5. **Marginal benefit:** successful conversion shows that LibreOffice can load/export these artifacts, and PDF text comparison confirms identical original-data pagination and page content in that renderer. It does not independently prove visual fidelity. Given exact original-data main XML preservation, unchanged supporting parts, verified source formatting in variants, and zero SDK errors, additional rendering would have offered limited value without a specific layout concern. No unresolved structural result justified another conversion or visual pass.

## 7. Failures, recommendations, and feasibility boundaries

1. No template, data-binding, summary, hierarchy, or package-preservation failure occurred. Environmental failures were the initial sandboxed localhost request and initial sandboxed LibreOffice invocation; permission retries resolved both. No compatibility-contract discrepancy was observed, and no engine limitation required changing the source design or removing unsupported content.
2. A future Skill should first produce a structured inspection inventory: ordered blocks, table/header/detail patterns, formatting variants, section boundaries, annotation/reference hazards, and candidate data scopes. Here that inspection established that one prototype could safely represent all occurrences. Without it, selecting a row or deleting materialized sections would have been a substantially less justified decision.
3. Skill guidance should require explicit summary ownership: extract reported values, reconcile them with detail data, and make callers responsible for supplying consistent counts/totals when the template language provides formatting rather than aggregation. Keep headers and subtotals at the correct loop level, test root/current-context binding, and exercise empty outer and inner collections separately.
4. Preserve package parts and namespace bindings deliberately; compare source-to-template editing separately from template-to-result generation. Require actual output checks for membership, values, cardinalities, summaries, formatting, relationships, and OOXML integrity. Analyze success alone cannot establish these results. Preserve MIME diagnostics and validate attachment extraction rather than saving the multipart envelope as DOCX.
5. A dedicated OOXML editor or DSL was unnecessary for this sample. Existing ZIP/XML capabilities with assertions and Open XML SDK validation were sufficient. A small deterministic helper might reduce repeated risk around expected-text preconditions, copying unchanged entries, namespace preservation, and supported marker placement across split runs or more complex documents. This experiment does not demonstrate a need to build that tooling, and does not authorize it. Source-specific scripts should not silently grow into a general editor.
6. **Recommend optional, risk-based visual verification for the future Skill.** Start with structural correctness and preservation evidence. Use an existing renderer when unresolved risks involve changed widths, unusually long replacements, added section/page breaks, complex repeated content, or a specific pagination defect. Select only relevant pages/cases. Skip or stop visual work when strong package/formatting evidence already resolves the question and no layout issue remains; do not require renderer installation, conversions for every dataset, or repeated visual passes by default.
7. Future Skill documentation should distinguish schema validity, package preservation, semantic output verification, conversion/pagination evidence, and actual visual inspection. No existing public guide or compatibility contract required correction for this result; any future Skill guidance remains a recommendation, not an architecture change or approved implementation.
8. The feasibility conclusion is bounded to this uniformly formatted, compatible report and the tested datasets. Structural and package design-preservation criteria passed. Full visual acceptance in Microsoft Word remains outside the evidence collected here.
