# Sample 3 — DOCX template authoring experiment

1. **Outcome.** The first authored template passed MonoReport Analyzer and generated successfully without warnings. Deliverables are [template](output/skill-sample-3.template.docx), [representative original JSON](output/skill-sample-3.json), and [modified-data report](output/skill-sample-3.result.docx). The delivered report uses [modified JSON](evidence/modified-data.json). No previous experiment solutions or existing templates were inspected. No production code or Feature architecture was changed, no Git mutations were performed, and no other agents were invoked.
2. **Inferred model.** The report has a project title and period, then three nested collections: `Projects`, `Groups`, and `Items`. The source contains 3 projects, 8 groups, and 16 items. Landscaping is an empty group with a zero subtotal. Items expose description, unit, quantity, unit price, and total; groups and projects expose names and totals, with a root grand total. Static column labels and USD remain in the template. Names and period are strings; quantities, prices, and totals are JSON numbers. Totals are caller-supplied data, not template calculations. The experiment independently reconciles each line, group, project, and grand total using decimal arithmetic; modified monetary line totals are rounded to cents before summation.
3. **Authoring method.** [author.py](author.py) reads the source ZIP and edits only `word/document.xml` using Python's standard DOM. It preserves the title's individual runs while replacing its split text, and builds three nested supported row loops using dedicated marker rows. The original project, group, and item rows supply formatting prototypes; table header and grand-total rows remain outside the loops. Horizontal four-column heading spans are retained; the source has no vertical merges, annotations, drawings, hyperlinks, content controls, headers, footers, or tracked changes requiring special handling. Editing-session paragraph/text identifiers are removed from repeating prototypes to avoid duplicate identities. No DSL, editor, or new engine behavior was introduced.
4. **Service validation.** The supplied `http://localhost:3000/` service was used through `/api/formatters`, `/api/documents/analyze`, and `/api/documents/render`. [Formatter metadata](evidence/formatters.json) confirmed `number` and its required pattern. Analyzer returned `valid: true`, no errors, and no warnings; its complete requirements and occurrences are in [analyze.json](evidence/analyze.json). All render requests specified `culture=en-US` and `Accept: multipart/mixed`. [cases.py](cases.py) uses Python's MIME parser to extract the DOCX and diagnostics, checks MIME defects, attachment identities, format, warnings, and ZIP integrity before saving. Raw MIME responses, HTTP headers, and full diagnostics are retained in `evidence/`. Every retained result has zero generation warnings. Repository guide and compatibility contract supplied the syntax; the running service's exact engine build/documentation identity was not advertised or independently established.
5. **Behavioral evidence.** [verify.py](verify.py) checks exact table-cell text and order, title/period, row counts, decimal totals, formatting, XML parsing, ZIP integrity, and internal relationship targets. It confirms no unresolved template braces in results. The source-data result matches every source paragraph's text and every source row's formatting, including the empty Landscaping group. The modified case changes project and period, project/group names, quantities and prices, collection lengths at every level, and special characters (`&`, `<`, `>`). It removes a group, shrinks one item collection, grows another, fills Landscaping, and adds a fourth project containing both populated and empty groups. Detailed assertions and hashes are in [verification.json](evidence/verification.json).

8. **Concrete tooling difficulties.** The default Python lacked `lxml`; the standard DOM handled the required edits without installing anything. Sandbox-local `curl` initially could not reach localhost; the same call with approved network access succeeded. Word divided the project title across five text runs, so replacing a paragraph wholesale would have needlessly changed its run structure. Nested row markers and representative style selection required manual OOXML inspection; each source row was later checked against the generated counterpart. Binary REST output required MIME extraction and warning preservation, beyond a simple file download. The first validator build failed because NuGet vulnerability metadata was unreachable and the repository treats warnings as errors; rebuilding this experiment-only runner with `NuGetAudit=false` used cached dependencies successfully. No general validator was rebuilt: schema validation delegates to the SDK. All scripts and evidence remain local to this experiment.
9. **Limitations and tooling implications.** Word opening, repair prompts, visual rendering, and exact pagination were not tested. No unresolved layout risk required LibreOffice or browser automation under the requested efficiency constraints. Longer names or larger datasets can alter wrapping/page count even with identical properties. Callers must recompute all totals when changing data; the template only formats supplied values. The static USD labels imply USD inputs. Empty cases intentionally retain applicable heading rows and a zero grand total. The experiment demonstrates that a narrow package edit can succeed without a dedicated editor, but run-aware field replacement, safe nested marker insertion, and reliable HTTP/MIME handling remain concrete opportunities for reducing authoring effort. It does not authorize implementation of those tools, and no compatibility discrepancy or documentation correction was identified.
