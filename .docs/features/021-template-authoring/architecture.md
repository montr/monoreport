## 3. MCP-only versus Hybrid

1. **Approved D1:** host MCP in the existing Service API. **Proposed D2:** two MCP tools for documentation/formatter discovery; existing REST for analysis, Sample JSON, and generation. Samples 1–5 support REST feasibility, not approval of Hybrid, MCP interoperability, or OpenCode portability.
2. **Recommended flow:** select a connection → retrieve matching docs, formatter metadata, and REST binding → inspect/infer the model → edit a separate local template → perform the selected Fast/Full checks through REST and local verification. Keep binary payloads out of conversational context.

| Concern | MCP-only | Hybrid recommendation |
|---|---|---|
| Implementation/reuse | Three additional document handlers, binary schemas/limits, and diagnostic mappings alongside docs/discovery. | Reuse existing multipart endpoints/options/diagnostics; add only MCP knowledge/discovery and binding metadata. |
| Files/tokens | Base64 increases raw payload size by about one third; portable binary capture is unproved. Handles add storage/lifecycle work. | Raw multipart uploads/downloads and local files avoid binary model context; summarize large analysis/sample responses selectively. |
| Identity/authentication | Document calls stay on the MCP connection and its configured authentication. | Explicit REST pairing, permitted local network access, and independently usable REST credentials are required. |
| Permissions/portability | MCP tool policy applies; binary saving still needs client trials. | Shell/network policy applies. Suitable Codex/OpenCode environments can use local HTTP; MCP-only OAuth/tunnel environments may not. |
| Formatting/correctness | Transport cannot establish Office fidelity or model completeness. | Same boundary; five trials demonstrate targeted package editing and actual REST output checks, with important limitations in section 2.2. |

### 3.1. Minimum proposed server surface

| Capability | Interface | Boundary |
|---|---|---|
| Documentation/context | MCP `get_documentation` | Index with engine/docs identity, known defaults/limits, public API base and routes; bounded engine-matched document/section retrieval. Agent references are described in section 6. |
| Actual formatters | MCP `list_formatters` | Existing string-key discovery and selected metadata in the operation scope; no static catalog or replacement registry. |
| Analysis | Existing `POST /api/documents/analyze` | `template` file only; inspect `valid`, including on HTTP 200. |
| Sample JSON | Existing `POST /api/documents/sample` | `template` file; optional collection-count/value-mode text fields; retain data/warnings. |
| Generation | Existing `POST /api/documents/render` | `template` file, `data` JSON text field, optional culture; request `multipart/mixed`. |

1. Tool names/context fields remain proposed. Reuse [key discovery](../../../src/MonoReport/Core/KeyedServiceExtensions.cs), the API's DI composition, and a small shared formatter projection where justified. Resolve scoped dependencies per operation; REST retains `GenerationOptionsFactory`. No internal HTTP loopback, new engine facade/parser, or independent defaults policy is needed.
2. The official [C# MCP SDK](https://github.com/modelcontextprotocol/csharp-sdk) with ASP.NET Core support remains the dependency candidate. Its [license](https://github.com/modelcontextprotocol/csharp-sdk/blob/main/LICENSE) includes Apache-2.0 and retained MIT code; documentation is CC-BY-4.0. Released-version/protocol selection and complete transitive-license review remain outstanding. Existing Open XML SDK is [MIT licensed](https://github.com/dotnet/Open-XML-SDK/blob/main/LICENSE).
3. No separate server-info tool, document MCP tools, artifact store, token broker, localhost bridge, runtime formatter loader, or additional MCP executable is proposed. MCP-only remains an alternative if required client environments cannot use REST; it is not approved as a fallback implementation.

### 3.2. Do existing REST responses contain what authoring needs?

| Response | Confirmed content | Client responsibility |
|---|---|---|
| Analysis | Validity, errors/warnings, requirements, occurrences and available semantic hints. | HTTP 200 can mean `valid: false`; analysis does not validate datasets or infer all business dimensions. |
| Sample JSON | Data and ordered warnings; structural/limit failures use Problem Details. | Preserve synthetic-data labeling, diagnostics, and existing limits. |
| Multipart generation | Raw document and `diagnostics.json`: format, filename, original warnings. | Request exactly `Accept: multipart/mixed`; extract and validate attachments without text-decoding binary. |
| Binary-only generation | Document/MIME/filename and warning count when nonzero. | Count alone is insufficient for repair; prefer multipart rather than rerunning generation for details. |
| Engine failure | HTTP 422 with code, trace ID, field, errors, `limitReached`; entries include available part/location/formatter/data path. | Retain all useful diagnostics and distinguish failure from a document. |
| Request/proxy/network failure | Safe application errors where handled; upstream rejection can be non-JSON. | Preserve status/context; reject HTML login/error pages, interrupted bodies, or missing diagnostics. |

1. Existing [document handlers](../../../src/MonoReport.Api/Services/DocumentEndpoints.cs), [multipart output](../../../src/MonoReport.Api/Services/GenerationMultipartResult.cs), and [problem mapping](../../../src/MonoReport.Api/Services/ApiProblemFactory.cs) supply sufficient repair diagnostics; no payload retrofit is justified. [Transport tests](../../../tests/MonoReport.Api.Tests/ApiDocumentTransportTests.cs) cover bytes, warnings, negotiation, and no-document failures; [analysis/sample tests](../../../tests/MonoReport.Api.Tests/HttpApiTests.cs) and [CLI parity](../../../tests/MonoReport.Api.Tests/ValidationContractParityTests.cs) add contract evidence. These suites were inspected previously, not rerun for this update.
2. Responses do not attest the engine/configuration or effective options per call. Use MCP build/default context plus the controlled routing/authentication invariant in section 4; do not invent per-response identity or exact policy overrides. Neither OOXML validity nor complete intended variability follows from these diagnostics, as Sample 5 demonstrates.

### 3.3. Local HTTP execution and whether a helper is necessary

1. REST itself requires no helper: [curl](https://curl.se/docs/manpage.html) can upload files, send JSON-file contents as a text form field, and save bodies. A saved multipart envelope is not a DOCX/XLSX file. Repeated transport assembly, malformed form quoting in Sample 4, and status-line/MIME confusion in Sample 5 justify a reusable response helper; see the [Sample 1](experiments/sample-1/retrospective.md), [Sample 4](experiments/sample-4/retrospective.md), and [Sample 5](experiments/sample-5/retrospective.md) retrospectives.
2. Keep its boundary narrow: fixed existing operations and the selected binding/credential reference, binary-safe extraction, HTTP/analysis validity, complete diagnostics, format/filename pairing, bounded reads/timeouts, and fresh output publication only after validation. Require valid framing, not a mandatory Content-Length when HTTP supplies other framing; exclude HTTP status lines from MIME headers. No OAuth acquisition, client-cache scraping, OOXML editing, generic SDK, or retry framework.
3. Prefer existing HTTP and [MIME byte parsing](https://docs.python.org/3/library/email.parser.html). Curl plus Python standard-library parsing worked in the experiments; the initial synthetic NUL/high-byte/trailing-CRLF check supported feasibility only. This is not a shipped portable helper or comprehensive malformed-response test. Declare prerequisites; avoid custom MIME splitting or importing the browser TypeScript runtime. Existing [Playground generation](../../../web/src/services/generation.ts) and [tests](../../../web/src/services/generation.test.ts) define useful response behavior to preserve.
4. A client with equivalent validated HTTP/MIME saving may omit the wrapper, but not its checks. Reusable inspection and verification now have separate evidence-based justification in section 6; this does not justify a dedicated mutation editor.

## 4. Binding the selected MCP connection to REST

### 4.1. Proposed deployment descriptor and multiple instances

1. **Proposed D6:** the documentation index advertises an operator-configured public REST API base ending in a slash, including external proxy/tenant prefixes, plus relative operation routes derived from existing constants. No secrets or duplicate route registry. Standard URI resolution must preserve prefixes and reject traversal/origin changes.
2. Do not derive REST by stripping `/mcp`: external MCP and API paths/origins may differ. Existing [Program](../../../src/MonoReport.Api/Program.cs) processes `X-Forwarded-Proto` only; no reliable public API-base discovery was identified. Request Host, internal addresses, or untrusted forwarded headers are not configuration. Missing/conflicting binding requires setup correction or an explicit user pairing, not a guessed origin.
3. Pin connection, API base, principal/tenant headers, and credential reference together; refresh on switching. Route both protocols to the same logical engine/configuration or homogeneous replicas. Same version/formatter lists detect some mistakes but cannot prove complete identity. Existing REST responses do not independently attest this invariant; heterogeneous routing or per-call provenance requirements need separate review.
4. Experiments used an explicitly supplied local origin and live discovery; they did not validate MCP advertisement, multiple instances, reverse-proxy rewrites, or exact engine/docs identity. Preserve those acceptance criteria rather than treating local REST success as proof.

### 4.2. Authentication, network access, and client portability

1. Official [Codex MCP documentation](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) describes named connections/OAuth/environment headers; [command security](https://learn.chatgpt.com/docs/agent-approvals-security) controls local network access separately. [OpenCode MCP](https://opencode.ai/docs/mcp-servers/) and [tools](https://opencode.ai/docs/tools/) likewise separate connections from local shell execution; textual webfetch is not a binary transport. No portable export of client-managed MCP OAuth into Skill scripts was established.
2. Minimal Hybrid requires intentionally available REST access, with operator-provisioned credentials when necessary. Use the same logical user/tenant/configuration; reuse a secret only where the intended resource/policy permits it. The [MCP authorization contract](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) requires audience validation. Do not scrape token caches or forward MCP credentials merely because URLs share a host.
3. Pin destinations, verify remote TLS, and stop unexpected redirects/login responses. Uploads follow shell/network permission, not read-only discovery consent. A helper cannot supply absent network reachability/authentication. No permission edits, new login flow, credential broker, or weakened access control is implied.
4. Browser-only cookies/CORS, hosted or tunnel-only MCP reachability, and unavailable local execution remain Hybrid limitations. Samples demonstrated local network-permission retries, not authenticated portability. If those environments are mandatory, revisit the architecture explicitly rather than introduce a hidden bridge.

### 4.3. Version-matched documentation and server-info

1. Retain the build-matched guides/contracts and engine identity requirement. Add concise agent authoring references with compatible engine/docs provenance, as requested, without duplicating the human manuals. Use bounded allowlisted retrieval and a small index; no search service/docs database is needed.
2. Report known actual defaults/limits; discover selected formatter registrations rather than infer behavior from a built-in name. General `formatters.md` covers usage rules, not availability, arbitrary custom semantics, or default/allowed-value data absent from metadata.
3. **Proposed D4 retained:** place engine/docs/defaults and REST binding in the model-visible documentation context instead of a separate server-info operation. Packaging proves docs correspondence; deployment routing/authentication establishes which engine receives files. UI versions, aliases, and experiment success establish neither independently.

## 5. Authoring capabilities available to Codex and OpenCode

### 5.1. Confirmed capability levels

1. A Skill supplies workflow knowledge/resources, not installed Office libraries or a renderer. Both clients' documented local execution/Skill facilities remain the portability basis; actual OpenCode and MCP authoring trials are outstanding.
2. Samples 1–5 used Python standard-library ZIP/XML facilities, curl, and an existing Open XML SDK validator. DOCX trials used targeted patches or DOM operations; XLSX trials changed selected workbook/worksheet parts. This supports narrow edits without a new editor, not arbitrary Office preservation.
3. Earlier PATH discovery did not find LibreOffice; Samples 1–2 later used an installed application for conversion. Treat availability as runtime-dependent, not a permanent prerequisite or absence. Sample 1 supplies limited visual evidence; Sample 2 supplies PDF text/pagination evidence; Samples 3–5 did not render. None establishes native Word/Excel opening or recalculation.

### 5.2. Creation/editing alternatives

| Approach | Appropriate use | Remaining boundary |
|---|---|---|
| Targeted ZIP/XML or namespace-aware DOM | Experiment-supported edits retaining unrelated entries and known properties. | Structural selection, run boundaries, identities, shared strings, namespaces, and geometry still need deliberate checks. Do not promote source-specific regexes. |
| Open XML SDK | Established package manipulation and schema validation; already used by the project. | [Design considerations](https://learn.microsoft.com/en-us/office/open-xml/open-xml-sdk-design-considerations) exclude layout/recalculation and automatic validity guarantees. Reuse its validator rather than rebuild OPC validation. |
| General authoring libraries | Optional conveniences when installed and suitable for the requested change. | [python-docx paragraph replacement](https://python-docx.readthedocs.io/en/latest/api/text.html) removes run formatting; [openpyxl save limitations](https://openpyxl.readthedocs.io/en/stable/tutorial.html) require preservation review. Neither was needed in the trials. |
| Office/LibreOffice or connected editor | Targeted application/layout/recalculation evidence when available and authorized. | Conversion alone is not visual review; save normalization can change packages. No default renderer installation or automation is proposed. |
| Dedicated editor/DSL | Only a demonstrated recurring mutation need could justify it. | Five trials do not establish that need. Keep inference with the agent and checks in small reusable scripts. |

### 5.3. Format-specific hazards and proposed editing workflow

1. **Model before mutation:** record static/dynamic fields, hierarchy, candidate independent axes, evidence/invariants, calculation ownership, empty-case policy, and unresolved assumptions before choosing JSON. For multiple completed reports, align stable identities and compare changes separately. If suppliers and criteria always change together, independence remains uncertain; unchanged criteria never prove fixed criteria. Ask a targeted question when this changes the resulting reusable model.
2. **DOCX references:** explain equivalent prototypes per row/block class, logical versus physical cells/merges, nested sibling marker scopes, summary ownership, split-run text edits, culture/decimal rounding, and story/opaque boundaries. Preserve run/paragraph/table/section properties, namespace bindings, relationships, and identifiers under the contract. Sample 3's simple split title does not prove mixed-format replacements or identity-bearing repeat bodies.
3. **XLSX dimensions/geometry:** describe vertical level-ordered records and contiguous header/detail/footer controls, nested horizontal collections, markers across every column of a multi-column block, parent-only/hidden columns, positional tuple order/count, and merge ownership. Plan control relocation and PrintArea with blank margins, styled blanks, widths, heights, views, and trailing content. The [existing combined guide](../../../docs/xlsx-template-guide.md#combining-both-directions) already describes supplier × criterion dimensions; Sample 5's primary failure was modeling, not missing engine support. Its [source-inspection provenance](experiments/sample-5/evidence/inspection-provenance.json) identifies narrower agent-guidance gaps about geometry/control placement.
4. **XLSX values/formulas:** preserve source scalar types before any requested coercion. Source numeric text and numeric cells behave differently in SUM; an unformatted whole-cell expression can remain native, while formatter output is text. Retain declared subtotal meaning, including non-weighted or unusual source sums, unless change is requested. Check relocated references and operand types separately from expected arithmetic; cleared caches/recalculation flags do not prove actual Excel results.
5. **Formula boundary:** Sample 5 retained subtotal formulas while empty children removed their targets, correctly producing `template.xlsx_unsafe_formula`. This does not imply all empty groups fail, that lots must universally contain items, or that independent criteria caused the rejection. No alternative empty-lot design was tested; require intended behavior before changing formulas, suppressing groups, or adding placeholders. Empty criteria need their own specified scenario.
6. **Preservation:** distinguish source-to-template edits, original-data reconstruction, and changed-data output. Compare uncompressed part contents and relevant XML properties, allowing changed parts to be a subset of permitted parts. Baseline SDK diagnostics against the source; Sample 4 inherited defects must be reported, not relabeled schema-clean or automatically fixed. Do not reject all braces/external relationships, parse binary parts as XML, or ignore meaningful whitespace based on experiment-specific verifiers.

### 5.4. Fast/Full validation architecture

1. Two modes and Full-on-Fast continuation are requested requirements; [Feature Spec section 5.1](feature-spec.md#51-fast-and-full-modes--requested-capability-proposed-check-policy) defines the proposed check matrix. Mode defaults/escalation remain D7. Both modes establish intent and essential output correctness; Fast reduces check breadth, not semantic obligations.
2. Full derives scenarios from each intended axis independently of the chosen JSON representation. For supplier × criteria, hold suppliers/items fixed while criteria change from two to three, then one, and reorder; vary suppliers separately. Distinct intersection values, parent-only hidden columns, merges, and subtotal references must follow data alone. Sample 5's fixed-field model cannot pass this scenario even though its previous verifier passed.
3. Full can consume existing Fast artifacts and evidence. Record source/template/dataset/result identity, engine/docs context (or explicit unknowns), mode/check coverage, assumptions, and timing. Reuse only matching evidence; unchanged files need no reauthoring, and missing cases alone need generation. Changed engine context invalidates relevant earlier checks. Report incomplete Full validation or a defect without silently editing the template.
4. Rendering is risk-based in either mode: target a named wrapping, pagination, geometry, application-opening, or recalculation concern. Structural/schema/property evidence is not visual proof. Missing required capabilities remain visible; a Fast label or inherited schema baseline does not establish an application-level guarantee.

## 6. Portable `monoreport` Skill design

1. **Requested package:** one `monoreport` folder with portable `SKILL.md`, reusable scripts, and agent DOCX/XLSX authoring references. Common discovery at `.agents/skills/monoreport` is documented for [Codex](https://learn.chatgpt.com/docs/build-skills) and [OpenCode](https://opencode.ai/docs/skills); actual dual-client trials remain required. No client-specific runtime wrapper, marketplace, or global setup mutation is implied.
2. Keep the entrypoint short: select engine/mode → establish intent/dimensions → inspect → edit a copy → use the selected validation path → report artifacts/assumptions/limits. Support optional natural-language structure, dynamic fields, nesting, axes, calculation/empty policies, JSON, and multiple completed reports. Contrasting reports are evidence, not authorization to invent unobserved business rules.
3. **Agent reference responsibilities:** proposed `references/docx.md` and `references/xlsx.md` explain compact authoring recipes/decisions and known pitfalls from section 5, with progressive links to authoritative engine-matched guides/contracts. `references/formatters.md` contains only general invocation/binding/culture/scalar and XLSX text-output rules. Discover actual names, parameters, positional targets, requiredness, and available hints through connected API/MCP; no copied built-in/custom catalog. Keep guidance version compatibility explicit. These files are requirements for later work, not files created by this task.

| Priority | Reusable responsibility | Experiment justification and boundary |
|---|---|---|
| 1 | Bounded package/source inventory and targeted comparison | Samples 2–5 repeatedly inspected run/style classes or worksheet geometry. Resolve namespaces/relationships; show representative regions, cell types/shared strings, merges, controls, formulas, and hazards. Multiple-input comparison exposes differences; the agent owns business inference. |
| 2 | REST/MIME response handling | Repeated across all samples; actual form-quoting and MIME/header errors in Samples 4–5. Preserve bytes/diagnostics and dataset-to-result links; keep credentials/network authority with the host. |
| 3 | Shared preservation checks and validator invocation | Samples 1–4 repeated setup/build issues; Sample 4 needs source diagnostic baselines. Reuse source inventories, hashes, allowed-change subsets, and batch SDK checks; await processes before consuming outputs. No parallel general OPC validator or formula evaluator. |
