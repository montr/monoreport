# Feature 014 — XLSX compatibility architecture research

## 1. Status and recommendation

1. **Date:** 2026-10-26. Discovery under [architect-brief.md](architect-brief.md). All design choices below are proposals for Product Owner review. This document creates neither a Feature Spec nor implementation authority.
2. Retain the Open XML SDK, existing Core façades, source/instance identities, final geometry, formula finalization and renderer. The observed failures do not justify replacing the XLSX engine, adopting another workbook library or building a general OOXML compatibility framework.
3. Replace undifferentiated feature rejection with explicit decisions about report content, disposable authoring metadata and coordinate-dependent features. Normalize recognized harmless metadata consistently for analysis and generation; preserve report semantics and fail when their safe transformation is unproven.
4. Keep explicit PrintArea cropping. Recommend allowing sheets without repetition controls and without PrintArea to retain their coordinates and content, including empty and formatting-only sheets. Continue requiring a finite rectangle for controlled repetition. This changes the Feature 012 baseline and needs approval.
5. Retain both Analyzer projections. Recommend adding aggregated vertical-level metadata to array requirements and leaving sample JSON construction in the UI, its only current consumer. Preserve the existing editable-scaffold promise rather than promising universally runnable generated data.
6. **Rich-text clarification — 2026-10-26:** the Product Owner requires whole-cell formatting and forbids rejection solely because partial-character formatting is present. The follow-up [rich-text investigation](rich-text-research.md) supersedes the original deferral recommendation: recommend preserving ordinary rich-text runs for textual results using the expression-start style, while retaining native numeric/Boolean types and whole-cell styling. The detailed formatting/annotation policy remains proposed; no implementation is approved.

## 3. Verified behavior and its classification

| Scenario | Observed current behavior | Classification |
| --- | --- | --- |
| Unchanged repository employees sample | Analysis valid; generation succeeds | Working baseline |
| Workbook AlternateContent containing only an absolute save path | Both operations reject; location points to sheet1 rather than workbook | Compatibility defect; diagnostic attribution defect |
| Workbook revision pointer alone | Both operations reject | Incidental metadata limitation |
| Selection A1:XFD1 with retained active cell B1 | Both operations reject because selection extends beyond B1:D3 PrintArea | View-state limitation, not a report-reference safety requirement |
| Active cell A1 outside PrintArea, selected range retained | Both operations reject independently of the range issue | Additional view-state limitation; clipping sqref alone is insufficient |
| Added empty ordinary worksheet without PrintArea | Both operations return template.xlsx_invalid_print_area for sheet2 | Deliberate Feature 012 restriction that conflicts with the new goal |
| Added formatting-only worksheet without PrintArea | Same PrintArea error, including a stored blank cell at XFD100 | Same restriction; visual emptiness cannot be determined from cell count or dimension alone |
| Field split into rich-text runs | Both operations reject at B2 | Known substitution limitation relevant to ordinary partial-text formatting |
| Whole-cell font change | Analysis and generation succeed; font XML preserved in output | Already supported formatting, not a missing feature |
| Report sheet with controls but no PrintArea | Both operations reject | Boundary remains necessary under current control conventions |

1. [XlsxPackageReader](../../../MonoReport/Services/Xlsx/XlsxPackageReader.cs#L44) resolves PrintArea before loading worksheet contents. It cannot distinguish empty, static and repeated sheets at the point of rejection.
2. [ValidateFeatures](../../../MonoReport/Services/Xlsx/XlsxGeometryPlanner.Static.cs#L78) uses workbook/root-child allowlists, rejects foreign worksheet descendants and extensions, and checks relationships. It does not determine whether each rejected feature affects a retained report or needs relocation. Workbook checks run per worksheet and construct worksheet diagnostics. This is application compatibility validation, not an OpenXmlValidator schema failure.
3. [CropViews](../../../MonoReport/Services/Xlsx/XlsxGeometryPlanner.Static.cs#L154) requires complete range images and unique retained active/top-left cells. These are unnecessarily strict requirements for transient selection and scrolling state. It already handles a list of sqref ranges when every range maps safely; non-contiguous selection is not inherently invalid.
4. Whole-cell style references and untouched rich strings already survive rendering. [Template planning](../../../MonoReport/Services/Xlsx/XlsxTemplatePlanner.cs#L82) rejects rich strings containing parsed tokens. Changing font/color for an entire cell and formatting individual characters inside that cell are materially different capabilities today.
5. Unsafe formula images, discarded required operands, partial/cross-owner merges and ambiguous repetition remain real correctness restrictions. Feature 012's prior unsafe-shift experiment demonstrated that schema-valid output can still contain semantically stale coordinates; removing the compatibility checks wholesale would regress that protection.

## 4. XLSX compatibility policy

1. Separate package/XML integrity checks, template-language checks and transformation safety. A valid OOXML construct can be unsupported by MonoReport; its diagnostic should name the actual construct, part and transformation constraint rather than declare an ordinary Excel save invalid in general.
2. Use a bounded policy in the existing XLSX reader/planners/renderer:

| Content category | Proposed treatment |
| --- | --- |
| Supported report values, styles and formulas | Preserve and transform with existing semantics |
| Recognized disposable authoring state | Remove or normalize using explicit rules; no user repair step |
| Known coordinate-bearing feature with a verified mapping | Transform through final geometry |
| Known feature proven unaffected, including its dependencies | Preserve; unchanged local coordinates alone are insufficient proof |
| Unknown content or unproven affected semantics | Actionable rejection; no silent content loss |

3. Start with the demonstrated absolute-path AlternateContent and transient revision pointer, recognizing namespace URIs, structure and context rather than literal prefixes. Inspect all branches of a candidate wrapper before classifying it as disposable; an AlternateContent containing report content is not equivalent to a save-path wrapper. Remove recognized disposable nodes from generated workbook XML, not merely from the validation inventory. No blanket deletion of AlternateContent, extLst, foreign namespaces or revision-related parts is proposed.
4. Apply the same effective source interpretation to analysis and merge before planning. Keep source stream bytes unchanged. Carry explicit normalization decisions to rendering: the reader currently inventories workbook XML with LINQ to XML, while the renderer updates the SDK workbook DOM. Merely filtering the reader's feature strings would leave metadata, including a local save path, in generated output. Use one authoritative interpretation and deliberate workbook edits; avoid independent recognizers that drift between those representations.
5. Treat selection and viewport position as disposable authoring state. Preserve uniquely representable state; clip a valid range where useful, otherwise reset selection/active/top-left position to a valid retained cell. Update or omit activeCellId consistently. Handle selections entirely outside crop and selections over repeated source cells without rejecting the report. Preserve ordinary view settings. Malformed coordinates/package structures still fail. Frozen/split panes, synchronization and print titles need separate proven boundary mapping and are not silently discarded under the selection rule.
6. Do not add a warning for every removed save-path pointer or reset selection; those are normal output normalization. No new permanent UI, preview preprocessor or mandatory analysis call is needed.
7. Alternative A is the narrow S3-01 patch only. It has low change cost but misses outside active cells, empty sheets and other demonstrated editing cases. Alternative B is the bounded semantic policy above, recommended. Alternative C is permissive pass-through or broad SDK preprocessing; it risks retained stale references or silent loss and is not recommended.
8. The SDK offers markup-compatibility processing, but filtering is based on Office-version support and changes saved content. That does not establish that MonoReport can transform a retained feature. Moreover, the current reader loads raw part streams, so changing OpenSettings alone must not be assumed to normalize that inventory. The conclusion that broad SDK preprocessing is insufficient follows from those documented behaviors and the repository's read/write paths. See Microsoft's [markup compatibility guidance](https://learn.microsoft.com/en-us/office/open-xml/general/introduction-to-markup-compatibility).
9. Excel selection can legitimately contain multiple ranges, with activeCellId identifying the active range. Preserve or normalize it as view state; do not adopt S3-01's proposed prohibition on all non-contiguous selections as a new product restriction. See Microsoft's [Selection reference](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.spreadsheet.selection?view=openxml-3.0.1).

## 5. PrintArea and worksheet retention

1. PrintArea currently has two roles: Excel printing configuration and MonoReport's report/control boundary. Excel itself permits clearing it to print the whole sheet; see [Microsoft's PrintArea documentation](https://learn.microsoft.com/en-us/office/vba/api/excel.pagesetup.printarea). Its universal requirement is therefore a MonoReport design choice.
2. Compare three product options:

| Option | Advantages | Costs |
| --- | --- | --- |
| Exempt only genuinely empty sheets | Smallest behavioral amendment | Needs an emptiness definition; formatting-only and ordinary reference sheets still fail |
| Allow no-PrintArea sheets without repetition controls | Covers empty/static/reference/scalar-only sheets without guessing report boundaries; recommended | Requires explicit identity geometry and optional crop in existing models/planners |
| Infer report bounds for every worksheet | Fewer authoring requirements for repetition | Used range/dimension includes stale formatting and cannot distinguish controls from retained content; risks deletion and changed reports |

3. Recommended rules: a valid explicit PrintArea keeps existing physical crop and A1-relative output; absent PrintArea with no repetition controls retains the sheet in place; controls without PrintArea produce an actionable boundary error; a malformed, duplicate or disjoint explicit area continues to fail. No automatic deletion of sheets or inference of replacement PrintArea is proposed.
4. A sheet without controls may contain scalar expressions; process those without relocating its cells. Preserve empty and formatting-only sheets with names, order, visibility, styles and authored dimensions/settings where supported. Do not fabricate cells, a print rectangle or an A1-only reference domain to represent emptiness. Scan for control-like text using the existing recognition rules before deciding that a sheet is uncontrolled, so malformed/misplaced controls do not disappear silently.
5. Separate optional crop bounds from stored-content extents and from coordinate mapping. Identity geometry must map references to implicit blank cells correctly, even outside the last stored cell. Keep sparse processing; do not materialize the full worksheet grid or trust dimension as a content boundary. Existing non-null PrintArea and PrintAreaNameIndex assumptions occur in reader, geometry, names and renderer; a reader-only exemption cannot implement this policy correctly.
6. Include identity sheets in workbook-wide reference handling. A formula on an unchanged sheet can reference an expanded report; such formulas and names still require final reference mapping and the existing safety checks. Keeping a sheet is not permission to copy unknown relationships or unsupported formula forms blindly.
7. This proposal preserves the existing finite-area convention for repetition. Supporting repetition without an authored boundary, multiple print areas, charts/tables or general print/view reconstruction requires separate concrete scope decisions.

## 6. Analyzer projections and level metadata

1. The [shared requirement builder](../../../MonoReport/Services/TemplateRequirementBuilder.cs) consumes parsed dependencies. Its requirements tree merges paths, preserves first-use order, checks incompatible shapes and describes data access. Occurrences preserve individual uses, original expressions, paths and source provenance. Both are externally documented and asserted in Core/CLI/HTTP tests. Requirements are dependencies, not a homogeneous JSON schema or a list of all mandatory data properties.
2. The actual scaffold consumer is [sampleJson.ts](../../../MonoReport.UI/src/services/sampleJson.ts). CLI and HTTP expose analysis, and the UI parses occurrences but currently does not display them or use them for scaffolding. Their absence from the current UI display does not invalidate the public provenance contract. Removing either projection would break behavior or transfer aggregation/parsing work to consumers without a demonstrated benefit.
3. Runtime probes confirmed employees requirements contain one Employees array with Department, Name and Position. The two loop occurrences retain levels only inside expression strings. The real converter emits one object without a discriminator; generation fails with generation.invalid_data demanding integer $level. Tender fails for the same immediate reason.
4. Compare additive approaches:

| Approach | Assessment |
| --- | --- |
| Parse occurrence expressions in the browser | Duplicates XLSX grammar and normalization; reject |
| Add optional numeric verticalLevel to vertical-loop occurrences | Viable minimal alternative from S3-02; preserves requirements unchanged but couples scaffolding to source-use metadata and requires path joins/deduplication |
| Add optional verticalLevels to array requirements | Recommended: aggregate input-shape metadata where the scaffold already consumes it; no expression parsing or provenance joins |
| Replace analysis with a new schema/sample-data model | Unnecessary migration and another representation for this scope |

5. Proposed verticalLevels means distinct numeric levels referenced by vertical presentation markers for that canonical collection. It is neither an enum of permitted input levels nor a demand that every input contain every level. Actual data may include ancestors unrendered by the template. Horizontal header levels and geometry markers must not populate this property. Keep source occurrences in their existing order.
6. Derive metadata from parsed controls in Core and aggregate it once per canonical collection, including repeated markers, independent regions and sheets. Extend the shared accumulator with only the data it needs; do not make it parse XLSX syntax. An optional property omitted for unaffected arrays preserves DOCX payloads. Update public model, UI parser/types, API schema/descriptions, README and contract tests together if approved. Existing clients ignoring unknown optional properties remain compatible; strict consumers may need updates, so this is not a claim of universal compatibility.
7. Generate one illustrative object per distinct vertical level, containing its numeric $level and the existing union of field placeholders. Use ascending numeric order for those new illustrative records. Employees then has levels 10 followed by 40. A childless vertical collection still needs level-bearing objects rather than the current empty-array fallback. Keep other collection/property ordering unchanged.
8. Do not use source first-seen order as data ancestry. Tender's body marker at level 20 precedes its level-10 footer in the source. [BindHierarchy](../../../MonoReport/Services/Xlsx/XlsxTemplatePlanner.Hierarchy.cs#L8) derives parents from input order and increasing levels; copying footer order into generated data would demonstrate the wrong ancestry. Sorting only newly created illustrative levels is distinct from sorting real input records, which remains prohibited.
9. Union placeholders in each item are a deliberate simplicity tradeoff. They do not claim that every field belongs to every level. Exact field-per-level assignment would require richer scope information, particularly for actual-data ancestors, footer presentation and repeated collections across sheets. Do not reverse-engineer that from source coordinates in the browser.

## 7. Sample JSON ownership and scope

1. Retain the converter in the UI for the recommended scope. It creates editor text and placeholder values; Core supplies parsed semantic facts. No other repository consumer currently requests constructed sample data. CLI analysis and API serialization are consumers of analysis, not existing sample-data generators.
2. An API-owned implementation would put semantics outside the shared library or introduce server-only behavior without another consumer. A Core service would become reasonable if reusable deterministic sample construction or a CLI command is explicitly required; neither is requested by this brief. It would currently add a public service, serialization decisions and transport/UI changes without demonstrated reuse.
3. Correct levels do not make all scaffolds runnable. [GroupRecords](../../../MonoReport/Services/Xlsx/XlsxTemplatePlanner.Rows.cs#L118) requires $path for horizontal intersections and validates Cartesian cardinality. Input-only ancestors, real field values and safe formula images can also require edits. Aggregated requirements do not encode all these conditions, and the current Feature 013 promise explicitly permits manual completion.
4. Recommend retaining that promise, fixing the loss of visible vertical levels and documenting the remaining boundary. If the Product Owner instead wants a minimal generation-ready example for two-axis templates, explicitly add $path/grouping, horizontal cardinalities and ancestor construction to scope and reconsider a Core-owned builder. Do not silently turn S3-02 into a general data synthesizer.

## 8. Decisions requested from the Product Owner

1. **Compatibility policy:** approve bounded normalization of proven harmless authoring metadata and transient selection/viewport state, with semantic safety checks retained? Recommended: yes. This supersedes the narrower S3-01 proposal; arbitrary extensions and unverified advanced workbook features remain unsupported.
2. **Worksheet policy:** allow all sheets without repetition controls to omit PrintArea, preserving their coordinates/content, or exempt only empty sheets? Recommended: the former; keep explicit crop and require a finite boundary for repetition. This is an explicit Feature 012 requirement amendment.
3. **Rich-text fields — updated after Product Owner clarification:** whole-cell formatting is mandatory, partial-character formatting is optional, and its presence alone must not reject analysis or generation. The [follow-up investigation](rich-text-research.md) recommends preserving ordinary text runs, with inserted text inheriting the expression-start style and native number/Boolean results retaining whole-cell style without run-to-cell style synthesis. Those detailed rules and phonetic-annotation treatment remain proposed. The previous recommendation to retain rejection is superseded; flattening modified text is now a permitted fallback if correctly implemented.
4. **Analyzer contract:** approve retaining both projections and adding optional aggregated verticalLevels to requirements, or prefer optional verticalLevel on occurrences to keep the requirement model unchanged? Recommended: aggregated requirement metadata, with no new occurrence field needed for this task.
5. **Scaffold contract:** keep an editable scaffold with correct numeric levels in parent-first illustrative order and union placeholders, or expand to construction of generation-ready grouped two-axis examples? Recommended: the editable scaffold; no promise of inferred actual hierarchy or complete runtime data.
6. **Ownership:** retain UI sample serialization with Core-derived semantic metadata, or require a reusable Core/API/CLI sample-generation capability? Recommended: UI ownership for the only demonstrated consumer; no new endpoint or command.

Test metadata normalization using a real Excel-saved fixture plus adversarial variants containing meaningful alternate content, and assert actual output metadata removal and correct workbook-part diagnostics.

Assert sheet identity/order/visibility, sparse output, absent fabricated PrintArea, preserved explicit crop and rejection of controls without a boundary.
4. Test numeric level metadata through Core/CLI/HTTP and the real UI conversion: employees 10/40, tender footer order 20/10, duplicate controls, multiple regions/sheets, nonconsecutive and negative levels, childless vertical arrays and separation from horizontal levels. Reuse existing DOCX order/conflict/duplicate tests rather than cloning them under a Feature ID.
5. Check representative whole-cell fonts, colors, borders, number formats, rich literals, formulas and structure after ordinary Excel edits, followed by save, analyze, generate and Excel reopen. Package validation alone does not establish calculation, formatting or print correctness. Browser automation and resource-intensive checks require separate authorization under AGENTS.md; none was performed in discovery.
6. No separate backlog work, viewer change, formula evaluation, general workbook-feature implementation, new dependency or Git operation is proposed. The Product Owner has clarified the rich-text acceptance baseline; detailed choices above remain proposals. The original accepted Feature Specs and Implementation Plans have not been modified.
