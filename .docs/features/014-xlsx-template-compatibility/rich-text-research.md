# Feature 014 — Rich-text substitution investigation

## 1. Conclusion and authority

1. **Date:** 2026-10-26. This supplements [architecture-research.md](architecture-research.md) following the Product Owner's clarification: whole-cell formatting is mandatory; partial-character formatting is optional, but its presence alone must not reject analysis or generation. The earlier recommendation to retain the rich-field rejection is superseded. Neither this clarification nor this investigation authorizes implementation.
2. **Recommendation:** include preservation of ordinary rich-text runs during textual substitution in Feature 014. It is a bounded extension of the existing XLSX value pipeline, not a new rendering engine. Flattening all modified rich strings would save some implementation effort, but the existing parser, source XML and DOCX precedent already provide most of the required foundation.
3. Define preservation precisely: unchanged literal text retains its character properties; inserted text inherits the properties at the opening brace of its expression; expressions may span arbitrarily many runs. Different styles inside a placeholder do not define a meaningful proportional distribution across a replacement of another length. A deterministic replacement-style rule is needed for either a simple or an elaborate implementation.
4. Keep existing value-type semantics. A whole-cell unformatted expression yielding a number or Boolean remains native; a string or explicitly formatted/interpolated result can retain rich-text runs. Native scalar output retains the authored whole-cell style, without character-run styling. Do not convert numbers to text or synthesize cell styles merely to preserve placeholder typography.
5. Exact preservation of every rich-string annotation, regeneration of phonetic readings for supplied data, or promotion of run typography into newly synthesized native-cell styles would be a broader requirement. Those capabilities are not prerequisites for ordinary rich-text substitution, and are not recommended for Feature 014. No backlog entry was added: the recommended ordinary-run support need not be deferred, and no demand for those advanced capabilities has been established.

## 2. Evidence and limits

1. Inspected [XlsxPackageReader](../../../MonoReport/Services/Xlsx/XlsxPackageReader.cs#L95), [XlsxTemplatePlanner](../../../MonoReport/Services/Xlsx/XlsxTemplatePlanner.cs#L82), [XlsxPreparedValue and cell models](../../../MonoReport/Models/Xlsx/XlsxTemplatePlan.cs), [binding](../../../MonoReport/Services/Xlsx/XlsxTemplatePlanner.Binding.cs), [per-instance binding](../../../MonoReport/Services/Xlsx/XlsxTemplatePlanner.Instances.cs), and [XlsxDocumentRenderer](../../../MonoReport/Services/Xlsx/XlsxDocumentRenderer.cs). Inspected existing native-value, shared-string, phonetic and rich-literal tests without rerunning the production test suites.
2. The reader already retains original inline XML or a copy of the referenced shared-string item. It concatenates decoded visible text before parsing and excludes phonetic readings from that text. Consequently, an expression split across runs can already be recognized. The explicit planner guard rejects any rich string with tokens, including escaped braces, before binding.
3. PrepareValue currently produces only a type and a flat value. WriteValue writes a plain inline string for textual substitutions; untouched rich strings already survive, and shared strings already become inline strings before the shared-string table is removed. Preserving modified runs therefore needs a prepared rich-text payload, not a new workbook storage strategy.
4. The DOCX [RenderParagraph implementation](../../../MonoReport/Services/DocumentRenderer.cs#L110) already places replacement text in the source text node containing the token start, leaving surrounding formatting in its original nodes. This is a useful product and algorithm precedent. Its Word XML traversal, mutable rendering context and scalar rules must not be imported into XLSX or generalized solely to share a short span algorithm.
5. A temporary diagnostic console in `/private/tmp/feature014-richtext-probe/` referenced the existing Release assemblies. It invoked the existing reader, parser and PrepareValue directly, bypassing the public planner's rejection only in the probe. No replacement algorithm, production patch or modified engine assembly was created. Ten normal binding cases and one unsafe-number case were examined; the probe is not evidence of working public rich-text generation.

| Existing binding with an expression split across bold/italic runs | Observed result |
| --- | --- |
| Whole-cell expression, number 12.5 | Native numeric value |
| Whole-cell expression, true | Native Boolean value |
| Whole-cell expression, string 00123 | Text, leading zeroes retained |
| Whole-cell expression, null | Empty value |
| Strings beginning with = or containing another expression | Text remains inert; no recursive interpretation |
| Literal prefix plus a numeric field | Textual interpolation |
| Explicit numeric formatter | Formatted text |
| Escaped braces surrounding a field | Correct literal braces around the replacement |
| SpreadsheetML-escaped character before a field | Correct decoded text and substitution offsets |
| Unsafe integer precision | Existing generation.xlsx_unsafe_number diagnostic recorded |

6. A separate storage probe confirmed that the installed SDK validator accepts ordinary inline rich runs, native numeric cells and formula cells. It also accepted a deliberately mixed numeric/inline payload, so schema validation alone cannot enforce the intended value semantics. Such a payload is not a proposed solution; current MonoReport storage checks reject inconsistent native/inline storage. Native type and text payload must be asserted explicitly in future tests.
7. No production files, Feature Spec, tests, API, dependencies, Git index/history or backlog were changed. No Excel or browser automation, calculation, production build or resource-intensive test was performed. The complexity assessment is based on source and isolated binding/storage probes; preservation after a real Excel save/reopen remains to be verified during authorized implementation.

## 3. Bounded preservation approach

1. Record decoded visible-text spans and their existing character properties once per source string. Use the same per-text-element SpreadsheetML decoding as the reader; do not index raw XML text using decoded token offsets. Ignore rPh text when constructing the visible span sequence. Store only data in the model; keep decoding and transformations in XLSX services.
2. Continue parsing the concatenated visible string with TemplateLanguageParser. Formatting boundaries must not become language boundaries. Preserve existing expression diagnostics, escapes, requirement extraction and whole-cell NativeField detection. Rich control cells can use the same concatenated text; they need no output rich-text machinery because controls are discarded by crop.
3. Resolve each expression once in the existing PrepareValue path, with its existing data scope, conversion, missing/ancestor diagnostics and precision checks. Compose literal slices and replacements while retaining their source style ownership. Do not resolve fields again in the renderer or infer substitution locations by diffing final text, since repeated substrings, adjacent fields and empty replacements make such a diff ambiguous.
4. For textual output, retain literal fragments in their original styles and assign the full replacement to the run containing the token's opening brace. The suffix after a cross-run token retains its own source style. Escaped braces inherit the first brace's properties. Preserve full rPr XML, including theme/font references and explicit disabled properties, rather than merging properties or constructing a new style registry.
5. Extend the internal prepared value with optional rich-text segments or an equivalent prepared payload. Existing Type and Value semantics can remain available; rich payload and plain value must represent the same visible text. Both static and repeated binding already transport that prepared value, so they need no separate rich-text evaluator. Snapshot or clone XML properties so one source/shared string or output placement cannot mutate another.
6. Extend the renderer to emit prepared rich text for textual cells and retain the existing native-value branch for numbers, Booleans and blank results. Preserve the cell's style index, borders, fill, alignment, number format and sheet geometry. Continue using inline strings, existing SpreadsheetML escaping and whitespace preservation. Untouched strings should keep the existing preservation path; no global string normalization is necessary.
7. An ordered span/token traversal can run in time proportional to source text, tokens and emitted text. Build source spans once and avoid rescanning every run for every character or repeatedly editing the entire string. Retained output segments add memory proportional to their actual output, without another workbook-sized intermediate representation.

## 4. Value types, formulas and annotations

| Result kind | Proposed rich-text behavior | Type/formula consequence |
| --- | --- | --- |
| Native string from a whole-cell expression | Replacement uses the expression-start style | Remains text, including identifiers with leading zeroes |
| Literal text with expressions, or an explicit formatter | Preserve surrounding runs and style inserted text | Remains textual under the existing contract |
| Native number or Boolean from a whole-cell expression | Keep whole-cell style; omit placeholder run formatting | Preserves arithmetic/logical meaning and existing precision checks |
| Null, missing value or unavailable ancestor | Existing empty-value/diagnostic behavior; retain surrounding literal styles where present | No new coercion or warning policy |
| Authored Excel formula | Keep the existing formula pipeline and whole-cell style | No templating of formula text, rich formula result or new calculation behavior |
| Unmodified rich literal | Existing source-preservation path | No avoidable formatting/annotation loss |

1. OOXML represents character formatting as string runs with properties, while formula cells use formula text and optional cached values. Changing native numeric values to strings to obtain run styling could change dependent calculations; changing the formula pipeline is unnecessary. These storage distinctions are documented by Microsoft in [shared strings](https://learn.microsoft.com/en-us/office/open-xml/spreadsheet/working-with-the-shared-string-table?tabs=cs), [inline strings](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.spreadsheet.inlinestring?view=openxml-3.0.1), and [formula storage](https://learn.microsoft.com/en-us/office/open-xml/spreadsheet/working-with-formulas).
2. Retaining whole-cell style does not mean preserving a font stored only in the placeholder's rPr when the result becomes numeric. Promoting that font would require composing/deduplicating cell styles and deciding which run wins when the placeholder spans several styles. That additional behavior is optional typography, not necessary to satisfy the clarified baseline, and is excluded from the recommendation.
3. Phonetic annotations require explicit treatment. Their sb/eb offsets refer to base text, so copied annotations become stale when earlier substitutions change its length. Preserve annotations over unchanged literal intervals and rebase their offsets; remove annotations intersecting replaced token text rather than attaching obsolete readings to new data. Do not invent readings for inserted data. Keep untouched rich literals unchanged. Unicode and SpreadsheetML-escaped text need dedicated offset checks before claiming this behavior verified. See Microsoft's [PhoneticRun reference](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.spreadsheet.phoneticrun?view=openxml-3.0.1).
4. Removing every annotation from a modified cell is not automatically equivalent to losing font formatting: the existing permitted ordinary-function grammar can include PHONETIC, which reads those hints. Thus the minimal alternative should also preserve/rebase annotations on unaffected literal text, or explicitly disclose an additional semantic limitation. Preserving unaffected intervals is a small companion to the same text-edit mapping; reconstructing readings for new data is a different capability. See Microsoft's [PHONETIC documentation](https://support.microsoft.com/en-us/excel/functions/phonetic-function).

## 5. Scope, complexity and risks

| Work area | Minimum with flattened modified text | Preserved ordinary rich text |
| --- | --- | --- |
| Analysis | Remove formatting-only rejection; retain syntax/type/structure checks | Same |
| Data binding and scalar types | Existing flat-value path largely sufficient | Retain existing evaluation; accumulate styled literal/replacement segments |
| Source model | Existing flat string usually sufficient; edit offsets needed if rebasing annotations | Add decoded styled spans or equivalent source descriptors |
| Prepared value and renderer | Existing flat output; annotation handling if retained | Optional rich payload and inline-run emission |
| Geometry, grouping, formula relocation, API and UI | No change needed | No change needed |
| Fidelity | Whole-cell style retained; all partial styling in a changed cell may disappear | Literal styles and replacement style preserved; native scalar exception remains |
| Main regression risks | Accidental type coercion or indiscriminate annotation loss | Span boundaries, escape decoding, shared-source mutation and annotation offsets |

1. The safe minimum is substantially simpler than general rich-text preservation, but for ordinary r/rPr/t strings the difference is a local text-span transformation. Expected production impact is approximately four to six existing XLSX files, optionally one small XLSX-specific helper service, plus focused tests. This is an architectural scope estimate, not a line-count estimate or evidence of a completed patch. There is no need for a public rich-text model, new package, new grammar or change to repeat scheduling.
2. Complexity is moderate and concentrated in bookkeeping, rather than formula or ownership semantics. Shared and inline strings use the same logical representation. Existing per-instance binding handles different values from a shared source; styled results can follow that mechanism. The current renderer already copies source cells and whole-cell styles.
3. The highest risks are indexing encoded rather than decoded text, losing the suffix of a token spanning runs, reinterpreting inserted braces, copying stale phonetic offsets, and mutating shared XML properties across repeated instances. They are addressable with focused behavioral checks and immutable/per-placement payloads; they do not require a general document abstraction.
4. A promise to preserve every source character style inside a replaced token has no unique meaning when the replacement length differs. A promise to preserve all character styling for native numeric/Boolean/formula results is incompatible with keeping those results as rich strings and simultaneously retaining their native meaning. Do not inflate the implementation to meet an undefined fidelity promise; state the replacement-style and native-type rules explicitly.
5. The minimum remains a valid fallback if delivery constraints later require it: accept rich source text, bind correctly across runs, flatten only modified textual cells, retain whole-cell styling and native types, preserve unchanged rich literals, and handle unaffected phonetic ranges deliberately. Removing only the planner guard is a useful source-based observation, not a complete implementation plan or sufficient regression verification.

## 6. Recommendation and decisions remaining

1. Recommend ordinary rich-run preservation in Feature 014 because it adds a bounded text transformation and an internal payload to the existing pipeline. It gives useful fidelity for interpolated labels, formatted output and string-valued fields without changing formulas, geometry or public APIs. The research does not establish a reason to defer that capability to backlog.
2. Adopt the expression-start style rule for replacement text, consistent with existing DOCX behavior. A token may cross styled runs without failure. Preserve surrounding literal styles; do not spread new characters proportionally across styles found inside the old token.
3. Keep native values authoritative: number/Boolean/blank results retain whole-cell styling, with no automatic promotion of placeholder run formatting into cell styles. A textual result can retain the expression's character style. This is the necessary fidelity boundary for the recommendation, not an unapproved type conversion.
4. Preserve/rebase phonetic hints for unchanged literal spans and remove hints attached to replaced token text. Do not promise new-data phonetic readings or exact annotation fidelity for changed content. These rules, plus the two formatting rules above, remain proposed design choices for the eventual Feature Spec; the Product Owner has already settled the prohibition on formatting-only rejection.
5. If the Product Owner instead requires native-cell font synthesis or complete regeneration of annotations, reassess that separately. Such expansion would have substantially greater scope and is not necessary to accept ordinarily formatted templates safely. No automatic permission request or implementation start follows from this recommendation.

## 7. Focused verification after implementation approval

1. Verify shared and inline sources with a field inside one run, a field spanning differently styled runs, literal prefix/suffix, adjacent fields, escaped braces split across runs, empty replacements, whitespace/newlines, theme-based properties and Unicode/SpreadsheetML escapes. Assert visible text and surviving character properties, not exact serialization or run counts.
2. Reuse native-type tests and extend representative rich-source cases for number, Boolean, string, formatted number, null and strict missing values. Assert cell storage type, style index, absent inappropriate formula/inline payload and unchanged unsafe-number behavior. Verify inserted equals signs and braces remain inert.
3. Exercise a repeated report using one shared source string with different scoped values, including a group/header case, to detect cross-instance mutation. Use existing geometry/formula fixtures; do not duplicate the entire nested-report matrix for text-only behavior.
4. Check untouched phonetic hints, offsets after a changed-length replacement before a hint, hints intersecting a replaced expression, and hints associated with escaped/non-BMP source text. A PHONETIC-bearing workbook needs semantic assertions; schema validity is insufficient. Actual calculated results remain an external spreadsheet verification item.
5. Confirm Analyzer requirements/occurrences and diagnostics remain the same for equivalent plain and richly formatted expression text. Invalid expressions and unsupported structural tokens must still fail for their real cause.
6. After source-level checks, use a representative Excel-authored file for visual save/reopen acceptance. Neither the binding probe nor SDK validation performed here establishes Excel visual or calculation compatibility. No new test infrastructure is needed for these checks.
