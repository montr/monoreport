# Feature 014 — XLSX Template Compatibility — Implementation Plan

## 1. Authority and scope

1. **Date:** 2026-10-26. **Plan status:** Revised following the completed independent review and Product Owner clarifications; awaiting Product Owner approval. Implementation has not started. This document contains one implementation stage, **Stage 1**; its internal work areas are not separate stages or approval gates. Submit the entire completed stage for implementation review.
2. The behavioral baseline is the [Feature Spec](feature-spec.md), identified as approved in the planning request. Use the [architecture research](architecture-research.md) and [rich-text research](rich-text-research.md) for implementation rationale only where consistent with that specification. Earlier proposals to reject multiple-range selections or flatten modified rich text do not satisfy the approved behavior.
3. Deliver bounded compatibility for recognized Excel authoring metadata, worksheet view normalization, optional PrintArea on uncontrolled sheets, and rich-text substitution. Preserve native values, supported formulas, formatting, source bytes, actionable diagnostics and failure without a partial report through existing Core, CLI and HTTP interfaces.
4. Analyzer schema/requirement enrichment, vertical-level metadata, Sample JSON construction and Feature 013 finding S3-02 belong to Feature 015. No UI, preview, endpoint, CLI command, formula evaluator, dependency replacement, general OOXML compatibility framework or Excel automation is included.

## 2. Existing implementation and design constraints

1. [XlsxPackageReader](../../../MonoReport/Services/Xlsx/XlsxPackageReader.cs) currently requires PrintArea before reading sheet content. It retains source cell XML and shared-string items and decodes visible string text, excluding phonetic readings. [XlsxTemplatePlanner](../../../MonoReport/Services/Xlsx/XlsxTemplatePlanner.cs) then rejects rich strings containing tokens. These are targeted compatibility changes, not reasons to replace parsing or the XLSX engine.
2. [XlsxTemplatePlan models](../../../MonoReport/Models/Xlsx/XlsxTemplatePlan.cs) and [XlsxWorkbookPlan models](../../../MonoReport/Models/Xlsx/XlsxWorkbookPlan.cs) assume finite crop bounds. Geometry, formula/name handling and output also depend on these bounds. Separate an absent crop from sparse stored-content extents and the valid worksheet reference domain; an empty sheet must not become an A1-only reference domain.
3. [Static geometry and feature validation](../../../MonoReport/Services/Xlsx/XlsxGeometryPlanner.Static.cs), [report planning](../../../MonoReport/Services/Xlsx/XlsxGeometryPlanner.Reports.cs), expansion, cell emission and reference projection must use one consistent retention policy. Preserve the existing source/instance identities, merge ownership and final geometry safety checks.
4. [XlsxTemplateHandler](../../../MonoReport/Services/Xlsx/XlsxTemplateHandler.cs) already performs shared source planning and preflight for analysis/generation. [XlsxFormulaPlanner](../../../MonoReport/Services/Xlsx/XlsxFormulaPlanner.cs) finalizes workbook-wide references before [XlsxDocumentRenderer](../../../MonoReport/Services/Xlsx/XlsxDocumentRenderer.cs) writes output. Keep this ordering and the existing recalculation policy.
5. Extend internal data models only as necessary for optional crop, normalization decisions and prepared rich text. Business logic stays in XLSX instance services with supplied dependencies. Prefer extending existing services; add a small XLSX-specific helper only where it makes the span transformation clearer. Do not introduce a public rich-text model, style registry, generic document abstraction or separate evaluation pipeline.

## 3. Test inputs and verification policy

1. Automated Feature 014 verification must run offline with installed/restored dependencies and must not read user-facing Samples, examples manifests, external URLs, Microsoft Excel or other external services. Expected values and JSON inputs are test-owned. A user sample may change, disappear or move externally without changing these test expectations.
2. Reuse [XlsxFixture](../../../MonoReport.Tests/Services/XlsxFixture.cs) and the existing nested/two-axis builders where practical. Generate small workbooks and malformed variants programmatically; use parameters for equivalent cases rather than one workbook or test per permutation. Name new test classes by the subsystem, such as package compatibility, worksheet retention or rich-text substitution; name integration scenarios by behavior rather than Feature IDs.
3. Start with one dedicated, sanitized Excel-saved XLSX fixture under a subsystem-named directory in MonoReport.Tests/Fixtures, with its own data and a short provenance/expectations note. Preserve the exact Excel save structures under test. Record Excel version, save/edit scenario and relevant package parts; use a harmless test path in any absolute-path metadata. Reuse this fixture across Core compatibility checks, creating isolated in-memory variants for negative cases. Add another static workbook only if a distinct Excel-specific behavior cannot be represented faithfully by this fixture or a programmatic variant. Existing transport contract tests can keep simpler generated inputs.
4. Obtain the Excel-saved fixture as an initial manual save if no maintained genuine fixture is available, before the automated checks that consume it. Keep this and final reopen acceptance a small manual activity. If Excel access or the required input is unavailable, continue independent programmatic Core verification and mark the Excel-saved fixture check and affected manual acceptance criteria Pending. Research files under temporary directories are evidence, not permanent test dependencies. Do not describe an SDK-authored or XML-injected package as proof of an Excel save. Automated tests consume the maintained test-owned fixture and never invoke Excel to create it; unavailable fixture checks must be reported as pending, not passed or silently omitted.
5. Existing XLSX smoke tests in Core, CLI and HTTP use [TenderSampleFixture](../../../MonoReport.Tests/Services/TenderSampleFixture.cs), which reads Samples. Decouple only existing tests needed for selected verification, using generated test-owned inputs or a frozen dedicated fixture and the minimum necessary helper/project changes. Keep comprehensive value/formula/formatting assertions in Core and preserve existing transport contract assertions in CLI/HTTP. Do not extend those transport tests with Feature 014 compatibility scenarios or require them to share the Excel-saved compatibility fixture. Avoid unrelated test renaming, reorganization or wholesale DOCX/UI fixture migration.
6. Selected automated verification must both build and run with user-facing Samples and examples manifests unavailable. Audit runtime reads, shared helpers, test-project copy items and relevant build dependencies; a test filter alone does not prevent missing unconditional copy inputs from breaking the build. Remove or replace required copied inputs with test-owned inputs, and condition or remove unrelated optional copy items only where necessary for these selected builds. Verify using fresh outputs so stale copies cannot conceal a dependency. Do not skip selected required tests to obtain a passing result. Record unrelated legacy sample-coupled tests outside the selected set as unverified; their refactoring is outside scope.
7. Assert visible text, value/storage types, styles and character properties, references, sheet identity and geometry. SDK package/schema validation complements these semantic assertions; it does not prove them. Avoid byte-identical ZIP/XML expectations, fixed rich-run counts, duplicate transport matrices, benchmarks or new test infrastructure.

## 4. Stage 1 — Implement and verify XLSX template compatibility

### 4.1. Work order and dependencies

1. Establish the reusable test inputs alongside the work they verify. Implement section 4.2 first so effective source normalization and view handling can be reused by section 4.3. Section 4.4 can be developed independently of optional PrintArea, then exercised on both sheet policies once section 4.3 is complete.
2. Complete sections 4.2–4.4 before the combined verification and manual acceptance in sections 4.5–4.6. Each work area has focused acceptance checks, but none requires an intermediate Product Owner approval or separate implementation review. The entire Stage 1 is reviewed after completion.

### 4.2. Recognized metadata and worksheet views

1. Recognize the observed workbook save-path AlternateContent and transient revision pointer by namespace URI, structure and workbook context, not prefix spelling. Inspect every Choice/Fallback branch and relevant attributes/children before classifying a wrapper as disposable. Unknown or meaningful alternate content, extension content and relationships remain subject to existing safety rejection; do not delete them wholesale.
2. Apply one authoritative classification in the common analysis/generation source path. Carry explicit removal decisions through the internal plan so rendering removes the corresponding workbook DOM nodes, including the embedded path. Filtering the reader's feature inventory alone is insufficient because it and the renderer use different XML representations. Leave caller-owned bytes unchanged.
3. Attribute workbook errors to the actual workbook part and worksheet/cell errors to their source context where available. Retain existing diagnostic contracts and useful remedies; do not manufacture a worksheet location for a workbook-only feature or add warnings for routine normalization.
4. Update view handling to preserve uniquely representable selection and viewport state. Map/clip valid selected ranges to retained output where useful; when state is wholly removed or has ambiguous repeated images, reset it deterministically to a valid output position. Keep activeCell within its selected range and update or omit activeCellId consistently. A fallback position on an empty sheet must not create a stored cell.
5. Validate coordinate syntax and structural consistency before fallback. Valid full-row, multiple-range, outside-crop and repeated-cell selections must succeed. Preserve ordinary view attributes. Pane presence, pane associations, synchronization anchors, print titles and manual page breaks retain their existing proven-support boundaries; selection normalization must not silently remove them or relax formula/reference safety.
6. **Focused acceptance:** the genuine Excel-saved fixture passes public analysis and generation; output omits recognized path/revision metadata and source bytes remain unchanged. Parameterized variants verify alternate prefixes, meaningful content in an otherwise familiar wrapper, unknown extensions/relationships and malformed XML with correct source-part diagnostics. A compact view matrix checks retained, full-row, multiple-range, wholly removed and repeated-cell selections, including activeCellId/top-left consistency. Compare report values, geometry and formulas against the same input without disposable view state. Retain representative pane/synchronization rejection checks and one supported unchanged-view case.

### 4.3. Optional PrintArea and complete worksheet retention

1. Distinguish a missing PrintArea from an invalid explicit definition. A valid explicit area keeps physical crop and A1-relative output even without repetition. Malformed, duplicate, disjoint or otherwise invalid explicit areas continue to fail. Keep worksheet-local and supported unambiguous workbook-scoped area resolution.
2. Read sheet content before deciding that absent PrintArea is permitted. Reuse existing control-prefix recognition across all source cells, including rich text, to detect valid, malformed and misplaced control-like cells. Controls require a finite boundary; bad controls cannot cause fallback to an uncontrolled sheet. Report the missing boundary or control defect with the available sheet/cell context.
3. Represent uncontrolled no-PrintArea sheets with identity mapping across valid Excel coordinates and no crop/name index. Update cell selection, preflight, static planning, report planning, row/column emission, setting transforms, name handling and rendering accordingly. Keep processing sparse; do not enumerate the worksheet grid, infer a crop from dimension/stored cells, or fabricate cells, rows or a PrintArea.
4. Preserve sheet IDs/names, order, visibility, existing cells and coordinates, scalar substitution, empty/formatting-only rows and cells, authored row/column sizes, styles, supported merges and settings. Do not rewrite an identity sheet's dimension as a full-grid print rectangle. Ensure mixed workbooks use identity handling for these sheets even when another sheet forces the repeated-report path.
5. Update static reference validation, range/reference projection and final formula/name relocation to respect optional crop. Identity mapping includes implicit blank cells beyond stored extents, including an otherwise empty sheet. Still finalize formulas and supported names on unchanged sheets that reference cropped/expanded reports. Do not treat identity sheets as opaque package copies.
6. Preserve existing failures for discarded, disjoint, empty or ambiguous retained references, unsupported reference syntax, unsafe merges and unproven settings. Accepting an absent boundary must not weaken the safety policy of explicit crop or repetition.
7. **Focused acceptance:** one small generated mixed workbook contains an explicitly cropped repeating report plus no-PrintArea empty, formatting-only, scalar and reference sheets with varied visibility and dimensions. Assert sheet identity/order, coordinates, values/styles, preserved sparse content, no invented PrintArea/cells and correct formulas/names in both directions between identity and report sheets. Include implicit-blank references beyond stored extents and a near-limit coordinate without allocating intervening cells. Exercise an all-uncontrolled workbook as well as the mixed repeated path. Parameterize missing-boundary controls, malformed/misplaced controls and invalid explicit areas; retain one unsafe cross-sheet reference failure with no report returned.
8. Amend existing tests that require PrintArea universally or encode the superseded selection behavior. Keep their still-valid invalid-area/control/crop assertions; avoid duplicating the existing nested geometry/formula matrix.

### 4.4. Rich-text substitution, native values and annotations

1. Extend source string data with decoded visible-text spans and snapshots of ordinary run properties. Decode each SpreadsheetML text element once, exactly as for parser input; exclude phonetic readings. Token offsets refer to this decoded text, not raw escaped XML. Use the existing language parser for fields and escaped braces across run boundaries; remove the formatting-only rejection while retaining syntax/context/control validation.
2. Extend XlsxPreparedValue with an optional internal rich payload whose visible text agrees with its plain value. Resolve each field once through PrepareValue with the existing scope, formatter, missing-value and precision rules. Build literal/replacement segments directly from tokens and source spans, without diffing final text or evaluating again in the renderer.
3. Preserve literal character properties; assign the entire textual replacement to the expression opening brace's properties and an escaped brace to the first brace's properties. Preserve the suffix after cross-run expressions, adjacent fields, empty replacements, whitespace, line breaks and Unicode. Snapshot/clone complete run properties, including theme references and explicit disabled properties, so shared sources and different output instances cannot mutate one another.
4. Render prepared textual output as inline rich strings using existing escaping and whitespace rules. Preserve unchanged rich literals through their existing path. Keep the cell style index and referenced whole-cell fonts/colors, fills, borders, alignment and number formats. Use the same prepared payload through static AttachValues and repeated BindInstances, including headers and footers; add no separate rich evaluator or geometry path.
5. Whole-cell expressions without an explicit formatter retain native number/Boolean/empty results and whole-cell style, without an inappropriate inline-string payload or synthesized cell styles. Strings, interpolation and explicit formatters retain their existing textual semantics. Inserted equals signs and braces remain inert. Formula cells stay in the existing formula pipeline, with no rich result/template evaluation and no fabricated caches.
6. Preserve/rebase phonetic ranges wholly associated with unchanged literal intervals, including after changed-length replacements. Remove ranges intersecting replaced expression/escape text; do not attach old readings to inserted data. Preserve applicable phonetic properties and unchanged literal annotations. Use one edit-offset mapping with validated source/output positions; verify the SpreadsheetML offset convention against the Excel-saved evidence, especially surrogate pairs and encoded characters.
7. Keep span/token composition proportional to source spans, tokens and emitted output. Build source spans once and reuse them across occurrences; avoid repeated whole-string edits, per-character rescans or a second workbook-sized representation. No benchmark harness is required.
8. **Focused acceptance:** parameterized shared/inline cases cover a field within one run and across differently styled runs, surviving prefix/suffix styles, adjacent fields, cross-run escaped braces, changed/empty replacements, whitespace/newlines, theme properties, Unicode and SpreadsheetML escapes. Assert text and effective surviving properties rather than exact segmentation. Equivalent plain/rich input produces equivalent Analyzer requirements/occurrences and real syntax/context diagnostics.
9. **Focused acceptance:** extend the existing native-scalar scenarios with representative rich sources for numeric/Boolean/string/null/missing values, formatted output, unsafe precision and inert inserted text. Assert cell type, value, style and absence of inappropriate formula/string payloads. Reuse one small repeated report with shared source strings and distinct scoped values in body/header/footer placements, covering vertical and horizontal instances without duplicating every nesting depth.
10. **Focused acceptance:** check untouched phonetic hints, shifted hints after a replacement, hints intersecting replaced text, and decoded/non-BMP offset cases. Validate ranges and retained readings explicitly, including a supported PHONETIC-bearing formula; calculated results remain part of manual Excel acceptance rather than an offline evaluator.

### 4.5. Combined behavior and focused regression verification

1. Keep comprehensive XLSX compatibility and generation verification in Core, including public TemplateAnalyzer and MergeEngine coverage. Reuse a test-owned compatibility workbook for a combined Analyze → Generate scenario with recognized metadata, a normalized selection, optional-PrintArea reference content, rich textual substitution and a native value with a dependent supported formula. Assert expected values/types, essential character/whole-cell formatting, formulas/names, crop/identity coordinates, recalculation flags, metadata removal and unchanged source bytes on success/failure. Do not replay this scenario or the work-area behavioral matrices through CLI/HTTP.
2. Reuse existing CLI/HTTP transport contract tests where sufficient for binary output, MIME/filename, warning/error serialization and no partial success. Existing CLI output-file sentinel and HTTP error-without-document assertions provide transport failure coverage; they do not need Feature 014-specific invalid workbooks. Add or adjust a transport test only for an identified uncovered transport contract regression, not to repeat XLSX semantics already verified in Core. Limit input/helper/project changes to the sample independence required by section 3.
3. Run focused Core package/view, retention/reference and rich-text tests first, then the affected existing Core crop, static scalar, shared-formula/name, merge/ownership, nested/two-axis and analyzer diagnostics cases. Reuse selected existing CLI/HTTP contract checks and existing programmatically generated DOCX regression cases covering analysis/substitution and routing/composition. Confirm the selected projects build and tests run with Samples and examples manifests unavailable, as required by section 3, item 6. Reuse existing precision, missing-value and transport cases instead of cloning their entire matrices.
4. Validate representative generated packages with the installed Open XML SDK validator alongside semantic assertions. Inspect actual output workbook XML for metadata removal, valid views, formula cache/chain cleanup and no synthetic PrintArea. Confirm analysis and generation agree on data-independent source errors; retain a data-dependent unsafe-image case showing why valid analysis cannot guarantee generation success.
5. Keep verification offline, with no package downloads during test execution, real network hosts, browser automation, Excel automation, load tests or broad solution-wide runs by default. Expand only when failures or affected shared behavior justify it. Resource-intensive/disruptive operations remain subject to project authorization; none is a planned verification requirement.
