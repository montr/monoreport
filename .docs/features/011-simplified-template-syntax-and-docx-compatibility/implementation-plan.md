## 3. Design and complexity boundaries

1. Retain the existing pipeline and instance services: story/package reading, source planning, shared data-independent compatibility preflight, requirement aggregation, then rendering. Use bounded planning passes inside the current planner. Keep XML decisions DOCX-specific and all mutable source maps, deletion sets, reservations, and counters local to inspection/generation operations.
2. Collect eligible source spans and delimiter candidates before ordinary language tokenization. Reuse the parser's case/escape precedence through a small shared classification/scanning primitive; the planner supplies placement, source-root, and container information. This primitive must tolerate arbitrary Raw payload without invoking path/formatter parsing. It is not another regex parser or an error-producing parse whose errors are later discarded.
3. Match Raw in source order within one independent story root. An eligible opener may provide a paragraph container and, where valid, a dedicated-row candidate. Accept the first exact, unescaped close that forms a permitted sibling layout with that opener. Paragraphs must have the exact same parent; rows must be distinct dedicated siblings of the same table. A row's marker must be wholly in one paragraph in one cell, with the remaining visible content empty; concatenating fragments from several paragraphs/cells cannot create it. Never promote to a common ancestor.
4. While Raw is open, scan only for an eligible close and maintain the existing Word field state. Additional openers, malformed expressions/braces, other controls, and inline/mixed-content/wrong-parent/escaped/opaque closing lookalikes are literal. Once a close qualifies by placement, lock that extent before compatibility validation: an unsafe annotation or merge is an error at that extent, not permission to seek a later close. An opener with no eligible close produces an unclosed-Raw diagnostic, with no language errors for its payload. Active invalid openers and stray/invalid closers outside Raw produce shared structural diagnostics.
5. Build Raw as a childless literal node in the existing structural tree. Keep its body source elements, delimiters, and location for containment and preflight. Only active tokens outside Raw reach `BuildBlocks`/`BuildDependencies`; Raw delimiters produce no dependency or public occurrence. Literal controls cannot change the outer control/context stack. Validate that each Raw node lies wholly within one enclosing body or branch. Keep original source order for following dependencies and diagnostics.
6. **D3 feasibility:** source-root pairing and unchanged outside endpoint/attachment ownership already support simple enclosure. Existing `Ranges_local_to_sibling_roots_and_enclosing_operations_preserve_ownership` combines local and enclosing cases; separate the local part so enclosure remains a valid regression. Validate completeness/order for affected enclosures and preserve XML in place. No range reconstruction, endpoint relocation, branch projection, or new general interval framework is planned.
7. **D2 feasibility:** reuse normalized comment IDs, loaded definitions, source locations, and package XML reference information to classify removed versus surviving attachments. A bounded source deletion set and a lookup of surviving uses should suffice for standard ranged/point comments. Inspected archived comment fixtures have an ordinary `word/comments.xml` part and no additional comment metadata parts; that is feasibility evidence, not proof of all annotation variants. Preserve definitions required by surviving attachments/references and change only definitions proven safe to delete.
8. **Conditional stop for D2/D3:** if a concrete source cannot be handled by these simple source classifications and requires substantial linked-metadata machinery, relocation/reconstruction, a general cleanup graph, or similarly substantial new range logic, stop that implementation work and present the case to the Product Owner. Explain the practical value, the bounded implementation option and cost, document/reference/data-loss risks, and the simpler authoring remedy with actionable rejection. For D3, recommend rejection if preservation is no longer simple. For D2, do not silently replace approved safe deletion with blanket rejection. Obtain confirmation before changing the contract or introducing machinery; record the decision in the existing Feature documents. No such material blocker is established by current inspection.
9. Required work is the sequence below. Optional tree-based dependency traversal and moving the remaining DOCX allocator out of `MergeContext` are excluded from the baseline: keeping the existing dependency stack and allocator location is sufficient if verified. Do not introduce another parser, OOXML framework, product format, public schema, UI layout, coverage threshold, field evaluation, repair facility, or unrelated refactoring.
