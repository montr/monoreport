# Feature 011 — Architecture assessment

1. Updated on 2026-10-19 following Product Owner approval of D1–D6 and the complete revised [Feature Spec](feature-spec.md). D6 is the follow-up decision allowing supported blocks to empty a table cell while requiring targeted rendering-time paragraph synthesis. The [compatibility policy](../../../docs/docx-template-compatibility.md) incorporates those decisions. This assessment is not Feature acceptance or Git authorization.
2. The assessment evidence was source/test inspection and read-only sample XML inspection. Subsequent implementation and verification evidence is recorded in the approved [Implementation Plan](implementation-plan.md); this document does not duplicate that status.

## 1. Assessment

1. The Feature is feasible within the existing services. Closing-marker replacement is small; Raw requires a change before ordinary tokenization, and compatibility simplification requires stronger rejection before removal of identity transformations. No second template engine, general OOXML framework, public analyzer schema change, or format abstraction is necessary.
2. The reviewed ambiguities are now resolved in the target documents: delimiter precedence, safe Raw annotation deletion, simple enclosing-range preservation, Raw-specific merge safety, and the existing revision footprint. The specification also explicitly addresses affected links, retained permissions/drawing IDs, former closing-marker scalar semantics, and focused acceptance coverage.
3. The intended compatibility reduction deliberately removes accepted Feature 010 local comments/bookmarks in `For`/`If` bodies or deleted markers and local/ancestor anchor remapping. It retains simple enclosing ranges and adds safe delimiter-local annotation deletion specifically for Raw. This is a breaking Feature 011 product change, not a Feature 010 defect. Preserve ordinary formatting, tables, images, numbering, opaque content, supported stories, diagnostics, and operation isolation.

## 3. Recommended architecture

1. Keep the existing pipeline: package/story inspection, shared DOCX planning and compatibility preflight, dependency aggregation, then rendering from the source plan. Keep DOCX identity logic out of the format-neutral grammar; supply dependencies through constructors and keep allocations and mutable maps per generation operation.
2. Use the existing eligible-text adapter and a shared delimiter classifier to establish Raw extents in source order before ordinary parsing. This may use bounded planning phases; parse-once means no repeated grammar evaluation of clones or inserted data, not a mandatory single physical XML traversal. Do not introduce an independent regex grammar or parse arbitrary Raw payload and discard its errors afterward.
3. Represent Raw as a literal structural node using the existing sibling-container model. It contributes no JSON dependency, occurrence, loop context, warning, scalar operation, or escape operation. Active outer controls continue to contribute dependencies. Expressions after Raw must resume the original loop/root/parent context and source ordering.
4. At render time, retain the entire Raw body and remove only its marker containers through the current source-to-output map. An outer loop may clone it and an outer conditional may exclude it. After any Raw, `For`, or `If` removal directly affects a table cell, add one bare paragraph only if that cell is empty or ends in a nested table. Perform this through one shared renderer helper and leave cells needing no correction byte-semantically unchanged. No content inside Raw is parsed again. Drawing identities in outer copies still need allocation; semantic preservation does not mean identical ZIP bytes or frozen IDs in repeated drawings.
5. Keep Word-field state tracking and hard boundaries at hyperlinks, fields, drawings, and content controls while locating delimiters. A delimiter hidden in a field cache or `w:sdt` does not close Raw. Continue compatibility inspection independently of expression opacity, including forbidden ranges hidden in opaque content inside a `For`/`If` body and recognized revisions inside Raw or controls.
6. Replace local bookmark/comment copying inside `For`/`If` with data-independent rejection while preserving valid enclosing ranges in place. Reject internal links whose own location is inside the operation even when the target is stable; reject links to removed or invalidated targets without remapping. Preserve relationship-based external links, including fragments. Opaque field-based links and references remain unevaluated; do not add field-code analysis.
7. For standard delimiter-local Raw annotations, reuse source identity pairing and the already loaded comment definitions to establish what disappears and what survives. Removing complete attachments and updating only their no-longer-needed definitions appears bounded; no clone IDs, relocation, or package garbage collector is needed. Retain definitions used by surviving attachments/references and inspect the existing package reference map for targets invalidated by deletion. This is source-based feasibility, not proof for every annotation metadata variant. If additional linked metadata makes safe deletion require significant machinery, D2 requires a tradeoff report rather than an invented repair mechanism or silent rejection.
8. Use a Raw-specific row deletion safety check. The current `CreateBlock` rejects any vertical merge across a row block's entire footprint; reusing it unchanged for Raw would contradict D4. Validate only whether removal of delimiter rows damages surviving merges or required structure. Leave body merges intact and retain the current conservative check for `For`/`If`. Do not add merge or section-property repair.

## 4. Product Owner decision record

| Decision | Disposition of original recommendation | Approved requirement and consequence |
| --- | --- | --- |
| D1 — delimiters and literals | **Accepted.** | Exact dedicated paragraph/supported row delimiters; first structurally valid unescaped close; other lookalikes and all contained template constructs are literal. No nesting or language diagnostics in the body; DOCX checks still apply. |
| D2 — Raw annotations and links | **Modified, with complexity condition.** The original blanket rejection of delimiter-attached annotations was not adopted. | Preserve valid unaffected constructs; remove complete annotations/bookmarks wholly on one deleted delimiter safely, including associated references/definitions. | D3 — enclosing ranges | **Alternative conditionally accepted.** The original recommendation to reject every overlapping range was not adopted. | Preserve fully enclosing valid ranges with intact outside endpoints/attachments in place. If substantial extra logic is necessary, recommend actionable rejection and seek confirmation rather than changing behavior unilaterally. |
| D4 — Raw tables/merges | **Modified.** The blanket row-merge rejection was not adopted for Raw. | Support multiple paragraphs in one cell and complete tables, including merges. Reject only unsafe delimiter-row or required-structure deletion. No automatic merge repair, section relocation, or general repair. Existing `For`/`If` restrictions remain. |
| D5 — revisions | **Accepted.** | Keep current revision families and story inspection footprint, including Raw/inactive branches/controls, with existing exclusions. No package-wide expansion; the Track Changes setting alone is allowed. |
| D6 — empty table-cell results | **Accepted follow-up.** | Raw, `For`, `If`, and combinations may remove all cell paragraphs. Analyzer does not reject that possibility. 1. D1–D5 were approved in the Product Owner's architecture continuation request on 2026-10-19; D6 was approved in the Feature 011 follow-up on the same date. All are incorporated into the specification and policy. They do not constitute Feature acceptance or Git authorization.
2. No additional material product decision is currently established by source inspection. D3's simple preservation already matches the ownership model and existing enclosure regressions; the stricter overlap check originally recommended is unnecessary.
3. D2 remains a bounded feasibility condition: if safe cleanup of a concrete annotation variant needs significant additional metadata handling, report its user value, deletion/reference risks, a narrowly scoped implementation option, and actionable rejection as the simpler alternative. Obtain the Product Owner's decision before adding machinery or narrowing support. D3 has the equivalent confirmation condition if simple preservation proves insufficient. Neither condition is currently evidence of a blocker or permission to drop approved cases.

## 5. Required, optional, and excluded work

1. **Required under the approved decisions:** change the shared closing-marker grammar and maintained assets; suppress all language processing inside valid Raw; preserve outer semantics and simple enclosing ranges; support safe delimiter-local annotation deletion and Raw merge preservation; enforce shared rejection of unsafe cases; and apply the narrow shared rendering-time correction for affected empty or nested-table-ending cells. Keep opacity, relationships, drawing safety, permissions, independent note roots, and deterministic no-partial-output diagnostics.
2. **Required deletion after rejection:** remove bookmark/comment ID allocation used solely for rejected copies, bookmark name allocation, `IdentityFrame`/`ActiveIdentities`, dynamic anchor remapping, `CloneComment`, and recursive comment-definition copying. Remove dead model members after tracing usages. The earlier categorical removal of `SavePackageIdentities` is superseded: remove cloning-specific persistence, retaining or replacing the narrow comments-part writeback D2 needs. Package drawing reservations and permission allocations must survive.
3. **Optional simplifications:** derive dependency context from the validated structural tree instead of maintaining a separate linear control stack; reduce cross-part anchor binding work because affected targets are rejected directly; move the remaining DOCX copy allocator out of the shared-looking `MergeContext` if that reduces coupling without a new framework. None is a reason for a broad rewrite.
4. **Retained scope:** permission-range matching and local ID allocation are explicit requirements in specification section 5.7 and the policy. They are not an unresolved simplification decision. Reducing that support would be a separate product change requiring approval.
5. **Out of scope:** comment/bookmark relocation or repair; dynamic targets; field evaluation or TOC refresh; content-control binding repair; revision acceptance, normalization, or rendering; general OOXML validation/repair infrastructure beyond D6's single empty-paragraph correction; inline Raw; nested Raw; horizontal/cell repetition; merge-group support; numbering restarts; new formats; legacy syntax aliases. Existing opacity is not permission to ignore a known integrity violation caused by an outer supported operation.

## 6. Incorporated documentation changes

1. Specification section 4.1 now states former closing spellings are ordinary scalar paths, exact Raw is reserved, and existing case/escape semantics remain. Historical evidence is preserved while maintained executable fixtures migrate.
2. Sections 4.2 and 5 incorporate D1–D6: literal delimiter precedence, safe annotation deletion, simple enclosing-range preservation, Raw-specific merge/structure checks, the retained revision footprint, and targeted empty-cell normalization. The policy mirrors these choices and explicitly distinguishes Raw delimiter deletion from `For`/`If` body transformation while sharing the narrow post-removal correction.
3. Sections 5.3 and 5.7–5.9 resolve affected internal links, permissions, package-wide drawing reservations, and the precise clone/remap removal boundary. Fields and controls remain opaque; neither anchor repairs nor package-wide revision inspection are introduced.
4. Section 7 provides testable acceptance criteria grouped by behavior, using existing meaningful regressions and proportionate surface checks. Section 9 records architectural constraints and conditional escalation; section 10 records the approvals granted after this assessment.
5. The policy names Feature 011 as its approved contract while preserving Feature 010 authority and evidence. Implementation changes and executed evidence are recorded in the Implementation Plan rather than retroactively presented as architecture-assessment work.
