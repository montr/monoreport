# Feature 018 — Architecture Assessment

**Status:** Accepted (2026-11-09). Architecture and Feature Spec were approved by the Product Owner on 2026-11-08; the completed Feature and all six implementation stages were accepted on 2026-11-09. The unresolved large-Dataset Chrome crash is tracked in a [separate follow-up task](../../tasks/large-dataset-chrome-crash.md), not accepted as correct behavior. The assessment below retains its architectural decisions; subsequent approved UI refinements and final acceptance are recorded in the [review history](implementation-review.md).

## 1. Authority and boundaries

1. This architecture implements the [approved Feature Spec](feature-spec.md). The [DOCX compatibility contract](../../../docs/docx-template-compatibility.md) and [XLSX compatibility contract](../../../docs/xlsx-template-compatibility.md) remain authoritative. No supported syntax, input domain, generation restriction, or generation diagnostic behavior changes.
2. Reuse the previous investigation findings: requirements describe dependencies rather than a schema; XLSX occurrences flatten distinct record scopes; DOCX evaluation currently accompanies XML rendering; Generate already owns runtime validation. Sample generation needs source structure, not a new dataset validator.
3. Keep data-aware Analyze, JSON Schema, validation extraction, automatic Generate, CLI sample commands, caching, public compiled templates, and unrelated diagnostic improvements out of scope. Existing CLI Analyze naturally serializes additive occurrence hints; no new CLI operation is required.
4. Use the existing MonoReport assembly, System.Text.Json, OpenXML, keyed DI, React, and Ant Design. No new third-party dependency, plugin framework, formatter registry, or license decision is needed.

## 2. Library boundary and service composition

1. Introduce a public `SampleJsonGenerator` instance service beside `TemplateAnalyzer` and `DocumentGenerator`. Its operation accepts a readable template stream and optional `SampleJsonOptions`, and returns `SampleJsonResult`. Naming is proposed; responsibilities and compatibility boundaries are the decisions.
2. Options contain only `ItemsPerCollection` and `Values` (Filled or Empty), with approved defaults. Represent positive counts without an arbitrary collection maximum, using the platform's BigInteger where needed. Actual allocations are bounded by the aggregate limit; an unknown-shape array can remain empty even with a very large requested count. HTTP counts use positive decimal integer text, with no exponent/fraction syntax.
3. The result contains an independently owned `JsonElement Data` and read-only ordered warnings using existing `GenerationDiagnostic` fields. Construct JSON with standard platform objects/writers and return a detached element, so callers need not retain a document/package or dispose a result. No public mutable planner or schema is exposed.
4. Invalid options are argument errors. Template and sample-construction failures use existing `TemplateException` diagnostics and limit conventions; no candidate is returned. Reuse existing structural codes and introduce sample-owned codes only for sample limits, unresolved shape/ancestors, semantic conflicts, and incompatible collection demands. Do not route sample explanations through a generic-message conversion that discards their safe actionable detail.
5. Buffer the template once from its current position, detect actual package format through `PackageFormatDetector`, and delegate to DOCX/XLSX sample services. Preserve input bytes and caller stream ownership. Open packages read-only; keep all package references within the operation.
6. Register public orchestration and format services through the existing declarative `AddMonoReport` composition and TryAdd conventions. Dependencies enter constructors; operation state, counters, diagnostics, and JSON builders remain local. Do not build another provider or maintain duplicate keyed registration metadata.
7. Shared sample functionality is limited to scalar selection, ordered semantic-evidence resolution, JSON construction, and array-element budget accounting. Format services own scope, hierarchy, repetition, and collection identity. Private helpers remain with their owner; no generic format-provider abstraction or general template IR is justified.

## 3. Inspection reuse and semantic metadata

1. DOCX sample generation reuses `DocxStoryReader.OpenForValidation` and `DocxTemplateAnalyzer.Inspect`, including identity and compatibility inspection across all supported stories. Any inspection error prevents construction. Consume the returned story/block plans and parsed dependencies directly; never parse public occurrence expression strings.
2. XLSX sample generation reuses reader/planner and the same static geometry/formula preflight as `XlsxTemplateAnalyzer`. Introduce a format-local internal inspection method returning the validated `XlsxTemplatePlan`; both Analyze and Sample consume it. It preserves current error mapping and source checks. This narrow reuse does not change Generate's evaluation pipeline or extract validation into shared infrastructure.
3. Add nullable init-only `SemanticType` to existing `FormatterMetadata`, backed by Core's small semantic enum. Preserve the positional constructor, Deconstruct, and `IFormatter`. Number, Date, and external Spellout declare their own hints; casing formatters do not.
4. Capture the selected formatter's hint in the internal parsed formatter invocation during the existing keyed lookup and parameter validation. Both analysis and samples consume that captured evidence; do not resolve a formatter again simply to infer its meaning. Existing registration precedence, scopes, and ownership remain unchanged.
5. Add a nullable init-only hint to public `TemplateOccurrence`, preserving its positional constructor/deconstruction. Serialize only known values as lowercase strings; omit unknown hints. Do not globally change enum serialization or existing DTO members.
6. Preserve formatter evidence separately from structural evidence. Formatter hints remain per occurrence even where a Boolean sample value takes precedence. For DOCX, canonical loop scope identifies Boolean property uses; for XLSX, use actual record/header scope and level, not the aggregated requirement tree. An absent formatter hint may inherit an existing Boolean structural dependency only in that same scope.
7. No hint callback, AcceptedTypes, SampleValue, new formatter method, or runtime Format invocation is needed for inference. No new errors enter Analyze or Generate from semantic conflicts. Coarse hints are not proof of conversion success.

## 4. Sample construction and allocation

1. Each format first collects a compact sample description from its inspection: properties, collection shapes, scalar evidence, and format-owned repetition descriptors. It contains source locations and sufficient scope identity, but no generated per-item JSON. It is internal to this operation, not a reusable compiled template API.
2. Merge evidence in stable source order. Repeated identical hints agree, unspecified uses do not override known hints, and the first known conflicting hint wins with a targeted warning. Boolean structural dependencies take sample precedence with a conflict warning where necessary. Warnings identify the affected dependency and relevant source uses; repeated generated items do not multiply the same source limitation warning.
3. Filled values use a deterministic sequence from stable property/item traversal: distinct generic sample strings, conservative varied numbers, fixed-base ISO dates, and alternating Booleans where appropriate. Keep native sample numbers Excel-safe. Use no clock, process-randomized hashes, or unseeded randomness. Sample identity is shared for repeated references to an actual property, not for every occurrence of its expression.
4. Empty values use empty strings or Boolean false, while retaining collection structure and required XLSX controls. An unspecified custom formatter uses generic fallback without a warning merely for missing metadata. Domain-specific value validity remains unguaranteed.
5. Before allocating generated arrays or records, count all nested and expanded array elements over the description. Use bounded/saturating arithmetic at 1,000,001 for the budget, avoiding iteration over the requested count or unchecked products. Empty unknown collections contribute zero. Exact 1,000,000 succeeds; excess or arithmetic failure returns no candidate. This limit does not claim to bound all package or string memory.
6. After count preflight succeeds, materialize JSON in deterministic property/item order. Use built-in JSON handling for Unicode names and values; never assemble JSON source by string concatenation. A template with no dependencies produces an empty object, not an unavailable result.
7. Complete useful JSON with warnings is successful. An unresolved optional shape may remain empty; an unavailable ancestor is not fabricated. Fail when required sample structure cannot be reconciled, such as one shared collection needing incompatible record multiplicities. Do not silently truncate counts, choose a different collection size, or claim the candidate passed Generate.

## 5. DOCX sample ownership

1. Build object/array property structure from validated canonical dependencies while using story/block scope and parsed paths for current elements, parent references, and conditional branches. Consolidate the same collection across stories and repeated blocks; root paths resolve to the shared root description.
2. Known object-item collections generate the requested number of objects; nested collections repeat within each generated parent. Current-element-only use supplies scalar examples, including formatter hints. A collection with no item evidence stays empty with a source-specific unresolved-shape warning when relevant.
3. A loop using both current-element scalar output and item properties may be template-valid but have no fully satisfying nonempty sample. Prefer the richer property shape to preserve discovered nested data and emit a warning for unresolved whole-item scalar output. Do not invent a Value property, constrain mixed arrays, or change template validity.
4. Collect property dependencies from both valid conditional branches, without trying to exercise every branch or solve branch conditions. Preserve the first-source ordering and sample conflict policy; conditional-specific conflicts remain warnings about the sample.
5. Do not clone/render XML, initialize output identities, write package parts, or invoke formatters on sample data. Compatibility inspection remains authoritative for rejecting source errors.

## 6. XLSX sample ownership

1. Consume `XlsxSheetTemplate` controls, vertical regions/nodes, horizontal nodes, parsed cells, and source locations. Build separate identities for root properties, horizontal header items, vertical level records, ancestor records, and intersection tuples. Flat canonical paths alone are insufficient.
2. Generate one shared array for each distinct root header collection. Header axes remain separate root collections, including nested horizontal geometry; do not turn geometry nesting into nested JSON arrays. A known header item shape receives the requested count; unknown item shapes can remain empty under the approved policy.
3. For each vertical collection, generate the requested roots and children at represented numeric levels in depth-first parent-before-child order. Header/body/footer positions only identify layouts and property uses. They do not duplicate descriptors or reverse the data when the footer is authored first.
4. Use the same horizontal cardinality order and `RecordArity` semantics as the existing binder. Intersecting logical rows emit complete contiguous tuple groups, each with one deterministic unique opaque `$path` and identical `$level` across its records. Empty products emit one descriptor. Do not infer data parentage from `$path` strings.
5. Put ordinary/parent-only field evidence on the group's first record and leaf evidence on its corresponding tuple records; compatible extra fields may be repeated for simplicity. Resolve parent paths against generated ancestor descriptors and header paths against their header scopes, including explicit root access. If the template requests an ancestor absent from the represented hierarchy, warn and leave the unresolved field unsatisfied; do not manufacture numeric levels.
6. Shared-collection reconciliation occurs before allocation. Merge compatible properties and represented levels from independent uses in stable order. For shared levels with incompatible hierarchy or intersection multiplicity, fail with locations of the incompatible uses. Do not solve cardinalities by changing requested counts or silently splitting a collection into new properties.
7. Reuse existing binder helpers for cardinality and header/row scope semantics where they apply directly; add sample-specific mapping beside the XLSX owner. Do not call BindInstances, ScheduleSheet, dynamic geometry, formula finalization against sample data, or Generate merely to certify a sample. Source-only preflight is still required under Section 3.
8. XLSX safe-formula transformations, unavailable data ancestors, and application rendering can still fail for the candidate. Representative existing-engine generation tests cover intended samples; the operation does not promise all generated candidates render.

## 7. HTTP contract and integration

1. Add `POST /api/documents/sample` with exactly one nonempty file named `template`, optional text `itemsPerCollection`, and optional text `values` (`filled` or `empty`). Omission selects defaults; blank, duplicate, incorrectly represented, unknown, or invalid fields are HTTP 400 under existing request codes. Supplied count text must be a positive decimal integer; unknown fields are rejected.
2. HTTP 200 is application/json with `data` as a JSON value, not escaped JSON text, and `warnings` as an ordered array, including an empty array. No result taxonomy, requirements tree, format geometry, or mandatory Analyze request is added.
3. Invalid template/package content, incompatible sample demands, and aggregate element-limit failures return HTTP 422 Problem Details with stable code, ordered errors, traceId, and existing limitReached semantics where applicable. The element budget is not an upload error and does not mean the diagnostic error cap was reached. No failure returns candidate data.
4. Preserve HTTP 415 for unsupported request media type, 413 for request-size enforcement, and 500 for unexpected faults. Actual unsupported/corrupt template content follows existing template diagnostic conventions rather than trusting filename/MIME. Cancellation during form reading follows current request handling; client abort does not imply synchronous engine work can always stop immediately.
5. Extend `MultipartRequestReader` with explicit Sample handling rather than treating it as either existing Boolean analysis mode. Keep the old endpoint behaviors intact. Add a thin sample endpoint handler that binds settings and calls the library service; request parsing does not own sample rules.
6. Reuse ApiProblemFactory/normalization, adding only sample-code safe descriptions as required. Add route and OpenAPI request/response/error descriptions alongside existing document operations. Do not change current Analyze result validity or render content negotiation.

## 8. Playground architecture

1. Add a typed sample API client under `web/src/services`; it submits the original selected File and settings, normalizes existing Problem Details, and accepts data/warnings. Retire frontend `SampleJson` conversion once this flow uses the service. Do not use the analysis cache as an input to samples or automatically replace the displayed analysis after a sample request.
2. Keep stateful sample request/review coordination in a focused hook under `web/src/hooks`, integrated with the existing operation/revision guards in `useDocumentActions`. The dialog under `web/src/components` owns rendering and composition only. Avoid a new generic request-state framework.
3. Use one existing Ant Design Modal with settings and Generate sample, followed by a read-only JSON Monaco preview, diagnostics above the preview, Copy, Replace Dataset, and Cancel. Reuse the existing Monaco component with read-only settings; keep scrolling, line numbers, folding, responsive width, and framework layout/theme tokens. Permanently explain below the collection-count field that nested collections multiply the total and the overall limit is 1,000,000. Make the warning about editing after replacement and unsaved replacement visible in the review state.
4. Store the candidate with captured template identity, Dataset/content revision, settings revision, and request identity. Settings edits clear the candidate; context changes or close/cancel invalidate it and abort the request. Guard both response publication and Replace acceptance. Superseded finally/error paths cannot change a newer request. Never replace current content during generation or Copy.
5. Serialize the returned data once for preview/copy/replacement, retaining identical text. Replacement uses existing generated Dataset naming and update behavior, which also invalidates stale document results. Remove the pre-generation discard prompt; explicit Replace in the review state is acceptance. Clipboard failures report feedback and preserve Dataset/candidate.
6. Extend analysis parsing/types to retain optional semanticType and display it as an advisory formatter hint on occurrences. Clarify that requirement `value` is structural while semantic hints describe formatter meaning; preserve the analysis contract. Keep a complete stored wire analysis result alongside the normalized display model so the Analysis toolbar's Copy action copies the whole result, including errors and hints, rather than normalized table rows. Use the existing clipboard mechanism where available and make Copy available whenever an analysis result exists.
7. Treat sample diagnostics as transient operation state: show request failures in the modal above the preview area and candidate warnings above the preview; clear sample diagnostics when canceled, invalidated by settings/context changes, or accepted. The Problems pane open/collapsed preference persists, but diagnostic messages do not. Preserve later Generate diagnostics through the existing operation path.

## 9. Significant decisions and alternatives

1. Library and format-owned samples replace frontend inference: this removes duplicated engine semantics and serves library consumers. The trade-off is an additional server request and possible repeat inspection after a previous Analyze. Accept that cost without cache/session infrastructure.
2. Reuse validated internal plans within one operation rather than publish geometry or compile templates. A small format-local inspection reuse is justified; a cross-format validation extraction is not.
3. Fixed optional metadata preserves custom implementations and DI replacement behavior. Argument-aware hints and accepted-type/sample-value contracts add complexity without approved need; omission is the supported fallback.
4. Deterministic scalar selection and first-source conflict handling keep behavior explainable. A solver or automatic Generate would cost more and still not establish visual correctness; coarse hints deliberately provide no such guarantee.
5. Success-with-warnings and 422-without-data align with existing API patterns and avoid partial-status machinery. Rejecting irreconcilable shared collection shapes is safer and simpler than returning silent count changes.
6. Separate compact descriptions for counting from bounded JSON materialization avoid allocation surprises. This is sample-local data construction, not a general schema or compiler framework.
7. A single preview modal provides review and acceptance without a second editor or repeated discard confirmations.

## 10. Risks, verification boundaries, and approval

1. Highest risk: mapping XLSX parent/tuple scopes and reconciling shared collections. Use existing hierarchy/arity fixtures and representative source-to-sample-to-Generate scenarios, including footer-first, sibling horizontal geometry, empty products, unrendered ancestors, and worksheet reuse. Do not broaden engine acceptance to make samples pass.
2. Compatibility risk: additive record metadata must preserve constructor/deconstruction and older custom formatter use; verify replacements/aliases and unspecified hints. Formatter parameter validation remains unchanged, and inference must not invoke Format.
3. Regression risk: format-local inspection reuse must preserve Analyze error ordering, source restrictions, package ownership, and existing successful generation. Keep dynamic generation untouched and retain focused parity regressions.
4. Resource risk: hierarchical defaults multiply rapidly and horizontal tuples add another product. Budget checks must precede item allocation; exact boundary, nested/sibling totals, huge counts, and overflow paths need focused checks. No arbitrary collection maximum or automatic shrinking is proposed.
5. UI risk: candidate acceptance can race with edits, cancellation, context switches, settings changes, and later requests. Verify these behavioral guards and copy failure; no cosmetic/framework tests or browser automation are required by this architecture.
6. No unresolved product decision blocks this approved architecture. HTTP names/error mapping and deterministic conflict/fallback details above resolve the decisions explicitly delegated to architecture. The Product Owner approved architecture and authorized implementation planning on 2026-11-08. If source inspection during planning shows incompatible shared collection cases need a materially different fallback or broader abstraction, return for approval rather than expand scope.
7. Necessary future documentation corrections: document the new sample API/settings/errors, explain Filled/Empty and aggregate expansion limits, describe advisory occurrence hints and the preview/copy/replacement workflow, and retain the distinction from data validation. README, API guidance, and DOCX/XLSX authoring guides may need targeted updates; no user-facing documentation is modified by this architecture task.
8. This assessment is based on code/spec/contract inspection and previous investigations. No implementation, test execution, benchmark or browser automation was performed for the assessment. Stages and verification details are documented in the separate [Implementation Plan](implementation-plan.md), approved on 2026-11-08 and Accepted with all six stages on 2026-11-09.
