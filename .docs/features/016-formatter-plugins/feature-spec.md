# Feature 016 — Formatter Plugins

**Status:** Approved by the Product Owner (2026-11-01).

**Prepared:** 2026-11-01

## 1. Goal and authority

1. Support independently implemented formatters through public Core-owned `IFormatter` contracts and standard .NET keyed DI. Establish a small foundation for future plugins without implementing a plugin system.
2. Migrate every existing explicit formatter to that contract. Keep simple formatters in Core and move RUB spellout to `MonoReport.Formatter.Spellout`. Core must not reference external implementations.
3. Use explicit `IServiceCollection` registration. A registration key is the case-sensitive formatter name used directly in templates; no custom builder, fluent configuration API, discovery, or alias registry is required.
4. Use the same formatter contracts, binding, and validation for DOCX and XLSX through existing shared language/formatting services.
5. Preserve formatter behavior except for the approved syntax changes: one optional positional parameter plus named parameters, accepting only double-quoted string literals. Replace colon patterns; do not maintain colon compatibility or bare-value variants from earlier drafts.
6. Keep future package distribution and dynamic loading in [future-vision.md](future-vision.md). That document authorizes no implementation.

## 2. Existing implementation and complete formatter inventory

1. [Core](../../../MonoReport/MonoReport.csproj) targets .NET 10 and already references DI abstractions. [ValueFormatter](../../../MonoReport/Services/ValueFormatter.cs) dispatches by name and directly depends on `RubSpellOutFormatter`; there is no `IFormatter` contract. [TemplateLanguageParser](../../../MonoReport/Services/TemplateLanguageParser.cs) hard-codes formatter recognition and colon-pattern validation.
2. `upper` stays in Core: uppercase scalar text using configured culture.
3. `lower` stays in Core: lowercase scalar text using configured culture.
4. `caps` stays in Core: uppercase Unicode word-initial letters while preserving other characters; this is not title-case normalization.
5. `firstcap` stays in Core: uppercase the first Unicode letter while preserving other characters.
6. `number` stays in Core: accept JSON numbers or invariant numeric strings, including exponents and surrounding whitespace; preserve decimal precision and format with the supplied .NET pattern and configured culture.
7. `date` stays in Core: accept supported ISO date-only or explicit-offset date-time strings; format with the supplied .NET pattern and culture, preserving offsets and date-only midnight at offset zero.
8. `spellout` moves to `MonoReport.Formatter.Spellout`: [RubSpellOutFormatter](../../../MonoReport/Services/RubSpellOutFormatter.cs) spells Russian RUB amounts with numeric two-digit kopecks, away-from-zero rounding to two fractional digits, negatives, and an absolute rounded amount below 10^18 RUB. Its numeric input acceptance matches `number`; output is culture-independent. Numeric parsing currently belongs to `ValueFormatter`, so moving only the wording class would not complete extraction.
9. These are all seven explicit formatters. Unformatted scalar conversion is ordinary rendering behavior, not an eighth formatter or a reason to add a synthetic `value` service. Casing formatters and Spellout accept no parameters; number/date require a pattern.
10. [AddMonoReport](../../../MonoReport/MonoReportServiceCollectionExtensions.cs) uses `TryAdd` defaults, transient orchestration, and a singleton RUB wording service. [API](../../../MonoReport.Api/Program.cs) and [CLI](../../../MonoReport.Cli/Program.cs) currently reference only Core and call `AddMonoReport`.
11. [TemplateAnalyzer](../../../MonoReport/Services/TemplateAnalyzer.cs), DOCX planning, and XLSX planning share the parser; DOCX rendering and XLSX textual binding share `ValueFormatter`. Generation performs data-independent preflight before binding/rendering. Preserve those shared paths rather than adding another parser or validation pipeline.
12. Existing analysis exposes validity, errors, warnings, requirements, and occurrences. Parameter metadata is an extension contract, not an addition to analysis DTOs, sample dataset inference, HTTP schemas, or UI.
13. Relevant semantic sources are [Feature 010 scalar formatting](../010-unified-template-syntax/feature-spec.md#3-scalar-formatting), [Feature 011 syntax](../011-simplified-template-syntax-and-docx-compatibility/feature-spec.md#4-template-language), and [Feature 014 value types](../014-xlsx-template-compatibility/feature-spec.md#23-rich-text-substitution-and-value-types). This Feature supersedes their formatter extensibility restrictions and colon syntax only where explicitly stated. Do not modify completed Feature artifacts.

## 3. Approved functional requirements

### 3.1. Contracts, registration, and dependencies

1. All seven formatters implement the same public Core-owned `IFormatter` contract for metadata, formatter-specific validation, and formatting. Do not retain name-based runtime dispatch or formatter-specific parser validation as a parallel mechanism.
2. Keep public contracts/data models in Core. External projects use public contracts without friend-assembly access; Core references no external implementation. No contracts assembly, umbrella project, or general extension framework is required.
3. `AddMonoReport` registers the six Core formatters as keyed `IFormatter` services under their existing names. Discovery here means identifying existing implementations during development, not runtime scanning.
4. The external project provides the standard `IServiceCollection` extension `AddMonoReportSpelloutFormatter(string key = "spellout")`. Its receiver is the collection; returning that collection follows existing extension conventions and does not introduce a custom builder or fluent configuration API.
5. The supplied key is the complete template formatter name. Custom keys require no parser change or implementation-owned name property. Multiple registrations under different keys coexist. Custom-only registration does not implicitly supply `spellout`; that default is used only when the argument is omitted.
6. Use nonempty keys representable by existing template identifier rules: a Unicode letter/underscore followed by Unicode letters, digits, or underscores. Matching is ordinal and case-sensitive, without normalization, hidden aliases, or implementation-specific spelling rules.
7. API/CLI explicitly reference Spellout and register it using the default key. Core-only consumers can use the six simple formatters without Spellout; an unregistered Spellout invocation produces the ordinary unknown-formatter diagnostic.
8. Actual same-type/same-key registrations follow standard .NET single keyed resolution: the last registration wins. Metadata, validation, and formatting must come from that selected implementation. Do not reject duplicate service keys or invent priorities; see Microsoft's [keyed registration source](https://source.dot.net/Microsoft.Extensions.DependencyInjection.Abstractions/ServiceCollectionServiceExtensions.Keyed.cs.html).
9. Preserve `TryAdd` conventions for Core defaults, previous consumer replacements, and repeated `AddMonoReport` calls. The explicit Spellout extension adds a normal keyed singleton registration on each call: repeated same-key calls follow ordinary DI behavior and different keys remain independent. No custom deduplication or cross-key singleton-sharing mechanism is required.
10. Preserve provider/scope ownership and disposal. Keep orchestration transient and stateless defaults singleton where safe. Resolve custom dependencies from the caller's provider/scope, without building another provider or capturing scoped formatters in global caches. Do not store operation values/culture on shared formatters.

### 3.2. Parameter metadata and binding

1. Describe parameters by name, type, and required flag; exclude defaults and allowed-value lists. Reuse ordinary .NET types rather than a custom type system or automatic conversion framework.
2. Formatter metadata may identify one declared parameter by name as its positional target, or none. Keep this optional designation at formatter level; no second positional schema, ordered positional list, or arbitrary positional indexes are needed. The target is the same declared parameter used for named binding.
3. Optional positional syntax does not make the parameter optional. Number/date declare required string `pattern` and designate it as positional; callers supply it positionally or by name. Casing formatters and existing Spellout declare no parameters or positional target.
4. After the formatter name, accept at most one positional double-quoted string followed by zero or more whitespace-separated named assignments. Named-only invocations are valid. A positional argument precedes named assignments; a second or trailing positional argument is a structural error.
5. `{Amount number "N2"}` and `{Amount number pattern="N2"}` bind identically. `{When date "yyyy-MM-dd HH:mm zzz"}` preserves its pattern contents. `{Amounts.InWords spellout}` and existing no-argument formatters remain unchanged.
6. Named assignments use `name="value"`, without whitespace around the equals sign. Names follow existing identifier rules and ordinal case-sensitive matching; named order does not affect binding. Reject missing names/values, unquoted values, and single-quoted values.
7. Double-quoted values may contain whitespace, commas, parentheses, and equals signs as ordinary content; these are not invocation separators. Preserve current quote/brace boundaries: no embedded double quote or braces and no new escape syntax. An empty string is supplied information, distinct from absence; the formatter may reject it during literal validation.
8. Bind the positional argument to its metadata-designated name, then validate all supplied names against one parameter set. Reject duplicates, including positional-plus-named supply of the target, even with equal values. Reject a positional argument when no target exists. Do not silently overwrite duplicates or resolve them by order.
9. Remove colon-pattern parsing instead of retaining a compatibility/normalization path. Remove bare literals from the target grammar. Parentheses, comma-separated invocations, chaining, pipelines, and arbitrary expressions remain unsupported.
10. `{Amount spellout currency="USD"}` is syntactically well-formed but fails Analyze because RUB Spellout declares no `currency` parameter. It authorizes no new currencies, languages, options, or production demonstration formatter. Use focused test implementations for generic parameter scenarios.
11. Keep metadata separate from invocation values. Use a small operand representation that distinguishes literals from a possible future dataset reference, with enough existing source information for diagnostics. Feature 016 creates string literals only. Preserve occurrences until duplicate checking instead of losing them in dictionary construction.
12. Leave room for a distinct future reference operand without implementing reference syntax, resolution, evaluation, or additional dataset requirements. Quoted dataset-looking paths remain literals; unquoted paths are invalid. No expression hierarchy, interpreter, or full parameter source-map infrastructure is required.

### 3.3. Analysis and validation

1. Analyze needs no dataset. Validate syntax, formatter existence, binding, unknown/duplicate parameters, required presence, and formatter-specific structural constraints. Also allow validation of known literal values. Do not resolve dataset paths, evaluate dataset values, or call runtime formatting on actual data.
2. Use one formatter validation operation able to inspect structure and available literals. Do not introduce separate structural/literal validator service hierarchies or require another value-validation pass during formatting.
3. Number/date reject empty/invalid literal .NET patterns during Analyze in either form. Reuse framework checks against fixed sample values and invariant culture where appropriate; this is permitted literal validation, not dataset evaluation. Do not implement a custom .NET pattern parser.
4. The selected keyed formatter owns its constraints and literal validation. Replacing a registration replaces its metadata and validation; Core must not apply the former implementation's hard-coded pattern rules to the replacement.
5. Check before runtime null/empty/missing handling, including inactive branches and empty loops. Preserve Raw/opaque-content boundaries: literal document content does not become active formatter syntax.
6. Generation uses the same data-independent preflight under the same registrations. Successful analysis cannot guarantee formatting for later dataset values; value-kind, conversion, range, and other data-dependent checks may happen directly during formatting.
7. Reuse structural diagnostics, original expression and DOCX/XLSX location, deterministic ordering, and applicable limits. No formatter-specific transport schema or requirement/occurrence response change is required.

### 3.4. Context and preserved runtime behavior

1. Formatting receives the existing JSON scalar input, bound literal values, and a context containing effective `MergeOptions.Culture`. Do not depend on ambient thread culture or change accepted dataset domains merely because implementations move.
2. Preserve all seven formatters' semantics in section 2: casing/output culture, invariant numeric input, decimal precision, ISO date forms/offsets, and culture-independent RUB wording, grammar, rounding, and range.
3. Null and empty strings render empty without formatter conversion. Missing values retain `MissingValues` behavior; objects/arrays remain invalid scalar inputs. Unformatted scalar conversion remains unchanged.
4. Expected failures retain safe diagnostics, aggregation, ordering, limits, expression, location, and data path. Formatter diagnostic identity is the invoked key, including custom Spellout keys; default `spellout` identity remains unchanged. Do not expose raw exception details through transports.
5. Preserve no-partial-document behavior, caller bytes/stream ownership, parse-once rendering, and inert inserted text. Explicit XLSX formatting yields text; unformatted whole-cell expressions keep native values/precision rules. DOCX/XLSX rich-text and style behavior stays unchanged.

## 4. Architecture and complexity review

1. **One common path:** explicit formatters follow keyed lookup, metadata binding, validation, and formatting. Ordinary scalar output remains ordinary rendering. No registry, builder, catalog, generalized plugin host, or special external-implementation branch is justified.
2. **Small public boundary:** keep `IFormatter`, data-only metadata/operand/context models, and validation results in Core, independent of internal ASTs, OOXML, and transport DTOs. Services use externally supplied dependencies under project conventions.
3. **One binding model:** positional designation refers to a named parameter. Both forms produce the same binding; removing colon syntax avoids a third variant. Double-quoted-only literals eliminate bare-token coercion rules.
4. **One validation operation:** binding checks plus formatter-owned structural/literal checks suffice. Fixed-sample framework validation avoids both a custom pattern parser and independent validator infrastructure.
5. **Minimal future preparation:** an extensible operand boundary suffices. Do not implement unused reference nodes/resolvers, an expression hierarchy, generic conversion, cached discovery, or expanded source mapping; reuse existing source expression/location data where sufficient.
6. **Shared conversion only where needed:** number and Spellout retain identical numeric input rules. Reuse a small shared scalar-conversion service if needed instead of duplicating parsing or retaining a Spellout branch in `ValueFormatter`. Do not introduce a conversion-provider framework or unrelated service refactoring.
7. **Explicit composition:** Core owns six default registrations, Spellout its service-collection extension, and API/CLI selecting it. Registration keys supply invocation identity; implementations need no canonical name, aliases, manifest, or awareness of other keys.
8. **Normal lifetimes:** selected metadata and behavior must agree, but services need not be the same object across separate calls. Preserve normal transient/scoped semantics, stable metadata, and caller scopes rather than global instance caches.
9. **Review conclusion:** no remaining product-level architectural decision is needed for the stated behavior. Public member naming/helper placement are routine choices. Additional syntax, escaping, conversion infrastructure, or plugin machinery would require a separately approved scope change; none is proposed now.

## 5. Compatibility risks and migration boundary

1. **Intentional syntax break:** migrate colon patterns in affected samples, fixtures, README/syntax guidance, and embedded/example copies to positional or named double-quoted patterns. No automatic migration product or legacy grammar is requested. Preserve pattern contents and output behavior.
2. **Setup/source change:** consumers needing Spellout must reference it and explicitly register it. Moving `RubSpellOutFormatter` and changing `ValueFormatter` construction affects manual construction/test helpers. Document setup changes without implementation shims in Core.
3. **Build composition:** solution/application references and source/restore inputs must include Spellout. The current [Dockerfile](../../../Dockerfile) copies project files before restoring API; adding the reference requires including the new project's restore input. These are integration consequences, not a hosting redesign.
4. **Replacement correctness:** whitelist remnants, metadata from another registration, or retained built-in pattern validation would undermine independent/replacement implementations. Custom keys must work in DOCX/XLSX without dispatch or formatter source changes.
5. **Behavioral fidelity:** extraction must preserve casing, invariant numeric parsing, empty/missing behavior, dates/offsets, RUB range/rounding, and diagnostics. Unformatted XLSX fields must not be routed into explicit text formatting and lose native types.
6. **Lifetime/identity:** avoid singleton capture of scoped dependencies and operation state. Metadata stays stable within a composition. Different Spellout keys require equivalent behavior, not shared object identity; carry invoked keys in diagnostics without mutating shared instances.
7. The syntax/setup changes above follow approved decisions. No broader compatibility layer, migration feature, formatter functionality, or binary compatibility guarantee is implied.

## 6. Acceptance criteria

1. **Complete migration:** all seven formatters resolve as keyed `IFormatter` services and use shared analysis/formatting. Six remain in Core; Spellout is external. No name-based formatter whitelist/dispatch or concrete external dependency remains in Core. Unformatted behavior is unchanged.
2. **Public extension:** a focused external formatter registers through `IServiceCollection` and works in DOCX/XLSX using public contracts without parser edits or friend access. Contracts stay in Core; no separate assembly, custom builder, or fluent configuration API appears.
3. **Spellout keys:** `AddMonoReportSpelloutFormatter()` registers `spellout`; an explicit key becomes the template name. Register two distinct keys and verify both Analyze/Generate the same RUB behavior in both formats, with invoked keys in failure diagnostics. Custom-only registration does not supply the default implicitly.
4. **DI selection:** same-key actual registrations select the ordinary .NET winner; reversing order changes metadata, validation, and formatting together. Core defaults preserve earlier consumer replacements and repeated bootstrap. Explicit same-key Spellout calls append normal registrations. No priority, service-key rejection, registry, or alias layer appears.
5. **Metadata:** name/type/required descriptions have no defaults or allowed-value lists. One optional formatter-level positional target references a declared parameter. Number/date require string `pattern`; no-parameter implementations expose no target. No duplicate positional schema is introduced.
6. **Accepted syntax:** number positional/named forms produce identical output; date forms agree. Quoted whitespace/punctuation/empty strings parse without coercion. A focused formatter accepts a positional argument plus named parameters, independent of named order. Existing no-argument invocations, including `{Amounts.InWords spellout}`, work unchanged.
7. **Rejected syntax/binding:** reject colon patterns, bare/single-quoted values, malformed assignments, unknown formatter/parameter names, duplicate names, positional-plus-named duplication, a second/trailing positional argument, and a positional argument without a target. Required parameters remain required when positional syntax is omitted. Parenthesized/comma-separated invocations and pipelines remain invalid; quoted pattern punctuation remains content.
8. **Literal-aware Analyze:** empty/invalid number/date patterns fail in both forms with source diagnostics even when runtime values would be null/missing or branches inactive. A focused formatter demonstrates structural relationship and known-literal constraints. Instrument it to verify no dataset access or runtime formatting is required. A valid invocation may still fail Generate on incompatible dataset input.
9. **Unchanged RUB:** `{Amount spellout currency="USD"}` parses but reports an unknown parameter. No new currency/language or production demonstration formatter appears. Verify zero, negatives, grammar, kopecks, away-from-zero rounding, rounded 10^18 boundary, numeric-string acceptance, and invalid scalar/object/array inputs.
10. **Output regressions:** preserve all four casing behaviors, number input/precision/culture, dates/offsets, custom-formatter culture context, invariant RUB output, null/empty bypass, missing policies, safe aggregated diagnostics, no partial output, stream ownership, and inert insertion. Preserve XLSX native/text distinction and document styling.
11. **Composition/lifetimes:** API/CLI explicitly register default Spellout; Core-only providers support simple formatters and report absent Spellout normally. Default graphs pass provider validation; caller scopes support scoped custom dependencies. Repeated/concurrent operations do not leak values/culture. No extra provider/global instance cache appears.
12. **Migration consistency:** affected docs, samples, embedded copies, fixtures, test setup, references, and restore/build inputs agree with the approved syntax/composition. Relevant Core/CLI/HTTP tests check actual analysis/generation and unchanged response shape. Organize new tests by subsystem; begin with affected formatter/parser/DI tests and expand by impact.
13. **Future boundary/scope:** quoted dataset-looking paths stay literal and unquoted paths are invalid. The operand boundary allows a future distinct reference without implementing it. No `.nupkg` distribution/loading, plugin manager, extraction, discovery endpoint, UI, dynamic loading, expression evaluation, extra currencies, or per-merge bindings are implemented.

## 8. Product Owner decisions and remaining architectural concerns

1. **D1 — resolved, identity/project:** use `MonoReport.Formatter.Spellout` and default key `spellout`. The latest decision additionally permits custom registration keys used directly in templates, without canonical-name mapping or an alias registry.
2. **D2 — resolved, parameters:** accept one metadata-designated positional double-quoted string plus named double-quoted strings. Remove colon patterns and bare literals. Preserve no-argument invocations and formatter behavior. This supersedes earlier named-only/colon-compatibility proposals.
3. **D3 — resolved, literal validation:** Analyze may validate known literal values, including number/date patterns using fixed-sample framework checks, without evaluating dataset values. No custom pattern parser is required.
4. **D4 — resolved, composition:** use `IServiceCollection`, provide `AddMonoReportSpelloutFormatter(string key = "spellout")`, permit distinct keys, and register default Spellout explicitly in API/CLI. Core registers six simple formatters without referencing Spellout. Library consumers opt in explicitly.
5. **D5 — resolved, contracts:** keep public formatter contracts in Core; do not create a separate contracts assembly.
6. **Remaining concerns:** no unresolved product-level architectural question blocks this specification. Intentional syntax/setup migration, keyed selection, and lifetime risks are documented in section 5 and covered by section 6. No additional compatibility layer or plugin infrastructure is proposed for approval.
7. The supplied decisions approve these requirements and this documentation revision. They do not approve the complete revised Feature Spec, authorize an Implementation Plan, or authorize implementation. Routine member naming/internal design choices must not become additional Product Owner decision gates.
