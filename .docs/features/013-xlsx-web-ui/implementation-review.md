## 2. Stage 1 findings and disposition

1. **S1-01 — Pending-load workers survive preview disposal. Status: Rejected. Original severity: Stage 1 acceptance blocker.**

   **Affected component:** XLSX preview lifecycle and resource cleanup.

   **References:** [XlsxPreview.tsx:53](../../../MonoReport.UI/src/components/XlsxPreview.tsx#L53), with cleanup relying on `viewer.destroy()` at [XlsxPreview.tsx:26](../../../MonoReport.UI/src/components/XlsxPreview.tsx#L26); pinned-library acquisition handling at [canvas-viewer-mechanics-ycCX6v-z.js:528](../../../MonoReport.UI/node_modules/@silurus/ooxml/dist/canvas-viewer-mechanics-ycCX6v-z.js#L528).

   **Evidence:** An in-memory Node/jsdom check using the actual pinned viewer confirmed that its parsing worker remained alive after `destroy()` during a pending load, terminating only after that load settled. In the library, pending acquisitions become owned only after loading finishes; closing the viewer cannot dispose them immediately.

   **Impact:** Rapid template or tab changes can accumulate obsolete parsing work and memory, as documented in the accepted lifecycle limitation. The existing stale-operation guards do not stop that obsolete work promptly.

   **Original recommendation:** Make cancellation/resource ownership cover the pending load, using a narrow library fix if necessary. Investigation is recorded in Section 6.

   **Product Owner decision — 2026-10-25:** **Rejected.** Accept the known limitation of delayed pending-load worker cleanup in `@silurus/ooxml` 0.89.4. No permanent leak or demonstrated user-facing failure was established, and a maintained dependency patch is not justified at this time. Do not patch or replace the dependency. Preserve existing cleanup, the 30-second worker-request timeout, and stale-operation protections. The Feature Spec and Implementation Plan now reflect this accepted limitation.

## 6. S1-01 investigation — 2026-10-25

1. **Scope and status:** Investigation only, using the installed 0.89.4 artifact, public declarations and bundled README. At the time of investigation, S1-01 remained Open and the verdict was CHANGES REQUIRED. The subsequent Product Owner decision in Section 2 supersedes that disposition; technical observations below remain historical evidence. No application code, dependencies, tests, Git index/history, browser automation, or agents were changed or used. The only edit is this review record.
2. **Cause:** `XlsxViewer.load()` awaits an acquisition whose factory calls `XlsxWorkbook.load()`. The workbook factory creates its worker and workbook internally before awaiting parsing, but returns the workbook only after `_load()` finishes. The acquisition holder stores only completed resources; its `close()` invalidates the generation and destroys the installed resource, without retaining or canceling the pending factory. Viewer teardown therefore releases UI observers/listeners and installed resources, but cannot reach the pending workbook/worker. See [viewer acquisition](../../../MonoReport.UI/node_modules/@silurus/ooxml/dist/xlsx-lvftmF1U.js#L4902), [workbook factory](../../../MonoReport.UI/node_modules/@silurus/ooxml/dist/xlsx-lvftmF1U.js#L864), and [holder](../../../MonoReport.UI/node_modules/@silurus/ooxml/dist/canvas-viewer-mechanics-ycCX6v-z.js#L528).
3. **What happens later:** If the factory succeeds after closure, the holder immediately calls the returned workbook's `destroy()` and rejects with a closed error. Workbook destruction terminates its worker bridge and releases caches/fonts. If parsing fails or its request times out, the factory catches the failure and destroys the partial workbook before rejecting; the closed holder then reports closure instead of the original error. The App ignores these obsolete failures through its existing session guard. This is delayed resource release, not evidence that every disposed worker leaks forever. Once a workbook has been installed, ordinary viewer destruction does reach it promptly. See [factory failure cleanup](../../../MonoReport.UI/node_modules/@silurus/ooxml/dist/xlsx-lvftmF1U.js#L867), [workbook destruction](../../../MonoReport.UI/node_modules/@silurus/ooxml/dist/xlsx-lvftmF1U.js#L1402), and [bridge termination](../../../MonoReport.UI/node_modules/@silurus/ooxml/dist/canvas-viewer-mechanics-ycCX6v-z.js#L150).
4. **Focused evidence:** An ephemeral Node command imported the actual bundled acquisition holder and actual `XlsxWorkbook.load()`, using repository tender bytes and a minimal Worker substitute that withheld parsing replies. Closing after `init`/`parse` left one worker unterminated. With a 40 ms timeout supplied only to this investigative invocation, the loader terminated the worker and rejected after approximately 41 ms. A separate actual-holder check returned a resource after closure: destruction count changed from 0 to 1 and the promise rejected as closed; a rejected factory also became a closed error. This corroborates the earlier real-viewer Node/jsdom evidence without browser automation or saved test infrastructure. The substitute establishes host-side ownership/timeout behavior, not real WASM memory consumption or parsing performance. The application's 30-second configuration is unchanged.
5. **Supported cancellation:** Neither public `XlsxViewer.load(source)` nor `XlsxWorkbook.load(source, options)` accepts an AbortSignal or returns a pending-load handle; the workbook constructor is private in the declarations. `destroy()` and `workerTimeoutMs` are supported, but neither exposes immediate cancellation of an unreturned workbook. `XlsxWorkbook.load()` followed by `fromWorkbook()` still receives ownership too late to cancel initial parsing. The generic bridge internally supports signals, but XLSX loading does not pass one through. The separately exported model-source module protocol has a signal parameter; it is not a cancellation API for the normal XLSX loader and would require custom integration. Do not depend on private `bridge`, `acquisition`, or factory internals from App code. See [load options](../../../MonoReport.UI/node_modules/@silurus/ooxml/dist/types/xlsx.d.ts#L1482), [workbook API](../../../MonoReport.UI/node_modules/@silurus/ooxml/dist/types/xlsx.d.ts#L2492), and [viewer API](../../../MonoReport.UI/node_modules/@silurus/ooxml/dist/types/xlsx.d.ts#L2868).
6. **30-second mitigation and practical impact:** The timeout starts for a posted worker request and is cleared when that request settles; it is not a total-load deadline or a deadline from `destroy()`. On a stalled initial parse, it normally limits continued work to the remaining request timeout, after which factory cleanup terminates the worker. Async preparation/import before that request and subsequent font work are outside that timer; later worksheet requests have their own timers. It is therefore incorrect to promise all resources are released within 30 seconds of disposal. Rapid switching can leave several independent parsing workers, transferred input, WASM heaps and partial models alive concurrently until each settles. As an illustrative rate calculation, one stalled parse started each second can leave roughly 30 parsing workers outstanding before the earliest timeout; this is not a measured capacity figure or a strict bound. Existing per-workbook limits do not cap aggregate preview sessions. Small research fixtures settled quickly, so ordinary observed use has a shorter overlap, but that does not establish worst-case safety. Repeated disposal after successful loading is promptly cleaned up; repeated disposal during parsing is the affected case. UI stale-update protection remains effective.
7. **Correction options and trade-offs:**
   1. **Originally recommended, subsequently declined: narrow pinned-library ownership/cancellation patch.** Give the XLSX loading path a teardown handle while work is pending, terminate the partial workbook's worker on viewer destruction, and guard async preparation/worker creation so closure cannot create a new worker afterward. Retain existing success/failure cleanup and safety limits. This addresses the confirmed defect without changing viewer or adding a scheduler/framework. It requires modifying and reproducibly distributing the dependency, with a small focused regression check for disposal during parse and before worker creation; the exact patch mechanism is a separate implementation choice requiring approval. Prefer an upstream fix if available, but no newer release or upstream fix was evaluated in this investigation.
   2. **Keep the current behavior or shorten the timeout.** No dependency patch is required, and eventual cleanup is already present. This accepts delayed obsolete work; a shorter timeout can reject valid slow workbooks and still is not prompt cancellation. At investigation time this required an explicit Product Owner decision about the lifecycle requirement. The Product Owner subsequently accepted the existing behavior, with the existing timeout unchanged.
   3. **Serialize pending loads in the wrapper.** Supported APIs could bound the number of pending parses, but the latest selection must wait for obsolete work to finish or time out, and this adds coordination across disposed previews. It mitigates aggregate overlap without canceling the obsolete worker. It is more application machinery and worse responsiveness than fixing ownership, so it is not recommended for this requirement.
   4. **Upgrade or replace the viewer.** Consider only if a supported fixed version is verified or the narrow patch proves impractical. It requires Product Owner approval and renewed compatibility, safety, asset and license verification. There is no evidence here justifying replacement. Private-field access, global Worker interception, iframe isolation, and main-thread parsing are not recommended corrections: they add unsupported coupling/infrastructure or move obsolete work onto the UI thread.
8. **Final Product Owner disposition — 2026-10-25:** The original patch recommendation in item 7.1 is declined. S1-01 is Rejected for the rationale in Section 2; retain `@silurus/ooxml` 0.89.4 and existing cleanup/timeout/stale-operation protections. No patch, replacement, or correction verification is authorized. Stage 1 is Accepted; S1-02 remains Open for Stage 4 licensing work.
