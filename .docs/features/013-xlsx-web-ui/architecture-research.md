# Feature 013 — XLSX Web UI Support: Architecture Research

## 1. Recommendation and research boundary

1. Recommend **client-side XLSX preview using the XLSX entry of `@silurus/ooxml` 0.89.4**, subject to Product Owner approval of the limitations below. Keep the existing DOCX viewer. Use the existing generation API and download its original bytes. This requires one additional viewer dependency, without a server converter, spreadsheet renderer written by MonoReport, or changes to the XLSX engine.
2. The smallest viable workflow is **upload XLSX → manually enter JSON → generate → preview → download XLSX**. Include worksheet navigation and reuse the same XLSX component for template preview. Analysis and automatic JSON generation must not gate this workflow. XLSX analysis already exists, but extending its UI can be deferred.
3. Viewer consolidation was evaluated as research only. It offers a possible future simplification, but changes DOCX appearance and broadens acceptance work. It is neither a requirement nor a recommended part of Feature 013.
4. Research date: **2026-10-25**. Alternatives received a lightweight documentation/source comparison. Practical browser comparison covered the selected candidate and the existing DOCX baseline only, with explicit Product Owner authorization. No application code, application dependencies, Feature Spec, or Implementation Plan was changed or created. Temporary dependencies and harnesses were isolated under `/private/tmp/feature013-research/`.

| Success warnings | The backend optionally returns document plus warnings through `Accept: multipart/mixed`, from one merge. Keep binary for the minimum scope; full success-warning presentation is an optional extension, distinct from preserving generation errors. |
| Layout and examples | Reuse Monaco, Splitter, Template/Result/Errors tabs, upload/drop handling, download actions, cancellation and revision guards. The current paper preview has padding and a 760px maximum width, unsuitable for a spreadsheet viewport. 1. The XLSX engine already supports multiple worksheets, authored styles, dimensions, hidden rows/columns and supported merges. Its [compatibility boundary](../../../docs/xlsx-template-compatibility.md) requires a finite rectangular PrintArea on every worksheet and rejects several advanced workbook features. A viewer being able to display a workbook does not make it a supported MonoReport template.
2. [XlsxDocumentRenderer.cs](../../../MonoReport/Services/Xlsx/XlsxDocumentRenderer.cs) removes formula caches/chains and requests recalculation. It **does not calculate formulas**. This directly affects result preview.
3. [Program.cs](../../../MonoReport.Api/Program.cs) defaults the whole-request limit to 50 MiB. This is a transport limit, not a safe browser preview capacity guarantee. Existing static hosting can serve additional viewer assets; no new document API is required.

## 3. Focused comparison and selection rationale

| Candidate and official repository | Capabilities and integration | License and maintenance evidence | Assessment |
| --- | --- | --- | --- |
| **[@silurus/ooxml](https://github.com/yukiyokotani/office-open-xml-viewer), 0.89.4** | Rust/WASM parsing with Canvas rendering; a dedicated read-only XLSX viewer with worksheet tabs. Separate DOCX/XLSX entry points allow narrow adoption. | MIT; bundled parser dependencies are discussed in section 5. The inspected package is a young 0.x release. Its [release history](https://github.com/yukiyokotani/office-open-xml-viewer/releases) shows active compatibility/lifecycle fixes. Activity does not establish long-term stability. | **Selected candidate for XLSX.** Direct XLSX ingestion avoids a MonoReport-owned style/model converter. Practical results are in section 4. |
| **[@js-preview/excel](https://github.com/501351981/vue-office), 1.7.14** | Framework-neutral preview wrapper over ExcelJS and a modified x-spreadsheet implementation. [Source](https://github.com/501351981/vue-office/blob/master/core/packages/js-excel/src/main.js) selects read mode, disables the toolbar, and supplies worksheet switching/cleanup. | [MIT](https://github.com/501351981/vue-office/blob/master/core/LICENSE). The maintainer's [README](https://github.com/501351981/vue-office#readme) warns that issue responses may be delayed from December 2024. The underlying [x-spreadsheet repository](https://github.com/myliang/x-spreadsheet) says development migrated elsewhere. | Plausible, but less attractive maintenance and dependency transparency. Its [build manifest](https://github.com/501351981/vue-office/blob/master/core/package.json) includes old SheetJS; an empty published dependency list does not mean an empty bundled dependency graph. Not selected. |
| **[Univer](https://github.com/dream-num/univer) OSS + [ExcelJS](https://github.com/exceljs/exceljs)** | Established spreadsheet functionality and permissions; XLSX values/styles would need conversion into Univer's model. Official [XLSX import](https://docs.univer.ai/guides/sheets/features/import-export) uses Pro exchange packages and a conversion backend, rather than the OSS renderer alone. | Univer core: [Apache-2.0](https://github.com/dream-num/univer/blob/dev/LICENSE), actively released; ExcelJS: [MIT](https://github.com/exceljs/exceljs/blob/master/LICENSE), inspected release line 4.4.0. Pro extensions require separate terms. | Viable with a substantial adapter, but too much conversion and editor configuration for read-only preview. Core's license must not be assumed to cover Pro import. Not selected. |
| **[SheetJS CE](https://git.sheetjs.com/sheetjs/sheetjs), 0.20.3 + HTML/table UI** | Good data extraction and number formatting. [CE HTML utilities](https://docs.sheetjs.com/docs/api/utilities/html/) leave CSS text/cell styling to Pro. A plain HTML table does not meet practical report-formatting needs. | [Apache-2.0](https://docs.sheetjs.com/docs/miscellany/license/). [Official installation guidance](https://docs.sheetjs.com/docs/getting-started/installation/nodejs/) identifies its CDN as authoritative and public npm `xlsx` as outdated. | Useful for data inspection, but would require more rendering work or reduced fidelity. Not selected. |

1. **Client-side rendering is preferred:** it previews the File/API Blob already in memory, preserves local preview without uploading, and fits existing deployment. Tradeoffs are browser memory, payload size and approximate Office fidelity.
2. **Server conversion to PDF/HTML is not recommended:** [LibreOffice supports headless conversion](https://help.libreoffice.org/latest/en-US/text/shared/guide/start_parameters.html), but adds a runtime, fonts, temporary files, process isolation and conversion limits. PDF follows print areas/pages rather than worksheet navigation. LibreOffice's [MPL licensing and bundled terms](https://www.libreoffice.org/licenses/) require explicit evaluation and Product Owner approval under the stated policy.
3. **An embedded office service is disproportionate:** [ONLYOFFICE requires document-service integration](https://api.onlyoffice.com/docs/docs-api/get-started/how-it-works/opening-file), and its community server is [AGPL-3.0](https://github.com/ONLYOFFICE/DocumentServer/blob/master/LICENSE). Exclude it under the licensing preference. Hosted Office viewers would also introduce remote document access and deployment/privacy requirements.

## 4. Practical comparison using MonoReport documents

### 4.1. Method and evidence limits

1. A temporary local harness compared the existing renderer **with its actual normalization function/options** against `@silurus/ooxml` 0.89.4 using original bytes. It used local headless Chrome **156.0.8078.47**, a 1780 × 1220 viewport, and no external fonts/services. Requests outside the localhost harness were blocked.
2. The current CLI was built successfully in Release with no warnings/errors. Fresh outputs were generated from all five DOCX sample/template-data pairs and the XLSX tender pair. All six generations succeeded. This exercised real Core generation through CLI; it was not a production Playground or live HTTP acceptance test.
3. DOCX checks opened every template and generated output, visited every candidate page, recorded painted text, and captured screenshots. Baseline HTML and candidate painted text both included all 20 generated order IDs. Screenshots are visual comparison evidence, not a pixel comparison against Microsoft Word.
4. Supplemental research copies tested cached Word fields, two worksheets, and explicit spreadsheet caches. They are clearly distinguished from unmodified samples below. [evidence.json](research-evidence/evidence.json) records versions, timings, hashes and observations. The temporary harness is research tooling, not proposed application code or new test infrastructure.

## 6. Recommended architecture and conceptual changes

1. Preserve the existing application state and API workflow. Add an explicit frontend document-format value and a small preview dispatch boundary: DOCX continues to the current component; XLSX goes to a focused wrapper around the selected viewer's `/xlsx` entry. Do not introduce a generic plugin system or alternate generation implementation.
2. Lazy-load XLSX JavaScript/WASM/worker assets when needed and serve them from the application origin. Convert the File/Blob to a separate ArrayBuffer for preview. Keep the original File for API upload and original response Blob for download. Viewer state must never become the downloaded workbook.
3. Reuse the viewer's worksheet tabs. Give spreadsheets a full-width, bounded-height viewport with their own horizontal/vertical scrolling, rather than the DOCX paper frame. Preserve Splitter/mobile behavior. Recommend visible sheets in authored order, hidden sheets skipped, and no editing controls. Selection and formula inspection are read-only interactions.
4. Reuse current request cancellation/revision checks. Destroy obsolete viewers and workers on source replacement/unmount; prevent stale preview completion from affecting a newer source. A preview failure or resource refusal must leave successful output downloadable and must not block API generation.

| Frontend concern | Smallest conceptual change |
| --- | --- |
| Upload and dispatch | Accept `.docx` and ordinary `.xlsx` through the shared picker/drop path; adjust copy. Extension is a UI hint, not package validation. A misleading extension may fail local preview; the backend remains authoritative. |
| Generation response | Accept either supported nonempty binary MIME, derive result format from the response, and use a safe matching filename/fallback. Never force XLSX bytes through DOCX preview or rename them `.docx`. |
| Diagnostics | Retain existing HTTP/network/Problem Details handling without an analysis preflight. Display available code, field, source part/location and data path. Do not label preview failure as generation failure. |
| JSON | Keep manual Monaco editing. For the minimum scope, retain DOCX Generate JSON behavior and make XLSX analysis/Generate JSON unavailable with concise explanatory copy. Reusing the existing XLSX analysis route can be a later, separately accepted UI extension. |
| Examples | Existing DOCX catalog behavior stays intact. An XLSX tender entry and XLSX asset-copy support are useful optional additions; custom upload is sufficient for minimum acceptance. |

5. **No backend contract or engine change is necessary.** Retain existing routes, generation validation, binary responses and request limits. Verify production publishing includes the new assets and serves WASM correctly; static-asset packaging corrections, if needed, are hosting integration rather than a new rendering API.
6. **Formula policy:** do not introduce a calculation engine. Show cached values when available, accompanied by an XLSX preview notice that formulas are not recalculated and cached results may be stale or absent. Fresh MonoReport output normally has no formula caches. A compact read-only selected-cell formula display can use the library's [public selection context](https://github.com/yukiyokotani/office-open-xml-viewer/blob/main/packages/xlsx/src/selection.ts), which was exercised during research. Blank formula cells must not be presented as verified zero totals. If calculated totals in-browser are mandatory, this recommendation requires a separate scope/architecture decision.

## 7. Risks, performance and limitations

| Risk | Evidence and proposed boundary |
| --- | --- |
| Bundle cost | The production research Webpack build measured the existing DOCX renderer plus normalizer at **169 KiB raw / 48 KiB gzip**. The selected XLSX worker path requested approximately **4.89 MiB raw / 1.55 MiB gzip** across entry JavaScript, worker code and WASM. These are isolated harness assets, not final Playground bundle measurements. Lazy loading is material. |
| Startup | Single local runs: existing DOCX normalization/render API 4–130 ms; candidate DOCX load/layout 82–476 ms; small XLSX loads 35–49 ms in main mode and 77–107 ms in worker checks. Different rendering/pagination work and cached local assets prevent treating these as comparative benchmarks or user-facing targets. |
| Large workbooks | Not benchmarked. Workers reduce main-thread work but do not remove archive expansion, parsed-model or browser memory costs. Keep library archive/worksheet limits enabled, render the active sheet, and make preview resource failure recoverable. Agree a representative workbook/device target before promising capacity; the API's 50 MiB limit is not that target. |
| Bundler warning | Webpack 5.111.1 emitted a critical-dependency warning for a dynamic request in a model-source module. The tested XLSX entry and explicit worker mode worked without a custom patch. Keep the warning visible for implementation review; do not assume untested loading paths work or suppress it globally. |
| Fidelity | Browser fonts, wrapped text, number/date formats, merged borders and hidden/zero-size geometry can differ from Excel. The tender is a useful but small fixture. Charts, conditional formatting and other advanced features are not acceptance promises; many already reject in the engine. PrintArea/cropping concerns generation, while preview should initially show the authored sheet. |
| Security | Treat uploaded OOXML as untrusted. Keep resource guards, disable external font loading and hyperlink activation, avoid logging workbook contents, and do not execute formulas/macros or insert workbook strings as application HTML. Canvas rendering is not a complete parser-security boundary. Package/dependency advisories still require normal review. |
| Maturity/accessibility | Active 0.x development means API and compatibility churn. Pin the tested version and review updates deliberately. Canvas preview needs keyboard/tab/focus and assistive-technology checks; Chrome-only research does not establish Safari, mobile or screen-reader acceptance. |
| Analysis deferred | Users receive no early XLSX analysis panel or automatic JSON scaffold in minimum scope. They must author JSON themselves; data/template failures appear on Generate. Even existing Analyzer requirements cannot encode all hierarchy/cardinality rules. Preserve generation diagnostics and link existing authoring guidance; do not expand the engine to compensate. |

## 8. Decisions for Product Owner approval

1. Approve XLSX-only adoption of the tested `@silurus/ooxml` version, its permissive dependency/notice obligations, and its payload/maturity tradeoffs. Keep the current DOCX viewer and normalization unchanged.
2. Accept cached/absent formula-result preview, with clear notice and optional selected-cell formula text, rather than requiring browser recalculation. This is the main functional limitation of the recommendation.
3. Approve the minimum workflow independently of XLSX analysis/automatic JSON generation, and decide whether the low-cost existing Analyzer integration or a bundled XLSX example warrants inclusion now. Recommendation: defer both to keep scope smallest.
4. Agree the practical preview fidelity and workbook/device target, hidden-sheet policy, and recoverable handling of oversized/unrenderable workbooks. Recommendation: authored sheet view, visible worksheet navigation, no print-layout guarantee, and downloads preserved after preview failure.
5. Keep any DOCX consolidation proposal separate. Broader field/story/layout regression evidence and Owner acceptance would be required before changing existing viewer dependencies. No consolidation work is authorized by this research.

## 9. Recommended scope for the subsequent Feature Spec

1. Require ordinary XLSX upload, manual JSON entry, explicit generation through the existing route, real result preview, worksheet navigation and unchanged-byte XLSX download. Reuse the same preview for Template where available; a template-preview failure cannot block Generate.
2. Define a practical baseline of cell values, common fonts/fills/borders/alignment, number formats, supported merges, row/column sizing and hidden states. Include explicit formula-cache behavior and preview failure/download independence.
3. Preserve DOCX upload, preview, Generate JSON, examples, generation, downloads, existing replacement confirmations and stale-request protection. Keep editing, viewer consolidation, formula calculation, advanced Excel fidelity, server conversion, persistence, unrelated refactoring and feature flags outside this scope.
4. Defer standalone XLSX analysis UI, automatic XLSX JSON generation and full success-warning multipart presentation unless separately included by the Owner. No analysis enhancement is a prerequisite; generation error diagnostics remain mandatory.
5. Define focused frontend behavior checks and a small real browser/API acceptance flow for both formats, including multiple sheets, formula-cache absence, format switching and preview failure with download. Final production asset delivery, responsive layout and target-browser checks remain implementation acceptance work. This document completes architecture research; it is not an Implementation Plan.
