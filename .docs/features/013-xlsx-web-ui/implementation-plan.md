## 3. Integration design

1. **Format and bytes:** represent `docx` and `xlsx` explicitly. Use a case-insensitive supported extension only to choose the initial template viewer. Keep the original File for upload/template download. Normalize the generation response MIME, including parameters/case, to select result format independently of the template name, upload MIME, or filename supplied in the response. Add format to `GeneratedDocument`; reject empty bodies or unsupported/missing success MIME with a request diagnostic.
2. **Filename handling:** extend the existing Content-Disposition handling for both formats, preserving encoded filename support and rejection of separators, control characters, malformed escapes, and excessive length. Require a final extension consistent with response MIME; otherwise fall back to `document.docx` or `document.xlsx`. Keep the original response Blob for download and retain object-URL revocation. Never export or serialize viewer state.
3. **Preview dispatch:** use a narrow conditional at the existing Template/Result boundary and a focused `XlsxPreview` component. Load the `/xlsx` runtime dynamically inside the preview lifecycle so import failures can become preview messages. Do not load the XLSX runtime on the initial DOCX workflow. Supply a private ArrayBuffer from the source Blob/File, allowing worker transfer without changing upload/download bytes.
4. **Viewer configuration:** use `XlsxViewer` with explicit worker mode, built-in sheet tabs, authored visible-sheet order, hidden sheets skipped, external font loading disabled, and hyperlink activation disabled. Keep interaction read-only, including disabling row/column resizing controls. Use the library's existing resize support or a component-owned observer for Splitter/container changes. Do not add optional font, equation, legacy-format, or advanced-renderer imports.
5. **Lifecycle:** create an isolated host and viewer per source session. Guard every asynchronous boundary: import, byte read, viewer creation/load, readiness, sheet/render callbacks, and errors. Replacement, tab unmount, clear, format switch, and App unmount invalidate the session before destroying its viewer and releasing observers/listeners and owned resources. Dispose a viewer created after its session became obsolete. Use self-owned viewer loading so library destruction also releases its workbook/workers. Avoid retaining inactive Template and Result viewers in a cache.
6. **Failures and limits:** catch import/read/load failures and later `onError` render failures. Show a safe, preview-specific loading/error state within the relevant preview; a resource refusal may explain that the workbook exceeds preview limits. Do not clear the original template or successful result, disable generation/download, or move a preview error into generation diagnostics. A new source must recover without a page reload. Retain the pinned library's archive, worksheet, decoded-image, and worker-timeout guards; do not disable/raise them or equate them with the API's 50 MiB request limit. Record effective defaults during integration; no workbook-capacity promise or benchmark project is needed.
7. **Untrusted content:** verify the pinned XLSX path does not execute macros/formulas, follow external relationships/resources, or inject workbook text as application HTML. Set `useGoogleFonts: false` and `enableHyperlinks: false` explicitly. Render app messages as ordinary React text. Inspect actual worker behavior as well as the main entry; worker bundles can contain more code than the explicit entry imports. Do not rely on Canvas alone as a safety boundary or introduce global network hooks/CSP changes to compensate for a viewer defect.
8. **Layout and guidance:** give XLSX a full-width, bounded-height spreadsheet viewport with internal horizontal/vertical scrolling, visible worksheet tabs, and no DOCX paper maximum width. Preserve responsive Splitter behavior and external toolbars. Document approximate preview fidelity and the accepted formula-cache limitation in existing user guidance: formulas are not recalculated, cached results can be stale or absent, and uncached formula cells can appear blank. No new formula-warning UI element is required. Do not synthesize zeros or report missing caches as generation failures.
9. **Generate JSON and diagnostics:** retain the explicit Analyze action, shared requirement conversion, overwrite confirmation, pending state, revision checks before/after confirmation, and normal result invalidation when JSON changes. Explain that the scaffold needs editing and does not validate XLSX cardinality or other data-dependent constraints. Manual JSON generation never invokes analysis automatically. Display `part` alongside existing diagnostic context without redesigning Errors.

## 4. Incremental implementation stages

### 4.1. Stage 1 — XLSX upload and Template preview

1. **Dependency:** Product Owner approval of this plan. 2. Add the small format mapping for template selection. Update the common upload/drop path, picker filters, drop overlay, missing-template/error copy, and Template viewer dispatch for DOCX/XLSX. Preserve JSON and existing result invalidation on template replacement; keep server content validation authoritative.
3. Implement the XLSX wrapper and scoped layout described in Section 3, including worksheet navigation, representative styling, lifecycle isolation, worker disposal, safe options, built-in limits, and preview-only errors. Template preview must work before any API call and recover on source replacement or format switching.
4. Let Webpack emit the lazy entry, required worker/chunks, and WASM using the package's supported URLs and existing output conventions. Add only necessary asset handling; prefer native Webpack emission over custom copying/loader infrastructure. Keep runtime URLs local to the application. Do not suppress the dynamic-request warning observed in research; record whether the used path works and whether any warning remains.
5. Extend App tests for XLSX picker/drop, correct Template renderer selection, and preservation of JSON/result invalidation. Test the wrapper through existing mocked-library and deferred-promise patterns for source replacement, format switching, cleanup, preview errors, and recovery; do not load real WASM in jsdom.

## 6. Main regression risks and controls

1. **Format confusion:** template extension and server-selected output can differ. Separate template and result format metadata, test both response formats independently, and match downloads to response MIME.
2. **Stale UI and resource leaks:** lazy import, byte reads, worker loading, background rendering, requests, and example loads have separate completion times. Keep existing App revision guards and per-preview session guards; test delayed success and error paths and cleanup.
3. **Successful output lost on preview failure:** maintain generation state outside preview state; retain original bytes and enabled download when preview refuses or fails.
4. **DOCX behavior/layout changes:** preserve its renderer/normalization and paper styling. Scope spreadsheet styles and new lifecycle code to XLSX; retain existing regression tests and a real DOCX acceptance flow.
5. **Blank formula totals mistaken for data loss:** document the accepted preview limitation in existing user guidance, verify explicit caches separately, and inspect original downloaded formulas/settings. No new formula-warning UI is required. Do not change generator behavior to improve preview.
6. **Dependency/packaging gaps:** pin the artifact, inspect bundled worker obligations and advisories, emit all runtime assets/notices, and verify the published origin rather than relying on the development server. Keep unresolved Webpack warnings visible with evidence.
7. **Resource/security assumptions:** retain documented guards and verify inactive links, fonts, external resources, and inert text with a small fixture. Library guards are admission limits, not a strict browser-memory guarantee. Browser acceptance establishes the representative workflow, not universal workbook fidelity/accessibility or large-file capacity.
