# Feature 017 — Russian Name Inflection

**Status:** Research / On Hold

**Prepared:** 2026-11-02

## 1. Goal and approved scope

1. Add a separately registered `inflect` formatter that declines Russian personal names into a requested grammatical case in DOCX and XLSX templates.
2. Implement it in `MonoReport.Formatter.Inflect`, using the Core-owned `IFormatter` contract and the existing keyed formatter registration mechanism from [Feature 016](../016-formatter-plugins/feature-spec.md).
3. Keep case-name normalization and library adaptation inside the new formatter. Delegate component recognition and inflection to the selected library; do not create a local name parser. Do not change Core parsing, add a registration builder, or add a general localization mechanism.
4. Preserve existing formatter behavior and showcase content, adding one inflection demonstration immediately after the existing Spellout demonstration.
5. Do not begin implementation until this specification and the Product Owner decisions in section 8 are approved.

## 2. Completed library and runtime research

1. **Recommended candidate, subject to the decisions in section 8 — Morphos 3.2.30 as a separately deployed HTTP service.** Its source function accepts one, two, or three name tokens, and the official image exposes this through HTTP. Runtime verification confirms that no FIO object or `part` parameter is needed. However, Morphos does not infer arbitrary component ordering: one token is treated as a given name; two tokens are interpreted as surname then given name; three as surname, given name, patronymic. This fixed order is material to the input contract and needs Product Owner acceptance.
2. The official Docker image was pulled and run as `wapmorgan/morphos:3.2.30`. Its registry digest was `sha256:dc115a18f00097b14ebb2f65a0a064c37dc16c540897f81cf1845c4d22a1d86d`; the image ID was `sha256:71dcdd5209afb88ccf0b96474120b4c565221008660a17c4c80e5729817ec77f`. The bundled source tag points to commit `b7680f96101668ec910627239048e34aae64d6f8`, matching the 3.2.30 release. It started successfully: RoadRunner logged HTTP listening on `0.0.0.0:8080`, four workers started, and `GET /ru/cases` returned HTTP 200 with the six case keys. The host was arm64 and Docker ran the linux/amd64 image through emulation. PHP reported 8.2.8 and RoadRunner 2023.2.1. The temporary container was stopped and removed, and the newly pulled image/tag was deleted after verification.
3. Morphos is PHP rather than .NET. The service listens on port 8080 and accepts GET requests; the image uses PHP 8.2.8 CLI Alpine and RoadRunner 2023.2.1. Composer declares MIT and runtime dependencies on PHP, `ext-mbstring`, `spiral/roadrunner-http`, `nyholm/psr7`, and `nikic/fast-route`; the Docker image includes sockets support. MIT permits commercial use and redistribution with the notice retained. Source releases show 3.2.30, released 2025-06-27. Docker Hub's latest-image metadata still appears years older than that source release, but the requested 3.2.30 tag was available and its bundled Git tag/commit matched the release. Sources: [Morphos Dockerfile](https://github.com/wapmorgan/Morphos/blob/master/Dockerfile), [Morphos MIT license](https://github.com/wapmorgan/Morphos/blob/master/LICENSE.md), [Morphos releases](https://github.com/wapmorgan/Morphos/releases), [Docker Hub image](https://hub.docker.com/r/wapmorgan/morphos).
4. **Verified HTTP contract and representative results:** the running image routes `GET /ru/name` and reads query parameter `name` (plus optional `case` and `gender`). The README documents `fullname` for the API, but the image's `Russian::name` handler reads `name`; requests using `fullname` return HTTP 200 with an empty result. Direct inflection returns JSON shaped as `{"result":"..."}`. Omitting `case` returns `{"result":{"nominative":"...","genitive":"...","dative":"...","accusative":"...","ablative":"...","prepositional":"..."}}`. `GET /ru/cases` returns the case-key array and worked as a readiness probe. `GET /ru/detectGender?name=...` is the route listed by source. The HTTP behavior was observed directly against the official image, not inferred from README text.
5. Representative calls against the image:
   1. `GET /ru/name?name=Иванов+Петр+Сергеевич&case=dative` → HTTP 200, `{"result":"Иванову Петру Сергеевичу"}`.
   2. The same name with `case=дательный` returns the same result. Both `case=nominative` and `case=именительный` return `{"result":"Иванов Петр Сергеевич"}`. Thus nominative works directly despite being omitted from the README's explicit string list.
   3. `GET /ru/name?name=Иосиф&case=дательный` → `{"result":"Иосифу"}`; `GET /ru/name?name=Иванов+Петр&case=дательный` → `{"result":"Иванову Петру"}`. A three-token feminine name, `Иванова Мария Сергеевна`, returned `Ивановой Марии Сергеевне` in dative with automatic gender detection.
   4. Omitting case returned all six forms in one response. For the three-token sample, the keys were the six English keys above and values included nominative `Иванов Петр Сергеевич`, genitive `Иванова Петра Сергеевича`, dative `Иванову Петру Сергеевичу`, and instrumental under key `ablative`: `Ивановым Петром Сергеевичем`.
6. Morphos recognizes position by token count and applies fixed component classes; it does not detect/reorder “given name surname” input. Its source splits on spaces, treating token 1 as surname for 2/3 tokens and token 2 as given name (plus token 3 as patronymic for 3). The documented format is surname-first. The README's “automatic recognition” is therefore automatic dispatch by position, not arbitrary component classification.
7. Runtime edge behavior: an empty name returns HTTP 200 with `{"result":""}` for a requested case. An unknown two-token name (`Xyzabc Qwerty`) was returned unchanged as a string, so the caller cannot reliably distinguish an unrecognized name from a valid unchanged form. More than three tokens returns HTTP 200 with `{"result":false}`. A missing `name` returns HTTP 200 with an empty result and emits PHP warning/deprecation messages in service logs. A malformed query (`?%ZZ`) was not rejected; with no parsed arguments and no case it returned HTTP 200 with six empty forms. A bad case such as `not-a-case` returned HTTP 500 and plain text `Something Went Wrong!`; RoadRunner logged the exception and restarted the worker. A POST to `/ru/name` returned 405; an unknown path returned 404 when the worker was healthy. The Feature formatter must map/reject its own case literals before calling Morphos, detect non-string/false/malformed JSON responses, and map transport/server failures to a formatter diagnostic.
8. Morphos supports all six cases through both the direct endpoint and all-forms response. Its canonical English keys are `nominative`, `genitive`, `dative`, `accusative`, `ablative`, `prepositional`; Russian full names are accepted. It does not accept the Feature's English word `instrumental`; map that formatter alias to Morphos's `творительный` or `ablative` inside the formatter. The six English/Russian pairs can therefore be normalized locally. Automatic gender detection is uncertain for a lone given name. The Feature does not require a `gender` parameter; adding one would be a separate scope decision.
9. **NPetrovichLite 1.3.1** targets .NET Standard 2.0, has no package dependencies, and is MIT licensed. Its documented API inflects a word with a `NamePart`, or accepts a caller-populated `Petrovich.FIO` with separate surname, given-name, and patronymic properties. It does not document recognition from one string. It is maintained as a small package and is not a match for this Product Owner requirement. Sources: [NuGet package](https://www.nuget.org/packages/NPetrovichLite/1.3.1), [upstream API and license](https://github.com/mikhail-barg/petrovich-net-lite).
10. **NPetrovich 2.0.1** also expects separate name properties; it targets .NET Standard 2.0, depends on `System.Text.Json`, and is MIT licensed. It does not document automatic parsing of a plain full-name string. Sources: [NuGet package and dependency metadata](https://www.nuget.org/packages/NPetrovich/2.0.1), [upstream repository and MIT license](https://github.com/petrovich/petrovich-net).
11. **NameCaseLib.Core 9.0.1** targets .NET Standard 2.0/2.1 and documents whole-string `DetectGender(fullName)` and `QFullName(fullName, gender)` methods. The NuGet license expression is `MIT OR GPL-2.0-or-later`, with an MIT option suitable for commercial distribution if selected and its notice retained. However, its README documents only a three-component example, does not establish behavior for one- and two-component strings, and does not make the case mapping sufficiently clear for this requirement. It was last published 2023-10-17 and has limited visible adoption. It is not recommended over Morphos for the specified input shapes. Sources: [NuGet metadata and API](https://www.nuget.org/packages/NameCaseLib.Core/9.0.1), [NameCaseLib.NET repository](https://github.com/ExLuzZziVo/NameCaseLib.NET).
12. The deprecated `NameCaseLib` 0.4.2 package and unrelated `NameCaser` identifier-conversion package are excluded. No free, permissively licensed .NET library found in this research verifies automatic single/two/full-name recognition. Morphos is the only investigated candidate with explicit whole-string format documentation for all three shapes. Sources: [deprecated package notice](https://www.nuget.org/packages/NameCaseLib/0.4.2), [NameCaser package description](https://www.nuget.org/packages/NameCaser/1.0.0).
13. **Recommendation and verification state:** within the approved Morphos-over-HTTP direction, Morphos 3.2.30 is the simplest verified candidate that avoids a MonoReport name parser. The formatter must send `name`, not the README's `fullname`, map `instrumental` to `творительный`/`ablative`, and handle the observed result variants. Runtime behavior for tag 3.2.30 has been verified; the Docker Hub “latest” metadata discrepancy remains, but the requested tag was available and matched source commit `b7680f9`. The surname-first input convention remains for Product Owner approval. If order-independent recognition is required, no investigated permissively licensed .NET candidate has been verified to satisfy it; custom parsing would require a separate scope decision.

## 3. Async formatter and generation research

1. `IFormatter.Format` is synchronous and public in Core. `ValueFormatter.Format` dispatches to it synchronously. DOCX rendering calls it during `DocumentRenderer` traversal; XLSX binding/planning calls it from `XlsxTemplatePlanner.PrepareValue` before `XlsxDocumentRenderer` applies the prepared values. `MergeEngine.Merge` currently executes both formats synchronously.
2. The async-only design should replace `IFormatter.Format` with `Task<string> FormatAsync(..., CancellationToken cancellationToken)`, and replace public generation with `Task<MergeResult> MergeAsync(..., CancellationToken cancellationToken = default)`. Keep `IFormatter.Validate` and `TemplateAnalyzer.Analyze` synchronous: Analyze parses/validates formatter metadata but does not generate formatted values, and the case aliases can be normalized locally. Do not add sync wrappers or dual interfaces. Update all in-repository formatter implementations to the one async contract; CPU-only formatters can return `Task.FromResult` or use a completed async implementation.
3. The required internal propagation is `ValueFormatter.FormatAsync` → DOCX `DocumentRenderer` traversal and XLSX `XlsxTemplatePlanner.PrepareValue` plus its Bind/BindSheet/BindInstances callers → `XlsxTemplateHandler` → `MergeEngine.MergeAsync`. Any loops or LINQ projections that invoke formatter evaluation must await it while preserving current ordering and deterministic diagnostics. `XlsxDocumentRenderer` and Open XML package manipulation may stay synchronous because they consume already prepared values; only add async there if the implementation proves it performs formatter work.
4. API generation is already an async endpoint and should await `MergeAsync`, passing `HttpContext.RequestAborted`. API Analyze remains sync after its async multipart read. CLI `Program.Main` and `CliApplication.Run` should become async generation entry points and await `MergeAsync`; pass a cancellation token through the CLI, including Ctrl+C cancellation if supported by the existing host flow. CLI Analyze can remain synchronous. The public library surface should expose only async generation; tests and in-repository consumers should call/await the new methods.
5. Cancellation must reach the Morphos `HttpClient` request and be checked between render/planning iterations that may otherwise continue substantial work after cancellation. Failures from timeout, cancellation, unavailable service, malformed response, and invalid name should be translated consistently to formatter/generation diagnostics without swallowing `OperationCanceledException` as an ordinary formatting error.
6. Async-only avoids sync-over-async blocking, permits normal request cancellation, and gives every formatter one execution contract. It is source-breaking inside the repository but the Product Owner has confirmed MonoReport has no external consumers requiring API compatibility and explicitly authorized replacing public Core APIs. A dual contract would add dispatch paths and unclear behavior for remote-only formatter execution without serving a compatibility need. Use `Task`, not `ValueTask`, for the simplest uniform contract; local formatter overhead is small beside document processing and remote HTTP latency, while `ValueTask` would add consumption constraints for little benefit here.
7. The migration touches Core contracts/engine/rendering, the built-in and Spellout formatter implementations, API and CLI composition/callers, and tests/helpers that currently call synchronous Merge. It does not require making Analyze async, changing Core parsing, making Open XML I/O async, or adding a separate async-prerequisite Feature. Include this migration in Feature 017 because it is necessary for the selected remote formatter and the Product Owner has approved the API change.

## 4. Proposed user-visible behavior

1. The template formatter key is `inflect`. It accepts one required string parameter named `case`, supplied positionally or by name. Supported values are the six full English case names and their full Russian equivalents:
   1. `nominative` / `именительный`
   2. `genitive` / `родительный`
   3. `dative` / `дательный`
   4. `accusative` / `винительный`
   5. `instrumental` / `творительный`
   6. `prepositional` / `предложный`
2. Both spellings of a case produce the same output. Normalize and map these values in the Inflect formatter only. Match case-insensitively using ordinal rules and trim surrounding whitespace. Do not accept abbreviations, translated parameter names, or additional locales.
3. Supported invocation forms are the existing positional and named string-parameter forms, such as `{Person inflect "dative"}` and `{Person inflect case="дательный"}`. A missing or unsupported case value is a formatter validation error during Analyze/preflight, including when the value expression is in an inactive branch.
4. The input remains one scalar string; no `part` parameter is required. Pass it intact to Morphos; do not classify, split, or reorder components in MonoReport. Morphos treats one token as a given name, two as surname then given name, and three as surname, given name, patronymic. It does not detect alternate orders.
5. Do not promise accurate automatic gender detection for a lone given name or non-Russian names. Morphos infers gender and accepts optional `gender=m|f`; this Feature does not expose that parameter unless implementation evidence and separate Product Owner approval justify it.
6. Null, undefined, and exactly empty string values render as empty under the existing scalar formatter bypass; whitespace-only strings are not covered by that bypass. Morphos returns an unknown two-token input unchanged and returns JSON `false` for more than three tokens. Product Owner approval is needed for unchanged unknown-name results; the formatter should fail generation for `false`, empty results on a non-empty request, malformed responses, or service errors. Do not partially parse or rewrite input in MonoReport.

## 5. Proposed architecture and integration

1. Create one `MonoReport.Formatter.Inflect` project referencing Core and call the Morphos HTTP service through an injected `HttpClient`. Do not add another business/service layer. Use the async-only formatter and generation contracts described in section 3.
2. Configure the Morphos base address and HTTP timeout through formatter connection options registered in API and CLI DI. Keep transport configuration out of Core. Exact option names and defaults remain a proposal for Feature Spec approval.
3. Register `inflect` through `AddMonoReportInflectFormatter()` in the formatter project, following the established Spellout convention. API and CLI explicitly reference and register it. Add the project to solution and Docker build inputs as needed. Core remains independent; do not add a registration builder.
4. Use formatter metadata for a required string `case` parameter and set `case` as the positional target. Validate and normalize English/Russian case names only in the formatter; Core parsing remains unchanged.
5. Send the original scalar name as one URL-encoded `name` query value to `GET /ru/name` (the image expects `name`, though the README says `fullname`). Map English `instrumental` to Morphos `творительный` or `ablative`. Use the direct-case request and require a non-empty string in `result` for non-empty input. Treat `false`, empty/missing results, non-success HTTP responses, and invalid JSON as formatter failures. Do not split/reorder the name or store per-call values in shared state.
6. Add an entry immediately after `Russian RUB words` in `Samples/syntax-showcase.template.docx` and matching name data to `Samples/syntax-showcase.json`. Preserve existing examples. Use a three-component Russian name and a named case value; include its output in the showcase table.
7. Do not add `gender`, `part`, alternate-order recognition, runtime discovery, new Core parser syntax, or unrelated documentation/UI work.

## 7. Draft acceptance criteria for Feature Spec approval

1. `MonoReport.Formatter.Inflect` implements `IFormatter`, uses template key `inflect`, and is registered explicitly by API and CLI without Core dependency or a new registration builder.
2. `case` is required and works positionally or by name. Each supported English case name is equivalent to its Russian full-name alias; invalid values fail formatter validation without Core parser changes.
3. Single, two-token surname-first, and three-token surname-first names are accepted as one string without a `part` parameter. MonoReport does not split, classify, or reorder components; alternate token ordering is not promised.
4. Morphos handles the documented name shapes; gender behavior follows its detected/default behavior. No optional `gender` parameter is added unless the Product Owner separately approves evidence that it is necessary.
5. The DOCX Syntax Showcase contains a demonstration immediately after Spellout, with matching JSON sample data and expected output. Existing examples and results are preserved.
6. Focused functional tests and DOCX/XLSX Analyze/Generate verification cover the new behavior and relevant regression boundaries. Generation tests and callers await the async-only API; analysis remains synchronous.
7. Morphos 3.2.30 or another explicitly approved version is used with a pinned deployment image. The formatter sends `name`, maps `instrumental` to `творительный`/`ablative`, parses the direct-case JSON string response, and handles false/error results. MonoReport does not parse components itself.

## 8. Product Owner decision record

### 8.1 Approved decisions and constraints

1. The formatter accepts a full, two-component, or single Russian name as one string without a `part` parameter.
2. A grammatical case is required and can be positional or named. English and Russian full case names are equivalent; normalization belongs inside the formatter, with no Core parsing change or general localization mechanism.
3. The feature uses one separately registered `inflect` formatter in `MonoReport.Formatter.Inflect`, explicitly registered by API and CLI. Do not add a registration builder or make Core depend on the formatter.
4. The DOCX Syntax Showcase gets one demonstration immediately after Spellout with corresponding sample JSON; existing examples and behavior are preserved. Focused formatter tests and DOCX/XLSX integration verification are in scope.
5. MonoReport has no external consumers requiring synchronous API compatibility. Public APIs may be replaced to provide one async-only formatter and generation contract; do not retain sync wrappers, dual APIs, or compatibility layers solely for hypothetical consumers.
6. Preserve the current architecture direction: one `inflect` formatter calls Morphos through HTTP, with configurable connection options. The exact deployment image and option defaults remain open.
7. Feature 017 is on hold at the research stage. Do not implement or create an Implementation Plan until the Feature Spec is approved.

### 8.2 Proposals to finalize

1. Configure an injected `HttpClient` directly in the Inflect formatter; provide a configurable service base address and timeout via formatter options and DI. Do not add an extra service layer. Finalize option names and default timeout during Feature Spec approval.
2. Use the async-only `IFormatter.FormatAsync` and public `MergeAsync` design in section 3. Keep validation and template analysis synchronous because they do not execute formatting.
3. Pin the service image by immutable digest. The verified tag digest is recorded in section 2; confirm whether that exact image or a later verified image will be used in each deployment.
4. Preserve unchanged Morphos output for unknown names, while failing on `false`, empty/missing results for non-empty input, malformed responses, and service errors. This is the current behavior proposal pending the question in section 8.3.

### 8.3 Unresolved Product Owner questions

1. **Deployment details:** identify where the Morphos HTTP service will run, who owns its availability and updates, and whether the verified digest or a later verified version will be pinned. Morphos HTTP integration itself is the approved architecture direction.
2. **Input ordering:** approve the fixed convention verified in Morphos: two tokens mean `Surname GivenName`; three mean `Surname GivenName Patronymic`. Morphos does not infer arbitrary component order. If order-independent recognition is required, a custom parser would need a separate scope decision.
3. **Unknown-name output:** decide whether Morphos returning the input unchanged is acceptable or should be reported as a diagnostic. Its API has no recognition flag, so unchanged output cannot be distinguished from a valid unchanged form. The proposal is to preserve the returned string and fail on `false`, empty/missing results for non-empty input, malformed responses, or service errors.
