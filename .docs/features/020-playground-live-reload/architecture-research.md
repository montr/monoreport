## 4. Selected polling mechanism

1. While Live Reload is enabled, start one immediate read and a nominal 1,000 ms interval per selected usable Template/JSON handle. Each sample obtains a fresh File from the original retained handle and completes a full content read. Compare Template bytes and exact decoded JSON text, including whitespace; metadata is diagnostic/accepted-save context only. Equal-size/equal-timestamp content changes must be detected.
2. Baseline sampling must reconcile against the currently accepted workspace snapshot, not merely establish an isolated diagnostic baseline. A disk change between selection and enable must reach Preview/current inputs. Unchanged content preserves Template File identity and JSON text/baseline; timestamp-only changes do not render or regenerate. Update accepted Save metadata only when current content actually matches the accepted baseline/editor under Section 6.
3. Permit at most one native read in flight per source handle across interval, page-return and explicit refresh paths. Busy interval ticks are skipped, with no catch-up queue. A pending call from an obsolete binding using the same handle must settle before a new read uses it. Independent handles progress independently; a slow Template must not stop JSON sampling.
4. Keep only the accepted content and the transient candidate needed for comparison. Compare bytes directly; do not hash, retain history, cache requests, or copy diagnostic metrics/counters into production. Preserve accepted File identity on equal bytes to avoid viewer recreation and duplicate work. Native calls cannot generally be aborted; binding/read/reset guards make late completions inert.
5. **Only confirmed effective input changes invalidate generation and schedule regeneration.** A normal tick, read start, unchanged content, metadata-only change, dirty-JSON disk conflict, or baseline-only reconciliation does not advance the generation content revision or abort a request. Polling must not starve a Generate taking longer than one second. A real Template change or adopted/editor JSON change invalidates obsolete publication immediately, before the generation debounce.
6. On visible-page/pageshow return, request an immediate reconciliation. If a read is pending, invalidate its pre-return result and coalesce restoration events into one fresh follow-up after it settles. Prevent pre-return automatic continuations from publishing as current before reconciliation. Do not add another recurring loop, queue missed ticks, or prompt for access. Hiding alone need not trigger a read; hidden scheduling remains browser-controlled.
7. Production contains only polling for external changes. Stage 3 retired the temporary observer, continuation/resubscription, hybrid, directory and diagnostic-only polling implementations, their wiring and obsolete tests/UI/helpers. Retain useful production behavior regressions and historical evidence in the implementation plan; no runtime strategy selector or diagnostic query remains.

## 5. Stable snapshots and current Generate inputs

1. **Replace mandatory eager copying on every acquisition with stable materialization at consumer publication.** Retaining a handle or obtaining File metadata is not itself a reason to copy. Separate the retained source capability, transient fresh read and accepted consumer content. Before publishing a disk-backed Template to asynchronous Preview or a request, complete the byte read and detach its accepted content from external modification. Preserve name/type/lastModified and the handle separately. Typical Open immediately starts Preview, so this boundary can still require one initial materialization; this is not a promise of zero-cost Open. Guard asynchronous preparation against newer selections/reset/unmount.
2. Reuse bytes already read for selection, polling or Generate preparation. Compare candidates before creating another accepted File; equal content preserves accepted File identity and discards the candidate. Materialize only a new accepted version, not another copy for every getFile, unchanged poll or consumer. Known byte-backed example/generated inputs need no defensive recopy. Retain only the comparison data actually required by the selected equality implementation, without parallel byte histories or redundant manual copies.
3. The [File API](https://www.w3.org/TR/FileAPI/) defines byte-copy semantics when constructing a Blob/File from a BufferSource. Wrapping an old File, slicing it or creating an object URL does not establish detachment from its underlying file. Fresh getFile directly into FormData avoids an old reference but still leaves a change-before-consumption race; it is insufficient for the stable-input guarantee. A byte-backed File built once from a complete read is the conservative compatible solution with existing consumers. Stage 2 must confirm the narrowest necessary materialization sites before implementation, rather than enforce copying in every acquisition helper.
4. Existing DOCX Preview delegates Blob reading to docx-preview/JSZip; XLSX Preview awaits source.arrayBuffer after a dynamic import and then creates its workbook. These consumer reads already allocate full buffers, but can start after disk modification. Keep a stable accepted source across delayed rendering, view switches and later requests; do not rely on an earlier successful render to stabilize the original File. A consumer-owned buffer alternative is only justified if it demonstrably preserves all those lifetimes with fewer copies and no broader viewer redesign. Do not expose or transfer the sole accepted comparison buffer to a worker.
5. Confirmed Template changes refresh Template Preview even while invalid editor JSON or busy operations prevent generation. Result Preview remains the last successful generated Blob. With Live Reload off, Template Preview remains the stable selected content until explicit refresh/Open/Generate; no off-mode polling or implicit continuous disk freshness is promised. Upload/drop without a handle must establish stable selected content before consumption; failure retains prior usable state and requires reselection rather than pretending disk refresh is possible.
6. Manual Generate fully refreshes a handle-backed Template immediately before dispatch, including with Live Reload off. Automatic Generate uses that same preparation path, sharing a pending current read where appropriate; a completed earlier poll alone does not establish current disk content. Compare the fresh bytes and reuse an equal stable accepted File, or materialize the changed version once. Do not add an upload-specific copy after stable preparation or send an old render closure. Without a handle, use stable accepted upload/example content.
7. Preparation is an await inside the existing useDocumentActions operation lifecycle. Acquire existing operation ownership/busy protection before preparation; reuse its operation ID, AbortController, pending/status, diagnostics, Result and success/error/finally guards. After a guarded refresh commit, capture current Template, Dataset and exact editor text from refs/explicit inputs and establish the request revision. An owned refresh must not cancel its own operation; unrelated edits/rebind/reset still obsolete it. Do not add a preparation controller, second busy state, competing generation state machine or result-publication owner.
8. Share the narrow source-read path through existing workspace/hook composition. A pending-read reference/promise and binding token per source serialize data access; they do not own request lifecycle. LocalFiles owns reads/content rules; useLiveReload owns source timers/listeners and one debounce, then invokes the existing Generate action. Keep Analyze and Generate Dataset consuming stable accepted inputs through their existing paths. No broker, queue, new operation coordinator or broader command redesign.
9. Complete byte capture is stable against later disk modification, but cannot prove Office finished a multi-step save. Read failure retains accepted Template/Result and shows source unavailability; retry on the next scheduled tick while enabled. Explicit Generate reports failed fresh capture and sends no stale upload. Unreadable Template blocks automatic dispatch/unverified publication; other sources keep sampling. Recovery releases eligible cancelled/unattempted work even for equal content, without retrying an unchanged actual server failure every tick.
10. The existing Generate owner guards success/error/finally by operation ID, final input revision and current binding. Reconcile a relevant already-pending source read before publication and recheck those same guards; do not create a second response queue or wait for future ticks. Same-content reads permit publication; changed/failed required reads reject it. Retain the last successful Result on start/failure. Abort is best-effort; freshness is relative to accepted/reconciled inputs, not atomic external disk knowledge. Template and JSON are not an atomic disk transaction; later confirmed changes invalidate the old result normally.

### 5.1. Memory implications and unresolved optimization

1. For a compressed Template of size S, retaining a native File reference does not imply an S-byte JavaScript allocation. A full arrayBuffer read adds S bytes; snapshot construction from those bytes can add another S-sized backing representation. Keeping comparison bytes plus a detached File therefore has approximately 2S of logical compressed content. During replacement, old accepted data, a new candidate and its new File can coexist, approaching 4S before consumer allocations if representations are separate. These are allocation scenarios, not a guaranteed RSS multiplier or product size limit.
2. Browser storage and sharing are implementation-dependent: [Chromium's Blob design](https://chromium.googlesource.com/chromium/src/+/main/storage/browser/blob/README.md) describes backing references, browser-process storage and disk spill. Do not call the accepted File necessarily resident in JavaScript memory or promise zero-copy construction. Immutability from disk changes is the required property; browser-managed backing is acceptable without application disk writes or a new storage subsystem.
3. DOCX ZIP/decompression/rendering and XLSX read buffers/workbook/worker add memory beyond compressed file size; requests and generated Result coexist. Existing resultInputs and in-flight closures can retain older Template Files while the last successful Result is kept. Do not add snapshot history or duplicate consumer buffers to that lifetime. Any buffer-transfer optimization must first verify actual ownership and avoid detaching accepted comparison data.
4. Stage 2 records the read/materialization sites and live references; Stage 5 measures representative small/larger DOCX/XLSX, combined polling, Preview and Generate. Measure renderer heap, browser/worker pressure, GC and responsiveness where available; JavaScript heap alone cannot establish total cost. Actual copy counts, browser spill and peak memory remain unresolved. No metadata-only shortcut, slower cadence, silent size cap, OPFS cache or generic byte-storage layer is approved to conceal those costs.

## 6. JSON editor authority and Save reconciliation

1. Generate always uses current editor text, including unsaved changes. Built-in JSON parsing gates automatic dispatch only: invalid editor JSON cancels pending automatic work and invalidates older publication; correction resumes after the shared debounce without Save/toggle cycling. Keep Monaco diagnostics and the existing explicit Generate validation workflow. Never substitute hidden disk JSON for invalid editor text.
2. Continue full-content JSON sampling regardless of dirty state, editor validity, Template presence or generation availability. If current text equals baseline, valid changed disk text can update the same Dataset's text/baseline/accepted lastModified together. Recheck Dataset/handle/editor state after reading; an intervening edit invokes dirty handling instead of being overwritten.
3. If dirty editor text, disk text and baseline diverge, preserve editor text and show disk divergence at the existing combined status location. Store only the current disk comparison needed for status/Save, separately from accepted baseline/lastModified; do not queue file versions. A disk-only conflict does not regenerate unchanged editor inputs. Template/editor changes still generate with editor text.
4. Disk equals editor text: reconcile baseline/lastModified and clear modified/conflict status without generating solely for that reconciliation. Disk equals baseline: no new conflict. When editor becomes clean, reread current disk before import instead of adopting an old deferred sample. Exact text comparison preserves formatting changes.
5. Invalid or unreadable disk JSON stays out of the editor; retain accepted text/baseline/Result, expose a source-specific problem and keep polling for recovery. Valid current editor JSON remains usable for generation. Invalid disk content must still be recognized as external divergence for Save protection; parsing failure cannot imply unchanged disk. Do not advance accepted modification time merely because a failed/conflicting sample was observed.
6. Coordinate disk adoption with existing saving/savingRef: do not import during Save, then reread after the written-snapshot/current-edit reconciliation. Preserve edits made during the write and rebind on Save As. Discard obsolete reads across binding/write boundaries. Save/Save As remain the only application writes.
7. Preserve explicit overwrite confirmation and known divergence even when metadata is unchanged. Save must check current disk content against the accepted baseline, not depend on the last poll or lastModified alone; an external same-metadata edit can occur between samples or while Live Reload is off. Reuse LocalFiles comparison and existing confirmation, without a transaction/write queue. A race between the last check and an external write cannot be made atomic through this browser API.
8. Explicit Grant access/Reopen must really reread/rebind while preserving unsaved-change safeguards. Current same-file Open shortcuts cannot silently retain stale File/text during recovery. A matching self-save/poll is a content no-op and does not trigger another Generate.

## 7. Generation scheduling and cleanup

1. One trailing generation debounce, initially 500 ms, coalesces effective Template/editor changes. Sampling cadence and generation debounce are separate: never postpone a full-content poll merely because the editor keeps changing, or regenerate because an interval elapsed. Required source reconciliation completes before automatic dispatch. Invalid editor JSON pauses generation, not polling/Template Preview.
2. Reuse existing Generate/Analyze/Generate Dataset/dialog busy guards; explicit operations have priority. Reconsider the latest workspace inputs when the existing owner becomes available. One last-attempted input revision shared with manual Generate prevents duplicates and busy-to-idle retry loops. useDocumentActions remains the sole owner of operation IDs, cancellation, request dispatch, pending/status and all outcome publication, including asynchronous input preparation. Source-read serialization and the debounce must not become a second request lifecycle. Do not retain queued input snapshots or serialize physical server work through another coordinator.
3. An unchanged server failure waits for content change, explicit Generate or re-enable. A cancelled/undispatched attempt must not permanently consume its revision: no-op refresh/recovery can release eligible current work without an automatic failure loop. Cover this distinction and long unchanged polling during requests in verification.
4. Off per visit; enabling refreshes sources and generates when current valid inputs have no matching Result, otherwise waits for changes. Later automatic success preserves the active Template/Result view; first success can use existing Result activation. Manual Generate retains its behavior. No persisted toggle/settings or new consent flow; explain automatic requests in the existing dropdown context.
5. Disable clears polling intervals, page listeners, debounce and automatic publication continuations, without cancelling unrelated explicit work. A manual snapshot read can finish under its explicit owner; a stopped automatic owner cannot publish it. Source close/replacement, Save As, Clear Local Data and unmount invalidate applicable source bindings and reads; release accepted/candidate references when no longer needed. A pending same-handle native read cannot be bypassed by re-enable/rebind.
6. Closing Result cancels pending automatic dispatch/publication that could reopen it; it does not remove source monitoring. A later confirmed input change can schedule new work. Stale success/error/finally, obsolete read callbacks, and old preview work must not reopen Result, overwrite new inputs or clear a newer operation.
7. No per-save observer reconnection, repeated permission prompts, immediate retry loop, timeout/backoff framework, request cache, state-machine infrastructure or disk watcher backend is required. A permanently hung native call remains a verification risk; do not pretend that ignoring its result aborts it.

## 8. Preview and source status

1. Keep source-driven, single-session Preview replacement and existing stale-render isolation. Template content no-ops keep File identity and viewer state. Generation/read failure retains successful Result; renderer failure after successful generation keeps existing preview-error/download behavior. No staged rendering, parallel workbook, candidate promotion or rollback guarantee.
2. Preserve view state best-effort using existing public APIs only where normal refresh testing shows a need: XLSX visible sheet by name, then scale/logical offsets; DOCX outer-canvas scroll after render; Monaco save/restore view state for same-Dataset model replacement. Keep worksheet fallback/clamping, Name Box/formula bar and viewer-before-workbook cleanup. Unrelated source switches may reset state; exact semantic positions after document restructuring are not guaranteed.
3. Keep one checked Live Reload item in Generate's dropdown, reachable during requests. Reuse Dataset's modified-indicator position for accessible modified/editor-live/disk-monitored/divergence status and Template's existing control/header even while Result is selected. Never mark generated Result as a monitored source or use color alone.
4. External monitoring status requires enabled polling and a successful readable sample for that binding. Failed reads remove the healthy/current claim while retries continue; initial access/remembered handles/timers alone are insufficient. Use existing source feedback and Grant access/Reopen, without repeated toasts or a separate status framework. Editor-only operation remains available per unsupported/unusable source.
5. A one-second interval is nominal, not a maximum detection/generation latency or background freshness promise. Background/frozen/discarded pages can delay or stop execution; visible-page reconciliation must occur before restored automatic work is treated as current. Do not promise every intermediate save or complete disk history.

## 10. Risks and verification requirements

1. **Large-file cost remains open:** full reads/comparison cost roughly scales with Template plus JSON size per second while reads fit the interval. Retained snapshot, candidate buffer/File, viewer/workbook and request data can coexist and create memory/GC pressure. The reported DOCX totals lack sizes and do not validate large DOCX/XLSX/JSON. Measure representative small/larger real files, sizes, acquisition/read/comparison times, skipped intervals, responsiveness, memory and combined-source load, both idle and saving. Record API/logical-byte measurements separately from physical disk claims. No new size cap, slower cadence, hashing or metadata filter is approved; return to the Product Owner if evidence requires a material trade-off.
2. **Background tabs:** test short/long hidden periods, minimized window, sleep/resume, pageshow and available freeze/discard behavior. Timers may be throttled/suspended; immediate return reconciliation and obsolete-read suppression are essential. Continuous background polling remains best-effort with browser-controlled cost; no worker, wake lock, audio trick or background real-time guarantee is proposed.
3. **Handle replacement/read failures:** repeat Word DOCX and Excel XLSX saves, same-path replacement and subsequent saves without reselection, through both production Open and Drag & Drop. Check late handle acquisition, unsupported/rejected/null/non-file fallback and selection/disable/unmount cleanup. Record exact browser/OS/Office versions, location, source size and raw logs; cloud/network folders and unavailable platforms stay unverified. Polling cannot recover a permanently invalid handle; expose Reopen rather than expanding permissions silently.
4. **Stale File investigation:** reproduce reported ERR_UPLOAD_FILE_CHANGED with Live Reload off/on and record whether failure occurs during native read, viewer load or upload. Verify Preview and actual multipart bytes consume the fresh accepted stable content after Word/Excel saves and remain readable if disk changes during lazy render/upload. Test Open/upload/drop/restoration/recovery, delayed consumers, selection races and current refs. Record necessary materialization sites and reuse before adding copies. Source inspection and mocked invalidation support the risk analysis but cannot establish the exact reported browser cause or fix.
5. **External JSON:** real external edits/replacement, clean import, dirty preservation, invalid disk/correction, disk/editor/baseline combinations, intervening editor changes, and same-metadata Save confirmation remain production validation gaps.
