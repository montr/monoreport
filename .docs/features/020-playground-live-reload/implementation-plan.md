### 2.3. Pass/fail criteria and mechanism decision

1. **Pass:** all exercised repeated saves, same-path replacements, and subsequent saves produce native notifications and complete fresh reads through the retained handles, with current content reaching the existing Generate workflow and Result. No Playground reselection, reload, per-save resubscription, or manual Generate is needed after the baseline. Duplicate notifications may coalesce. A single successful save, API presence, or mocked callbacks cannot pass this gate.
2. **Fail or incomplete:** missed settled updates, observation termination, stale content, or unreadable retained handles fail the affected scenario. Separate native/read failures from experimental wiring, API, or renderer failures; an unrelated generation/Preview error alone does not prove native observation unsuitable. Correct minimal experiment defects and repeat affected checks; unavailable environments or unresolved downstream failures remain Pending rather than passing by assumption.
3. **Decision point before further monitoring work:** record the manual scenario matrix, evidence, limitations, and conclusion in the architecture record. If reliable, continue with native observation in the planned production stages. If native observation fails ordinary Office saves or required replacement/subsequent-save behavior, stop further native monitoring work and investigate polling before selecting a replacement mechanism. First establish whether the same handles remain readable; polling cannot repair unusable handles. Do not add polling alongside this experiment or use API absence alone to broaden browser coverage.
4. **Stage 1 exit is feasibility only:** submit the experiment and manual evidence for Product Owner review; acceptance does not make it production-ready or waive Stages 2–5. Independent editor-only work can proceed after a documented outcome while monitoring is blocked. Broader folder permissions, dependencies/helper/backend work, changed browser coverage, or weaker guarantees require a new Product Owner decision before affected implementation.

Failed observer subscription attempts wait for a later successful poll read before retrying. An unresolved `observe()` is logged as timed out after 5,000 ms and disconnected, but its pending-call lock remains until the browser promise settles, preventing overlapping subscriptions. Polling continues while it is pending. A terminal event while that promise is pending also cannot cause overlap. Late successes/failures cannot reactivate a detached observer. Log fields distinguish `metadataChanged`, `contentChanged`, and `metadataOnlyMiss` (unchanged metadata with different bytes); the initial successful sample has no prior comparison. Semantic unchanged saves can still change Office package bytes. This diagnostic intentionally measures full-byte audit cost, not a metadata-only optimization.
